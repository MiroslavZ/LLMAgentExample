# Функциональность агента и требования к будущему чату

Дата анализа: 15 сентября 2026 года.

Документ описывает текущую реализацию по исходному коду и существующим тестам. Его цель — помочь спроектировать интерфейс NiceGUI и определить границы адаптации. Разделы 1–8 описывают существующее поведение; разделы 9–11 содержат предложения, которые ещё не реализованы. Внешний API в рамках этого анализа не вызывался; совместимость его возможностей с выбранной моделью отдельно не проверялась.

## 1. Общее устройство

Сейчас это текстовый диалоговый агент для DeepSeek с сохранением истории, несколькими режимами управления контекстом и учётом токенов. Автономного цикла выполнения задач и вызова инструментов в коде нет.

CLI выполняет один запрос или одну операцию управления ветками за запуск. Продолжение разговора происходит при следующем запуске с тем же файлом истории. Интерактивного цикла чтения сообщений из терминала нет.

| Модуль | Ответственность |
|---|---|
| [main.py](main.py), [llm_agent/__main__.py](llm_agent/__main__.py) | Запуск CLI через `python main.py` или `python -m llm_agent` |
| [llm_agent/cli.py](llm_agent/cli.py) | Аргументы, загрузка `.env`, сценарий запуска, Rich-вывод и часть проверок |
| [llm_agent/agent.py](llm_agent/agent.py) | Клиент модели, обычный запрос, мета-промптинг, сжатие, обновление facts |
| [llm_agent/history.py](llm_agent/history.py) | Сообщения, системный промпт, память, расход токенов, чтение и запись JSON |
| [llm_agent/context_strategy.py](llm_agent/context_strategy.py) | Окно сообщений и правила обновления facts |
| [llm_agent/branch_history.py](llm_agent/branch_history.py) | Ветки, checkpoints, выбор активной ветки, сохранение снимков |

`Agent` уже доступен как Python-класс и сам не печатает в терминал. Веб-интерфейсу не требуется запускать CLI как подпроцесс или разбирать его текстовый вывод.

## 2. Пользовательские сценарии

### 2.1. Обычный запрос

Метод: `Agent.request(user, ...)`.

Последовательность:

1. Установить системный промпт, если его ещё нет.
2. При включённом сжатии проверить порог и при необходимости обновить summary.
3. В режиме facts обновить постоянную память отдельным запросом к модели.
4. Собрать контекст из истории и нового сообщения; применить окно, если оно включено.
5. Синхронно получить ответ DeepSeek.
6. Одной записью сохранить пользовательское сообщение, ответ и его расход токенов.
7. Вернуть `RequestResult`.

Ввод и сохраняемый ответ — строки. Для отображения CLI использует Markdown либо подсветку JSON. Потоковой выдачи токенов, вложений и отдельного сохранения текста рассуждений нет. Основной ответ сохраняется и при `finish_reason`, отличном от `stop`; пустой `content` сохраняется как пустая строка. Это отличается от строгих проверок служебных ответов сжатия и facts.

### 2.2. Мета-промптинг

Метод: `Agent.request_with_meta_prompt(user, ...)`.

Один пользовательский запуск выполняет два основных запроса:

1. По исходной задаче модель генерирует улучшенный промпт. Используется фиксированная инструкция `META_PROMPT_SYSTEM`, формат всегда `text`.
2. Сгенерированный текст автоматически отправляется как новый пользовательский запрос. Применяются системный промпт диалога и выбранный формат итогового ответа.

Первый этап получает доступную историю и память, но вместо исходного системного промпта — инструкцию генерации промпта. Второй этап получает актуальную историю, включая сохранённый первый этап, с учётом возможного сокращения контекста.

Особенности:

- В историю добавляются две пары: исходная задача → сгенерированный промпт; сгенерированный промпт → итоговый ответ. Окно или сжатие могут затем удалить часть этих записей.
- Промежуточного подтверждения или редактирования промпта пользователем нет.
- Оба результата возвращаются вместе после завершения всего метода; промежуточного события результата первого этапа нет.
- Если второй этап завершился ошибкой, первый остаётся сохранённым, но метод не возвращает пару результатов.
- Сжатие проверяется перед каждым этапом. Facts обновляются один раз по исходному сообщению; сгенерированный промпт не обновляет память повторно.
- Модель, температура, максимальный ответ и stop-последовательности общие для обоих основных этапов.

**Значение для UI:** один пользовательский ход может включать несколько сетевых операций. Полезно показывать сгенерированный промпт как отдельный раскрываемый результат, а не как второе сообщение, которое пользователь якобы ввёл вручную. Для надёжного восстановления такого представления сейчас не хватает метаданных этапов.

### 2.3. Системный промпт

`HistoryManager.set_system_prompt()` сохраняет первый переданный непустой текст. Его можно добавить после начала разговора. Если промпт уже установлен, новое значение игнорируется, а не заменяет его.

Он хранится первым сообщением с ролью `system`, сохраняется между запусками и не входит в размер окна или хвоста сжатия. Служебные инструкции для мета-промптинга, summary и facts не заменяют сохранённый промпт.

Отдельного метода изменения существующего промпта нет. `clear()` позволяет установить новый, но одновременно очищает весь текущий диалог и его статистику. В ветке, созданной из checkpoint с промптом, этот промпт уже установлен.

**Значение для UI:** поле существующего промпта должно отражать это ограничение. Обычная кнопка «Сохранить изменения» без доработки ядра будет вводить в заблуждение.

### 2.4. История и очистка

- История автоматически читается из файла; по умолчанию это `history.json` в текущем рабочем каталоге.
- Можно использовать отдельные файлы для разных диалогов. Каталоги и файл создаются при сохранении.
- `get_messages()` возвращает копию подготовленного контекста без `usage`, включая служебные блоки summary/facts. Это не специализированный метод получения ленты для UI.
- `get_messages(include_system=False)` убирает только основной системный промпт; блоки summary/facts всё ещё могут иметь роль `system`.
- `add_message()`, `add_messages()` и `add_exchange()` доступны из Python, сохраняют данные без обращения к модели.
- `clear()` сбрасывает сообщения, системный промпт, summary, facts и накопленные счётчики; в режиме branch — только активную ветку.
- Команды CLI для очистки, удаления отдельных сообщений, поиска или экспорта нет.

## 3. Режимы контекста и памяти

### 3.1. Сводная таблица

| Режим | Что получает основной запрос | Что происходит со старыми текстами | Дополнительные вызовы модели |
|---|---|---|---|
| Обычный, без стратегии и сжатия | Вся доступная история и сохранённая память, если она была в файле | Не удаляются автоматически | Нет |
| Сжатие в summary | Summary и несжатый хвост; до порога — доступная история | Сжатые сообщения заменяются summary без текстового архива | Один на каждое срабатывание сжатия |
| `window` | Системные сообщения и последние N сообщений, включая текущий запрос | Удаляются из памяти и файла | Нет |
| `facts` | Системный промпт, словарь facts и последние N сообщений | Удаляются после извлечения/обновления памяти | Один перед обычным запросом или всей парой мета-промптинга |
| `branch` | Весь доступный контекст активной ветки | Автоматически не сокращаются | Нет для управления ветками |

Это взаимоисключающие режимы в текущем API. `branch` нельзя сочетать с `window`, `facts` или сжатием. Сохранённые summary/facts могут быть унаследованы веткой, но автоматически не обновляются.

### 3.2. Сжатие в summary

Настройки: `last_messages >= 0` и `compress_every > 0`; нужны обе. Если задана только одна, сжатие выключено; CLI выдаёт предупреждение.

Перед запросом берутся все старые сообщения, кроме последних `last_messages`. Если их количество не меньше `compress_every`, вся эта старая часть вместе с предыдущим summary передаётся выбранной модели для создания нового summary.

Пример: при 16 сообщениях, хвосте 6 и пороге 10 первые 10 сообщений заменяются summary. Считаются отдельные сообщения, не пары. Текущий новый запрос ещё не включён в этот подсчёт. Между сжатиями хвост может быть больше 6.

Служебный запрос использует фиксированную инструкцию и формат `text`, без пользовательских температуры, stop и `max_tokens`. Summary передаётся в дальнейшем отдельным системным справочным блоком `<summary>`.

Сохраняются новый summary, хвост и накопленный расход. Полные тексты сжатой части не архивируются. При успешном сохранении вызывается `on_compression(CompressionResult)` с числом заменённых сообщений и статистикой служебного запроса.

Размер summary в токенах не ограничен отдельной настройкой. Сжатие не привязано к `context_limit` и не гарантирует, что следующий запрос поместится в контекст модели.

### 3.3. Скользящее окно `window`

Настройка: положительное целое `window_size`.

Сохраняются последние N отдельных сообщений пользователя/ассистента. Системный промпт не входит в N. Правило действует и при отправке запроса, и после сохранения ответа.

При N=1 модель видит системный промпт и текущий user, а после ответа в файле остаются системный промпт и только assistant. Поэтому сохранённая история может начинаться с ответа, а не с вопроса.

При открытии длинного файла через менеджер с этой стратегией сокращение может произойти уже в конструкторе, до отправки нового запроса. Прежние summary и facts удаляются; накопленный расход сохраняется.

### 3.4. Постоянная память `facts`

Настройка: положительное целое `window_size`; ограничение последних N сообщений такое же, как у `window`.

Память — словарь строковых ключей и строковых значений. Отдельный запрос к модели извлекает цели, предпочтения, ограничения, решения, имена и точные значения. Модель возвращает JSON изменений:

- строка добавляет или заменяет значение;
- `null` удаляет ключ;
- отсутствующий ключ сохраняется;
- `{}` означает отсутствие изменений.

Основной ответ получает эту память отдельным блоком `<facts>`. В Python доступны копия `history.facts` и флаг `history.has_facts`; пустой инициализированный словарь отличается от ещё не созданной памяти.

При первом включении facts старая доступная история и summary используются для извлечения памяти до сокращения. На следующих обновлениях учитываются прежние facts, доступный контекст и новое сообщение пользователя. Исходные удалённые тексты восстановить нельзя.

Обновление и его расход сохраняются до основного запроса. Если основной запрос падает, facts уже могут содержать сведения из пользовательского сообщения, которого ещё нет в сохранённой ленте. Размер словаря не ограничен отдельным параметром. В обычном режиме сохранённые facts читаются, но не обновляются; переход к window удаляет их.

`update_facts()` доступен как низкоуровневый метод менеджера с параметром расхода, но готового пользовательского сценария ручного редактирования facts нет. Передача `usage=None` учитывается как служебный ответ без статистики, поэтому напрямую использовать этот метод для редактора памяти без уточнения семантики не стоит.

### 3.5. Ветки и checkpoints `branch`

В одном файле находятся независимые снимки веток и неизменяемые checkpoints. Начальная ветка — `main`.

| Операция | Поведение |
|---|---|
| `list_branches()` | Список имён веток |
| `list_checkpoints()` | Список имён checkpoints |
| `active_branch` | Имя текущей ветки |
| `create_checkpoint(name)` | Снимок текущей ветки: сообщения, промпт, память и расход |
| `create_branch(name, from_checkpoint=...)` | Копия checkpoint в новую ветку с немедленным переключением на неё |
| `switch_branch(name)` | Переключение контекста и сохранение выбора в файле |
| `clear()` | Очистка активной ветки без изменения соседних веток и checkpoints |

Имена не могут быть пустыми или содержать пробелы по краям; внутренние пробелы разрешены. Повторное имя в соответствующем списке отклоняется. Checkpoint и ветка имеют отдельные пространства имён. Отсутствующие ветки/checkpoints вызывают ошибку.

Checkpoint без `--user` создаётся из текущего состояния; с `--user` — после успешного запроса, включая оба этапа мета-промптинга. Создание и переключение ветки выполняются до запроса и могут остаться сохранёнными, даже если последующая работа с API не удалась.

Управление через `BranchHistoryManager` не требует ключа или вызовов API. CLI также разрешает эти операции без `.env` и `--user`.

Ограничения:

- Ветка создаётся только от именованного checkpoint, не от произвольного сообщения.
- Нет удаления, переименования, слияния веток, восстановления checkpoint поверх текущей ветки или сравнения изменений.
- Не сохраняются связи «родительская ветка → checkpoint → дочерняя ветка», время создания и подписи. Список доступен, достоверное дерево происхождения из текущего формата не восстановить.
- Активная ветка записана на весь файл; это не независимый выбор для каждой браузерной вкладки.
- Расход ветки включает общую предысторию до checkpoint. Сумма расходов всех веток повторно посчитает общий префикс.

## 4. Полный набор параметров запуска

Значения ниже описывают код проекта, а не гарантии поддержки параметров внешним API.

| CLI | Значение и поведение | Возможное место в UI |
|---|---|---|
| `--user` | Текст запроса; требуется кроме операций управления ветками | Поле ввода |
| `--model` | Строка имени модели; по умолчанию `deepseek-chat`, списка доступных моделей нет | Настройки запроса |
| `--system` | Первый системный промпт; уже установленный не заменяется | Настройки диалога |
| `--max-tokens` | Положительное целое; без значения параметр не отправляется | Дополнительные настройки |
| `--temperature` | `float`; справка заявляет 0–2, но код диапазон не проверяет | Дополнительные настройки с явной валидацией |
| `--stop-sequences` | Ноль или несколько строк; пустой список не отправляется | Дополнительные настройки |
| `--response-format` | `text` по умолчанию, `object` или `schema` | Настройки формата |
| `--meta-prompt` | Два этапа вместо одного | Переключатель режима отправки |
| `--history` | Путь к файлу истории; по умолчанию `history.json` | Основа будущего выбора диалога |
| `--context-limit` | Положительное целое для арифметики в CLI; не передаётся агенту/API | Статистика и настройки отображения |
| `--last-messages` | Неотрицательный размер хвоста при сжатии | Настройки контекста |
| `--compress-every` | Положительный порог старых сообщений для сжатия | Настройки контекста |
| `--strategy` | `window`, `facts`, `branch`; без параметра — обычный режим | Настройки диалога |
| `--window-size` | Положительное число сообщений для window/facts | Настройки контекста |
| `--branch` | Выбор существующей ветки | Список веток |
| `--checkpoint` | Создать checkpoint сейчас либо после запроса | Действие над веткой |
| `--create-branch` | Имя создаваемой и сразу активируемой ветки | Диалог создания ветки |
| `--from-checkpoint` | Источник новой ветки | Выбор checkpoint |
| `--list-branches` | Вывести ветки и checkpoints | Навигационная панель |
| `--help`, `-h` | Стандартная справка argparse | Справка по возможностям |

Правила сочетания:

- Window/facts требуют `window_size`; с другими режимами этот параметр запрещён.
- Любая явно выбранная стратегия запрещает параметры сжатия.
- Все параметры веток требуют `strategy=branch`.
- Создание ветки требует одновременно `create_branch` и `from_checkpoint`; совместить его с `branch` нельзя.
- CLI разрешает только одно из действий `checkpoint`, `create_branch`, `list_branches` за запуск.
- `list_branches` нельзя совместить с `user`. Без `user` нельзя задавать `system` или `meta_prompt`.
- Ряд проверок находится только в `parse_args()`. При прямом вызове `Agent` их нельзя считать автоматически выполненными: например, пустой ввод, диапазон температуры и выбор формата требуют отдельного решения в UI/сервисном слое.

### Форматы ответа

`text` отправляет `{"type": "text"}`, `object` — `{"type": "json_object"}`, `schema` — только `{"type": "json_schema"}`.

В проекте нет поля для самой JSON Schema, её передачи и проверки результата по схеме. Поэтому наличие пункта `schema` в CLI не означает готовую поддержку структурированных ответов по пользовательской схеме. Перед переносом в UI его нужно доработать или явно обозначить ограничение.

Основной ответ в формате object/schema не валидируется перед сохранением. CLI лишь пытается красиво отформатировать JSON и при ошибке показывает исходную строку. Для обновления facts JSON, типы и завершённость ответа проверяются отдельно.

### Подключение и сохранение настроек

`BASE_URL` зафиксирован в `agent.py` как `https://api.deepseek.com`. Ключ передаётся в конструктор; CLI читает `API_KEY` из окружения после загрузки `.env` в корне проекта. Значения окружения имеют приоритет. Однако текущий `load_env()` требует существования файла даже при уже заданном `API_KEY`.

Настройки модели, температуры, формата, мета-промптинга, режима контекста, размеров окна/сжатия и `context_limit` в истории не сохраняются. Они задаются при создании агента или каждом запросе. В файл сохраняются данные разговора и, для branch, активная ветка. При перезапуске UI настройки нужно будет восстанавливать отдельно.

## 5. Результаты и статистика

`RequestResult` содержит:

- `content` — текст первого ответа;
- `response` — исходный `ChatCompletion`, включая `finish_reason` и доступный `usage`;
- `elapsed` — время одного основного вызова API, без сжатия, facts и записи истории;
- `dialogue_usage` — снимок накопленного расхода на момент сохранения этого ответа.

| Показатель | Как трактовать |
|---|---|
| `prompt_tokens` текущего ответа | Вход конкретного запроса, включая отправленную историю |
| `completion_tokens` | Выход; может включать рассуждения, если API их учитывает |
| `total_tokens` | Общий расход конкретного запроса |
| `history.get_usage()` | Накопленный расход диалога/активной ветки, включая служебные запросы |
| `missing_responses` | Число сохранённых ответов/служебных операций без статистики |
| Cache hit/miss, reasoning tokens | Детали текущего ответа, если API их вернул; уже входят в основные счётчики |
| `finish_reason` | Причина завершения ответа, например достижение лимита |
| `elapsed` | Длительность конкретного основного этапа, а не всего пользовательского хода |

Счётчики берутся из API; локального предварительного подсчёта токенов и расчёта цены нет. Неизвестный расход отмечается как неполный. Итог учитывает повторную отправку истории и не является размером контекста.

`context_limit` используется только после получения ответа: CLI показывает `prompt_tokens / context_limit`, остаток и остаток после вычитания `max_tokens`. Это не предварительная проверка, не автоматическое сжатие и не ограничение отправки запроса.

В истории сохраняются только три счётчика `usage` у assistant и общая архивная статистика. Не сохраняются время, модель, `finish_reason`, детализация кэша/рассуждений, настройки запроса и тип этапа. Поэтому после открытия старого диалога можно восстановить суммарный расход, но не все подробности прежних запросов.

## 6. Хранение и конкурентный доступ

Поддерживаются три структуры JSON:

1. Линейный список сообщений с `role`, `content`, необязательным `usage` у assistant.
2. Объект с `messages`, `summary`, `archived_usage` и необязательным `facts`.
3. Хранилище веток: `version=1`, `active_branch`, `branches`, `checkpoints`; каждое значение ветки/checkpoint — снимок одного из линейных форматов.

Старые линейные файлы поддерживаются. При переходе в branch история становится `main`; формат файла меняется при первом сохранении. Другие режимы отказываются открывать файл веток.

Запись выполняется через временный файл, `fsync` и атомарную замену. Состояние памяти обновляется после успешной записи. Повреждённые JSON, сообщения, память и счётчики отклоняются без перезаписи исходного файла. В branch проверяются также неактивные ветки и checkpoints.

Атомарная замена защищает от частично записанного JSON, но не обеспечивает работу нескольких писателей. Линейный менеджер не проверяет, изменился ли файл другим экземпляром. Branch сравнивает файл с загруженной версией и отклоняет устаревшую запись, но не использует межпроцессную блокировку.

**Значение для UI:** операции с одним файлом должны выполняться последовательно. Для branch это ограничение касается всего хранилища, а не только отдельной ветки. Переключение ветки или очистка во время запроса могут привести к сохранению ответа не в тот контекст, поэтому такие действия нужно сериализовать вместе с запросами.

## 7. Ошибки и частично выполненные операции

Один вызов агента не является общей транзакцией: подготовка контекста и каждый основной этап сохраняются отдельно.

| Ситуация | Что остаётся сохранённым |
|---|---|
| Ошибка чтения/валидации файла | Исходный файл не перезаписывается |
| Ошибка основного API до ответа | Новая пара не добавляется; ранее установленный промпт и успешные служебные изменения остаются |
| Ошибка или незавершённый/пустой ответ summary | Сжатие не применяется, основной запрос не выполняется |
| Ошибка JSON, типов или завершённости facts | Обновление не применяется, основной запрос не выполняется |
| Успешные summary/facts, затем ошибка основного запроса | Обновлённая память и её учтённый расход остаются |
| Ошибка второго этапа мета-промптинга | Сохранён первый этап и возможные служебные изменения |
| Ответ API получен, но сохранение не удалось | Метод завершается ошибкой; новая запись в истории не подтверждена, хотя API уже мог израсходовать токены |
| Ошибка создания checkpoint после ответа | Ответ уже сохранён, checkpoint не создан |
| Файл веток изменён другим экземпляром | Запись отклоняется; менеджер требуется загрузить заново |

Расход служебного ответа, который не прошёл проверку или не сохранился, не попадает автоматически в историю. Поэтому счётчики проекта не следует трактовать как полную сверку биллинга провайдера.

CLI переводит `ValueError` и `OSError` в завершение без traceback. Унифицированной обработки всех ошибок SDK и структурированного результата частичного выполнения нет. `on_compression` вызывается после сохранения; ошибка самого callback тоже способна прервать дальнейший сценарий.

## 8. Чего в агенте сейчас нет

Этот список фиксирует границы реализации, а не обязательства добавить все перечисленные возможности:

- Вызовов инструментов/function calling, MCP, выполнения команд, поиска в интернете, RAG и работы с содержимым загруженных файлов.
- Изображений, аудио, видео и мультимодальных сообщений.
- Потокового ответа, публичных async-методов, прогресса по всем этапам и отмены запроса.
- Подтверждений действий пользователем, паузы и продолжения выполнения.
- Каталога диалогов с ID, названиями, датами, поиском, переименованием и удалением.
- Полного несокращаемого архива переписки при использовании окна/summary/facts.
- Редактирования/удаления отдельных сообщений, регенерации ответа и ветвления от выбранного сообщения.
- Истории изменений facts/summary, пользовательского редактора памяти и отдельной кнопки ручного сжатия в публичном API агента.
- Хранения этапов мета-промптинга и ошибок как отдельных событий с ID.
- Авторизации пользователей, разграничения доступа и управления браузерными сессиями.
- Сохранения конфигурации диалога и выбора произвольного API-провайдера через публичные параметры.

## 9. Предлагаемая организация NiceGUI

Следующая компоновка — предложение на основе существующих функций, не реализованный интерфейс.

### Центральная область: разговор

- Лента сообщений user/assistant с Markdown и отображением JSON.
- Поле ввода, кнопка отправки, переключатель мета-промптинга.
- Состояние «выполняется» и сообщение об ошибке без потери набранного текста.
- Сгенерированный промпт как раскрываемый этап хода.
- Пометка незавершённого или пустого ответа по данным результата.

На первом этапе допустим ответ целиком после завершения запроса. Кнопка «Остановить» требует отдельной реализации отмены; прекращение ожидания в UI само по себе не останавливает текущий синхронный вызов и последующее сохранение.

### Левая панель: навигация

- Выбор диалога и создание нового: поверх отдельных файлов нужен небольшой каталог.
- В режиме branch — список веток, активная ветка, список checkpoints.
- Действия «Создать checkpoint» и «Создать ветку из checkpoint».
- Очистка текущего диалога/ветки с точным описанием последствий.

Обычные диалоги и ветки одного диалога следует показывать как разные сущности. Для первой версии достаточно списков; дерево происхождения потребует новых метаданных.

### Правая панель или вкладки

| Вкладка | Содержимое | Доступность данных сейчас |
|---|---|---|
| Настройки | Модель, промпт, параметры ответа, режим контекста | Параметры есть; сохранения полной конфигурации нет |
| Память | Текущие facts в таблице и summary как текст | Есть `facts`, `summary`; история изменений отсутствует |
| Контекст | Что доступно модели, размер окна/хвоста, режим | Есть подготовленный контекст; предварительная оценка токенов отсутствует |
| Статистика | Последний запрос, накопленный расход, неполные данные | Суммы восстанавливаются; детали текущего ответа доступны только в `RequestResult` |

Для первой версии память лучше показывать только для чтения. При просмотре контекста надо пояснять, что подготовка запроса может ещё изменить его через сжатие или обновление facts.

## 10. Что потребуется адаптировать

### 10.1. Отделить ленту чата от контекста модели

Это главное решение перед разработкой UI. Сейчас окно и сжатие физически удаляют сообщения. Если лента должна сохранять всю переписку после перезагрузки страницы, нужен отдельный архив пользовательских ходов, из которого строится сокращаемый контекст.

Также полезны ID сообщений/ходов, время, тип этапа, статус и модель. Текущая валидация истории запрещает неизвестные поля, поэтому просто дописать метаданные в существующие сообщения нельзя без изменения формата или отдельного хранилища.

### 10.2. Ввести небольшой сервисный слой

Предлагаемые обязанности:

- Открыть/создать диалог и восстановить его настройки.
- Владеть экземпляром агента и последовательностью операций над файлом.
- Проверить параметры до возможных изменений истории и вызовов API.
- Выполнить запрос вне блокирующего обработчика интерфейса.
- Вернуть отображаемый результат, статистику и сведения о частичном успехе.
- Управлять ветками/checkpoints/очисткой через тот же механизм последовательного доступа.

Не требуется переносить Rich-рендеринг в ядро: UI должен получать данные из `RequestResult` и менеджеров. Загрузку ключа и конфигурации стоит отделить от обязательного CLI-файла `.env`.

### 10.3. Согласовать длительные операции и события

Сейчас есть только callback успешного сжатия. Для точных статусов нужны события начала/окончания подготовки памяти, генерации промпта, основного ответа и сохранения. Для потокового ответа потребуется изменить запрос к API и определить правила сохранения неполного результата.

Простое выполнение синхронного агента в рабочем потоке может стать первым шагом, но само по себе не решает отмену, параллельные изменения одной истории и восстановление после закрытия вкладки.

### 10.4. Сохранять настройки и контролировать смену режима

Режим и размеры контекста следует выбирать при создании диалога и сохранять отдельно. Смену режима существующего диалога нужно проектировать явно: конструктор window способен сразу удалить тексты/память, а branch меняет формат хранения. Нельзя использовать создание агента с новым режимом как безобидный предпросмотр настройки.

### 10.5. Представлять частичный результат

Нужны различимые состояния: запрос не выполнен; память обновлена, ответ не получен; первый этап выполнен, второй не завершён; ответ получен, запись не подтверждена. Повторная отправка должна учитывать уже сохранённые этапы, иначе возможно дублирование сообщений и дополнительных затрат.

## 11. Рекомендуемый объём первой версии

1. Решить, нужна ли полная лента независимо от выбранного режима контекста; определить хранение сообщений и настроек.
2. Добавить выбор диалога, отправку текста, отображение ответа и ошибки, последовательное выполнение запросов.
3. Перенести настройки, обычный запрос и мета-промптинг с учётом промежуточных результатов.
4. Добавить просмотр памяти/статистики и текущие операции веток/checkpoints.
5. Проверить восстановление после обновления страницы, ошибку второго этапа и конфликт доступа к истории.
6. Отдельно расширять ядро для streaming, отмены, редактирования сообщений или памяти, если они понадобятся.

Переход на UI сам по себе не требует добавлять отсутствующие инструменты, RAG или многопользовательский режим.
