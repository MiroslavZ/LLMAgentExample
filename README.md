# LLMAgentExample

Агент на Python для запросов к DeepSeek API.

## Индексация документов — день 21

Отдельный CLI разбивает Markdown/TXT по фиксированному размеру или структуре,
вычисляет локальные эмбеддинги и сохраняет два SQLite-индекса с метаданными.
Сборка, просмотр чанков, проверочный поиск и сравнение: [INDEXING.md](INDEXING.md).

```shell
python -m llm_agent.indexing corpus
python -m llm_agent.indexing build --strategy all
```

## Оркестрация MCP — день 20

Агент выполняет многошаговые запросы с инструментами любых подключённых
MCP-серверов. Пользователь задаёт цель обычным сообщением в веб-чате или CLI;
модель выбирает инструменты и порядок, агент маршрутизирует вызовы и сохраняет
журнал цепочки. GitHub → NIST NVD → Telegram используется как демонстрационный
пример. Настройка подключений, пример запроса и проверки:
[ORCHESTRATION.md](ORCHESTRATION.md).

## Композиция MCP-инструментов — день 19

Один запрос запускает цепочку `search_repositories → summarize → save_to_file`.
Модель выбирает шаги по описаниям инструментов, а агент передаёт результаты по
ссылкам на предыдущие вызовы, без перепечатывания данных. Сервер суммаризует
данные через LLM и возвращает готовый UTF-8 TXT; в веб-чате появляется кнопка скачивания.
Файл и журнал цепочки остаются доступны после перезапуска чата.

Добавьте `LLM_API_KEY` в `MCPServerExample/.env`; по умолчанию суммаризатор использует
`LLM_BASE_URL=https://api.deepseek.com` и `LLM_MODEL=deepseek-chat`.
Пример запроса: «Найди 5 репозиториев по language:python stars:>10000,
суммаризуй через summarize и сохрани сводку в repositories.txt через save_to_file».
Настройка и проверка: [MCP.md](MCP.md#композиция-инструментов--день-19).

## Планировщик и фоновые задачи — день 18

cron или Windows Task Scheduler запускает CLI с обычным сообщением `--user`.
Агент собирает данные через MCP, сохраняет результаты и по следующему запросу
строит сводку через локальный `local_read_observations`, в том числе после сжатия истории.
Для запуска без терминала доступен `--batch` (JSON и код завершения).
Модель выбирает инструменты по промпту; сводку можно запросить только по накопленным данным.
Настройка и примеры: [SCHEDULING.md](SCHEDULING.md).

## Собственный MCP-инструмент — дни 16–17

Агент получает схемы инструментов через Streamable HTTP, передаёт их DeepSeek,
исполняет выбранные моделью `tool_calls` и возвращает результаты модели для ответа.
Собственный сервер в [MCPServerExample](MCPServerExample/README.md) предоставляет
восемь инструментов чтения GitHub, суммаризацию и сохранение TXT.
В чате сохраняются аргументы, результаты вызовов и вложения.

1. Установите зависимости: `python -m pip install -r requirements.txt`.
2. Укажите `API_KEY` DeepSeek в корневом `.env`.
3. Запустите сервер: `python MCPServerExample/server.py`.
4. В другом терминале запустите `python -m llm_agent.web`.
5. В **MCP → Добавить MCP** оставьте `http://127.0.0.1:8000/mcp`, включите
   **Использовать в чате**, сохраните и проверьте **Get tools**.
6. Напишите: «Получи через MCP сведения о репозитории octocat/Hello-World:
   основную ветку, количество звёзд и ссылку».

Если сервер требует авторизацию, добавьте его `MCP_ACCESS_TOKEN` в корневой `.env`
и укажите **имя переменной** в форме. GitHub-токен задаётся только в
`MCPServerExample/.env`; публичные данные доступны и без него.
Для VPS укажите `https://ваш-домен/mcp` и отдельный MCP-токен.
Существующие подключения дня 16 нужно явно включить для использования моделью.

Тот же сценарий из терминала:

```shell
python -m llm_agent --mcp-url http://127.0.0.1:8000/mcp --user "Получи сведения о репозитории octocat/Hello-World"
```

Настройка, протокол, ошибки и проверки: [MCP.md](MCP.md).
Публикация на VPS с HTTPS: [README сервера](MCPServerExample/README.md#настройка-удалённого-доступа).

## Инварианты — день 14

Стек, архитектура, технические решения и бизнес-правила задаются отдельным
JSON-файлом. Агент проверяет запрос до генерации и весь ответ до сохранения,
включая план и предлагаемое изменение состояния задачи. При конфликте он
объясняет отказ со ссылкой на правило и сохраняет текущий этап и шаг.

```shell
python main.py --invariants-import examples/invariants/python-agent.json
python main.py --invariants-show
python main.py --user "Перепиши сервер на Node.js"
```

По умолчанию CLI и веб из корня проекта используют `data/invariants.json`.
В браузере правила доступны в панели «Инварианты агента»: кнопка «Изменить правила»
открывает форму добавления, редактирования и удаления с явным сохранением.
Они действуют во всех диалогах независимо от
профиля, стратегии контекста и перезапуска. Без файла правил проверка выключена.
Для текстовых правил используется отдельная LLM-проверка; её семантическая
точность не гарантирована. Настройка, стоимость вызовов, сценарии отказа и
проверки описаны в [INVARIANTS.md](INVARIANTS.md).

## Состояние задачи и контролируемые переходы — дни 13 и 15

Режим задачи хранит цель, этап `planning → execution → validation → done`,
текущий шаг, план, результаты и ожидаемое действие. Один запрос выполняет
один шаг; пауза и возобновление сохраняют прогресс между запусками.
Состояние передаётся модели отдельно от сокращаемой истории.
Граф переходов и допустимые действия проверяются кодом. Предложенный план
остаётся в `planning` до явного утверждения пользователем; новый план после
`replan` также требует утверждения. Завершение разрешено только из `validation`
с итогом проверки, когда сохранены результаты всех пунктов.

В браузере используйте панель «Состояние задачи»: задайте цель, нажмите
«Начать задачу», затем «Продолжить шаг». Когда появится план, проверьте его
и нажмите «Утвердить план» либо отправьте правки в чат. Для CLI
заменяйте `<ID>` на ID диалога, напечатанный первой командой:

```shell
python main.py --new-conversation --task-start "Подготовить функцию сложения и примеры на Python"
python main.py --conversation <ID> --task-continue
python main.py --conversation <ID> --task-show
python main.py --conversation <ID> --task-approve
python main.py --conversation <ID> --task-continue
python main.py --conversation <ID> --task-pause
python main.py --conversation <ID> --task-show
python main.py --conversation <ID> --task-resume
python main.py --conversation <ID> --task-continue
```

Создание, просмотр, утверждение плана и управление паузой не вызывают API.
Пока план не утверждён, `--task-continue` отклоняется с пояснением;
правки передаются через `--user`. Согласие текстом не заменяет явную команду.
Обычные чаты остаются
доступны без запуска задачи. Устройство автомата, формат состояния и сценарии
проверки описаны в [TASK_STATE.md](TASK_STATE.md).

## Персонализация — день 12

Профили пользователя задают обращение, язык, стиль, формат, ограничения и
контекст. Выбранный профиль автоматически применяется к каждому следующему
запросу и обоим этапам мета-промпта. Он хранится отдельно от памяти и истории,
переживает перезапуск и не теряется при сжатии или обрезке контекста.

В браузере выберите профиль в настройках диалога; кнопка «Профили пользователя»
открывает создание и редактирование. В CLI можно импортировать готовые примеры:

```shell
python main.py --profile-import examples/profiles/beginner.json
python main.py --new-conversation --profile beginner --user "Как добавить кэширование результатов медленной функции?"
```

Инструкция, второй профиль для сравнения и правила приоритетов:
[PERSONALIZATION.md](PERSONALIZATION.md).

## Модель памяти — день 11

У агента три отдельных слоя: текущий диалог, рабочая память задачи и общая
долговременная память (единый словарь общих сведений). В браузере откройте
«Память агента»; записи рабочей и долговременной памяти сохраняются явно,
через выбор слоя, ключа и значения. Обычное сообщение само по себе их не меняет.
Новый диалог получает пустую рабочую память и общие
долговременные записи. Все слои переживают перезапуск приложения.

Стратегии окна, фактов и сжатия продолжают управлять контекстом текущего
диалога. Явные записи подмешиваются отдельно и не обрезаются окном.
Подробности хранения, правила сохранения, CLI-примеры и сценарии проверки:
[MEMORY.md](MEMORY.md).

## Чат в браузере (NiceGUI)

Из корня проекта, с установленными зависимостями и `API_KEY` в `.env` или
окружении, запустите:

```shell
python -m llm_agent.web
```

На Windows можно использовать интерпретатор существующего окружения напрямую:

```powershell
.\venv\Scripts\python.exe -m llm_agent.web
```

Откроется [локальный чат](http://127.0.0.1:8080). Без ключа интерфейс доступен
для просмотра и настройки диалогов; отправка включается после настройки ключа
и перезапуска сервера. Ключ не передаётся в браузер и не сохраняется в диалогах.

### Как пользоваться

- **Слева:** создание, выбор и удаление диалогов. Название автоматически
  формируется из первого сообщения. Удаление требует подтверждения в интерфейсе.
- **В центре:** полная переписка и поле сообщения. Перед первой отправкой
  можно задать системный промпт. Затем он доступен только для чтения справа.
  `Ctrl+Enter` / `⌘+Enter` отправляет сообщение, `Enter` добавляет новую строку.
- **Справа:** состояние задачи, профиль, стратегия контекста и её параметры. Стратегию можно выбрать
  до первой отправки. После начала диалога меняются только числовые параметры.
  Кнопка «Сохранить настройки» сохраняет их для следующего запроса; отправка
  также применяет изменения, внесённые в этой вкладке. Конфликтующие изменения
  из другой вкладки отклоняются с сообщением.
- **Параметры запроса:** мета-промпт, температура от 0 до 2 и лимит токенов
  ответа. Пустые числовые поля используют значения по умолчанию у модели.
  Мета-промпт выполняется в два этапа; улучшенный промпт доступен в раскрываемом
  блоке, включая случай ошибки итогового ответа.

| Стратегия | Что передаётся агенту | Изменяемые параметры |
|---|---|---|
| Вся история | Весь контекст диалога | — |
| Скользящее окно | Последние N отдельных сообщений и системный промпт | Размер окна |
| Факты диалога | Локальные факты, последние N сообщений и системный промпт | Размер окна |
| Сжатие истории | Краткое содержание старой части и последние сообщения | Размер несжатого хвоста, порог сжатия |

Размер окна считается в отдельных сообщениях, включая текущий запрос,
а не в парах «вопрос–ответ». Изменение параметров действует со следующей
отправкой. Увеличение окна не возвращает уже удалённые из контекста стратегии
сообщения. Полная переписка при любой стратегии остаётся в чате.
Извлечение фактов и сжатие выполняют дополнительные запросы к модели.
При любой стратегии дополнительно передаются непустые рабочая и долговременная
память и выбранный профиль; их сохранение не вызывает модель.
При включённом режиме задачи дополнительно передаётся её формальное состояние.
Мета-промпт в этом режиме недоступен: формат ответа управляется протоколом задачи.

Во время ответа можно открыть или создать другой диалог. Запрос принадлежит
исходному диалогу и продолжает выполняться при обновлении или закрытии страницы,
пока работает сервер. Повторная отправка, изменение настроек и удаление занятого
диалога блокируются. Вкладки получают обновления автоматически. После ошибки
исходный текст доступен для повторной отправки; успешные промежуточные этапы
сохраняются. Повторная отправка с мета-промптом выполняет оба этапа заново.

### Хранение и запуск

Общие диалоги CLI и веб хранятся в `data/conversations/` — один JSON на диалог, включающий
настройки, полную ленту, контекст стратегии и состояние выполнения. Обновления
атомарны, записи защищены блокировкой между потоками и процессами CLI и веб-сервера.
Каталог исключён из Git. Для резервной копии достаточно скопировать этот каталог.
Файлы `.lock` служебные; они могут оставаться после удаления диалогов.
В этом же каталоге `memory.sqlite3` хранит отдельные таблицы рабочей и
долговременной памяти. В стандартной конфигурации CLI и веб используют одну
историю, рабочую и долговременную память. Рабочая память и выбранный профиль
привязаны к ID диалога, поэтому сохраняются при смене интерфейса.

После перезапуска незавершённые запросы помечаются как прерванные и не
отправляются автоматически повторно. Повреждённые файлы остаются на диске;
интерфейс сообщает о проблеме. Если диск отказывает после получения ответа,
сервер удерживает доступный результат в памяти и сообщает, что сохранение
не подтверждено. Такой результат не переживёт остановку сервера, пока запись
не станет доступна и не выполнится успешное изменение диалога.

```shell
python -m llm_agent.web --port 8081 --no-browser
python -m llm_agent.web --data-dir ./my-chats
python -m llm_agent.web --help
```

По умолчанию сервер слушает только `127.0.0.1`. Это локальное приложение
для одного пользователя; авторизация для публичного размещения не реализована.
На узком экране боковые панели открываются кнопками в заголовке чата.
Потоковая выдача токенов и отмена запроса пока не реализованы. Старые отдельные
CLI-истории (`history.json`, файлы веток) не импортируются; новый CLI работает
только с общим форматом `Conversation`. Ветки/checkpoints доступны только через
низкоуровневый Python API.

### Один диалог в CLI и браузере

Оба интерфейса используют `ConversationService` и один каталог данных. CLI не
требует запущенного веб-сервера: можно закрыть веб и продолжить с того же места.
Кнопка с иконкой терминала «Продолжить в CLI» в заголовке веб-чата показывает
готовую команду с путём к выбранному диалогу; её можно скопировать.

```shell
# Создать диалог и получить его ID и путь
python main.py --new-conversation --user "Меня зовут Мирослав"
# Посмотреть список общих диалогов (JSON)
python main.py --list-conversations
# Продолжить по ID, в том числе после общения в браузере
python main.py --conversation <ID> --user "Как меня зовут?"
# Или выбрать существующий файл по пути
python main.py --conversation data/conversations/<ID>.json --user "Продолжим"
# Полная лента, настройки и контекст в JSON без вызова модели
python main.py --conversation <ID> --show-conversation
# Открыть веб: созданный в CLI диалог появится в списке
python -m llm_agent.web
```

`<ID>` в примерах нужно заменить на реальный ID из вывода CLI или списка
диалогов, без угловых скобок. `--history` — синоним `--conversation`: он открывает
только существующий файл общего формата. Несуществующий путь не создаёт историю.
`--user` без выбора диалога, как и `--new-conversation`, создаёт новый диалог;
следующий запуск без `--conversation` не продолжает предыдущий автоматически.
`--new-conversation` без `--user` создаёт пустой диалог без API-запроса.

По умолчанию каталог `data/conversations` определяется относительно проекта,
а не текущей рабочей директории. Для другого каталога используйте одинаковый
`--data-dir` у CLI и веб. При выборе файла по пути CLI использует его каталог,
включая базы памяти, профилей и MCP. Изменения станут видны в другом интерфейсе
после обновления. Одновременный запрос к одному диалогу отклоняется блокировкой.

### Устройство веб-части

`llm_agent/web/app.py` собирает приложение; `page.py` хранит состояние страницы,
`components.py` отображает сообщения, `jobs.py` запускает фоновые запросы.
Сервис `llm_agent/service.py` управляет диалогами и вызывает существующий `Agent`.
Модели данных и атомарное хранилище находятся в `models.py` и `storage.py`.
Ядро и сервис не импортируют NiceGUI, поэтому CLI и веб используют
их напрямую без HTTP-соединения друг с другом. Полная лента хранится отдельно от сокращаемого контекста, но
успешный этап и соответствующий контекст записываются вместе.

Все проверки без обращений к DeepSeek:

```shell
python -m unittest discover -s tests
```

```text
LLMAgentExample/
├── llm_agent/              # Код приложения

│   ├── __main__.py         # Запуск через python -m llm_agent
│   ├── agent.py            # Agent и запросы к модели

│   ├── task_state.py       # Конечный автомат задачи и проверка действий модели
│   ├── context_strategy.py # Скользящее окно и локальные факты диалога
│   ├── memory.py           # Рабочая и долговременная память, SQLite, снимки контекста

│   ├── mcp_config.py       # Настройки MCP-серверов и SQLite-хранилище
│   ├── mcp_tools.py        # Схемы для LLM, проверка аргументов и выполнение вызовов
```

Команды ниже выполняются из корня проекта. Также доступен запуск
`python -m llm_agent --help`. Импорты Python используют пакет `llm_agent`,
например `from llm_agent.agent import Agent`.

Установите зависимости: `pip install -r requirements.txt`. Создайте рядом с
`main.py` файл `.env` с переменной `API_KEY=ваш_токен`. Значение `API_KEY`, уже
заданное в окружении, имеет приоритет.

```shell
python main.py --user "Объясни принцип работы ИИ-агента"
python main.py --user "Объясни принцип работы ИИ-агента" --meta-prompt
python main.py --help
```

Для скользящего окна укажите стратегию и положительный размер окна:

```shell
python main.py --user "Продолжим" --strategy window --window-size 10
```

`window` хранит только последние N отдельных сообщений пользователя и агента,
а не N пар. Системный промпт сохраняется отдельно и в N не входит.
В запросе к модели текущий пользовательский запрос входит в окно; после ответа
в контексте остаётся не больше N сообщений диалога. Полная лента в `turns`
сохраняется на диске для обоих интерфейсов.
Например, при N=1 модель получает только текущий запрос и системный промпт,
а после ответа в контексте остаётся только ответ и системный промпт.
Это правило действует на обоих этапах `--meta-prompt`.

При применении окна лишние сообщения и прежнее summary удаляются из контекста.
Полная лента диалога сохраняется независимо от стратегии.
Накопленные счётчики расхода токенов сохраняются между запусками.
При удалении сообщений поле `working_context` может хранить объект `messages`, `summary` (пустая
строка для окна) и `archived_usage`, чтобы не терять статистику.

Для нового диалога `--strategy window` и `--strategy facts` требуют `--window-size`.
У существующего диалога размер можно оставить сохранённым. `--window-size`
передаётся вместе с `--strategy window` или `facts`. Без параметров контекста
используются сохранённые настройки диалога; новый диалог использует `full`.
Параметры сжатия совместимы только со стратегией `summary`.
В Python: `Agent(token="ваш_токен", strategy="window", window_size=10)`.

Для локальных фактов диалога **Sticky Facts / Key-Value Memory** используйте:

Это производное представление краткосрочного слоя. Факты не переносятся
автоматически в явную рабочую или долговременную память.

```shell
python main.py --user "Создаём ИИ-агента на Python. Отвечай кратко и по-русски" --strategy facts --window-size 6
python main.py --conversation <ID> --user "Теперь нужны подробные ответы"
```

Для N переиспользуется `--window-size`: это уже существующий жёсткий лимит
числа отдельных сообщений. `--last-messages` остаётся параметром сжатия в summary.
В Python: `Agent(token="ваш_токен", strategy="facts", window_size=6)`.
`facts` также нельзя совмещать с `--last-messages` и `--compress-every`.

После каждого нового сообщения пользователя, перед основным ответом, отдельный
запрос к выбранной модели обновляет словарь `facts`: цели, ограничения,
предпочтения, решения, договорённости, имена и точные значения. Ключи и значения —
непустые строки, например `{"goal": "ИИ-агент на Python", "preferences.language": "русский"}`.
Модель возвращает JSON изменений: строка добавляет или заменяет значение,
`null` удаляет отменённый факт, а `{}` оставляет память без изменений.
Неупомянутые ключи сохраняются автоматически. Для служебного запроса используется
[JSON Output DeepSeek](https://api-docs.deepseek.com/guides/json_mode/);
параметры формата, температуры, stop-последовательностей и лимита ответа основного
запроса на него не распространяются.

Основной запрос содержит системный промпт, отдельный справочный блок `<facts>`
и последние N сообщений диалога. Текущий запрос пользователя входит в N,
системный промпт и facts — нет. После ответа в контексте тоже остаётся не больше
N сообщений диалога. При N=1 запрос содержит facts и текущий user, а после ответа
в контексте остаются facts и ответ; системный промпт сохраняется в обоих случаях.

Поле `working_context` содержит `messages`, `summary` (пустую строку), `facts` и
`archived_usage`. Память сохраняется между запусками; её копия доступна через
`agent.history.facts`. `clear()` сбрасывает факты, сообщения и статистику.
При первом включении `facts` доступные старые сообщения и прежнее summary
передаются на извлечение фактов до сокращения контекста. Сообщения из полной
ленты не возвращаются в контекст автоматически. Для последовательного обновления памяти запускайте диалог
с `--strategy facts` при каждом обращении; другие режимы не обновляют facts.
Переход к `window` удаляет facts вместе с прежним summary.

Обновление facts и его расход токенов сохраняются атомарно до основного запроса.
Если модель вернула некорректный JSON, неверные типы значений или незавершённый
ответ, память и сообщения остаются прежними, основной запрос не отправляется.
При ошибке основного запроса уже обновлённые facts сохраняются, а новая пара
сообщений не добавляется. Установленный системный промпт также остаётся сохранённым.
Расход обновления входит в суммарную статистику диалога; `elapsed` его время не включает.
В режиме `--meta-prompt` память обновляется один раз по исходному сообщению
пользователя, оба этапа получают одинаковые facts. Сгенерированный промпт сам
по себе не считается новым указанием пользователя для обновления памяти.

### Ветки в низкоуровневом Python API

`Agent(strategy="branch")` и `BranchHistoryManager` сохраняют поддержку веток
и checkpoints для отдельных программ. CLI и веб работают с линейными общими
диалогами; флаги веток и checkpoints в CLI отсутствуют. Файл `branches.json`
из следующего примера не является общим диалогом и не открывается в вебе.

Checkpoint хранит неизменяемый снимок контекста, состояния задачи и статистики.
Новая ветка получает независимую копию этого снимка. Профиль и явная память
в snapshot не входят. Расход ветки включает общую предысторию, поэтому суммы
расхода разных веток нельзя складывать без двойного учёта. Изменение файла другим
экземпляром отклоняется; используйте менеджеры последовательно.

В Python управление доступно через менеджер истории:

```python
from llm_agent.agent import Agent
from llm_agent.branch_history import BranchHistoryManager

agent = Agent(token="ваш_токен", history_path="branches.json", strategy="branch")
agent.request("Общая задача")
agent.history.create_checkpoint("start")
agent.history.create_branch("a", from_checkpoint="start")
agent.request("Вариант A")
agent.history.create_branch("b", from_checkpoint="start")
agent.request("Вариант B")
agent.history.switch_branch("a")
agent.request("Продолжим вариант A")

# Управление без API; используйте экземпляры последовательно.
history = BranchHistoryManager("branches.json", branch="b")
print(history.active_branch, history.list_branches(), history.list_checkpoints())
```

Для выбора ветки при создании агента доступен `Agent(..., strategy="branch", branch="a")`.
`clear()` очищает только активную ветку, включая её промпт, память и статистику;
остальные ветки и checkpoints сохраняются.

### Системный промпт и Python API

В общем диалоге системный промпт фиксируется при первой отправке, в том числе
если он пуст. `--system` задаёт его для нового диалога; попытка заменить промпт
начатого диалога отклоняется. Для другой инструкции создайте новый диалог.
В режиме `--meta-prompt` оба этапа сохраняются; если второй завершится ошибкой,
результат первого останется в ленте и контексте. Служебный `META_PROMPT_SYSTEM`
не заменяет системный промпт диалога.

Прямой `Agent` с `HistoryManager` — низкоуровневый API. Он по-прежнему использует
`history_path="history.json"` по умолчанию и отдельный формат списка сообщений
или снимка контекста. Такие файлы не являются диалогами CLI/веб. Для интеграции
с общей лентой используйте `ConversationService` и ID диалога.
В низкоуровневом API файл создаётся при первом сохранении, старые записи без
`usage` поддерживаются, `set_system_prompt()` сохраняет первый непустой промпт,
а `history.clear()` сбрасывает контекст. Одновременная запись нескольких
экземпляров в такую отдельную историю не поддерживается.

Агента можно использовать без консольной обёртки:

```python
from llm_agent.agent import Agent

agent = Agent(token="ваш_токен")
result = agent.request("Объясни SOLID", temperature=0.5)
print(result.content)

meta_result, result = agent.request_with_meta_prompt(
    "Объясни SOLID",
    system="Отвечай кратко и на русском языке",
    max_tokens=1000,
)
print(meta_result.content)
print(result.content)
```

Конструктор принимает токен и необязательный `history_path` (по умолчанию `history.json`).
Сжатие по умолчанию выключено. Для его включения задайте оба именованных параметра,
например `Agent(token="ваш_токен", last_messages=10, compress_every=10)`.
Если один из параметров равен `None` (значение по умолчанию), сжатие не выполняется.
Менеджер доступен как `agent.history`: `get_messages()` возвращает копию сообщений,
`add_message("user", "Текст")` добавляет и сохраняет сообщение, `add_messages([...])`
сохраняет несколько сообщений вместе, а `clear()` очищает память и файл
(в режиме branch — только активную ветку).
`set_system_prompt("Инструкция")` сохраняет системный промпт, только если его ещё нет,
а `get_system_prompt()` возвращает сохранённый текст или `None`.
Оба метода запросов принимают параметры конкретного
запроса: `user`, `model`, `system`, `max_tokens`, `temperature`, `stop_sequences`
и `response_format`. Результат `RequestResult` содержит текст `content`, исходный
ответ API `response` со статистикой токенов и время запроса `elapsed` в секундах.
Поле `dialogue_usage` содержит накопленные `prompt_tokens`, `completion_tokens`,
`total_tokens` и число ответов без статистики `missing_responses` на момент этого ответа.
Текущий итог также доступен через `agent.history.get_usage()`.

После каждого ответа CLI отдельно выводит **контекст запроса: вход по API**,
расход за запрос и **суммарный расход диалога**. Единственный источник счётчиков — поле `usage` API DeepSeek.
Входные токены включают системный промпт и отправленную
историю. Итог диалога — сумма расходов всех запросов, включая повторную передачу
истории, оба этапа мета-промптинга, запросы сжатия и обновления facts, а не размер текста истории в токенах.
Статистика сохраняется между запусками и сбрасывается вместе с `clear()`.
Например, запросы с расходом 100 входных + 30 выходных и 150 входных + 40 выходных
дают итог 320 токенов: повторно отправленный контекст учитывается в каждом запросе.
`completion_tokens` включает токены рассуждений модели, если используется режим
мышления, поэтому это не обязательно число токенов видимого ответа `content`.
Детализация `completion_tokens_details.reasoning_tokens` уже входит в выходной расход,
а `prompt_cache_hit_tokens` — во входной; добавлять их к итогам повторно нельзя.
Текущий формат истории сохраняет только три общих счётчика, поэтому восстановить
долю рассуждений или попаданий в кэш из сохранённой истории нельзя.
При наличии этих полей в текущем ответе CLI показывает их отдельно как части
входа и выхода, без повторного прибавления к расходу.
Описание полей: [DeepSeek API](https://api-docs.deepseek.com/api/create-chat-completion/).
Если API не вернул `usage` или в истории есть старые ответы без него, итог
помечается как неполный с указанием числа таких ответов: неизвестный расход
не подменяется оценкой или нулём. Метаданные статистики не отправляются модели.

Для сравнения входа с лимитом используйте `--context-limit N`. Лимит задаётся
явно: программа не выводит его из имени модели.
CLI покажет процент входа от лимита и остаток; при `--max-tokens` также вычтет
этот резерв ответа. Это арифметическая оценка бюджета, а не гарантия принятия
запроса сервером. Накопленный расход диалога с лимитом не сравнивается.
В новом диалоге по умолчанию контекст не сжимается. Чтобы включить автоматическое сжатие отдельным
запросом к той же модели, явно укажите оба аргумента:

```shell
python main.py --user "Продолжим" --last-messages 6 --compress-every 10
```

`--last-messages N` сохраняет последние N сообщений без изменений при сжатии
(допускается 0). `--compress-every K` запускает сжатие, когда
перед очередным запросом накопилось хотя бы K сообщений сверх этого хвоста
(минимум 1). Если указан только один аргумент, CLI отклоняет команду.
Настройки сохраняются в диалоге и применяются при продолжении в CLI или вебе.
Считаются отдельные сообщения пользователя и агента,
а не пары; системный промпт и summary не учитываются. Текущий пользовательский
запрос добавляется после проверки сжатия. Например, при N=6 и K=10 история
из 16 сообщений превращается в summary первых 10 и последние 6 сообщений.
Между сжатиями несжатая часть растёт; N не является жёстким лимитом каждого запроса.

Модель получает JSON со списком старых сообщений и предыдущим summary,
если оно есть, и возвращает обновлённое summary. Запрос сжатия использует текстовый
формат и собственную инструкцию; параметры формата, stop-последовательностей,
температуры и лимита ответа основного запроса на него не распространяются.
В рабочем запросе summary передаётся отдельным системным сообщением после
исходного системного промпта с указанием трактовать его как справочный контекст,
а не инструкции. В мета-промптинге сжатие проверяется перед каждым этапом,
и оба этапа получают актуальное summary.

После сжатия `working_context` общего диалога хранит объект с полями `messages` (системный промпт и несжатые
сообщения), `summary` и `archived_usage` (расход удалённых сообщений и сжатий,
включая `missing_responses`). В контексте сжатая часть заменяется summary;
полная лента `turns` сохраняется для просмотра в обоих интерфейсах.
Summary и статистика сохраняются атомарно и используются после перезапуска.
После успешного запроса CLI выводит сообщение о сжатии, число заменённых
сообщений и токены по API: `до (вход сжатия) … → после (выход summary) …`.
Это `prompt_tokens` и `completion_tokens` запроса сжатия: вход включает служебную
инструкцию, JSON и предыдущее summary, а выход может включать токены рассуждений.
Эти числа не являются точным размером всей истории до и после сжатия; несжатый
хвост в запрос сжатия не входит. Если статистика отсутствует, CLI сообщает об этом.
Дополнительные API-запросы для подсчёта не выполняются. При использовании агента
из Python уведомления можно получать через аргумент конструктора
`on_compression`: callback принимает `CompressionResult` с полями
`messages_compressed` и `usage` (`TokenUsage` или `None`). По умолчанию callback
отсутствует и сам агент ничего не печатает.
`clear()` сбрасывает их вместе с сообщениями. `get_messages()` возвращает готовый
контекст, включая summary или facts, без статистики.

При ошибке сжатия, пустом или незавершённом ответе исходные сообщения остаются
на месте, основной запрос не отправляется. Если сжатие успешно, но основной
запрос завершился ошибкой, успешно сохранённое summary остаётся. Сжатие может
терять детали и само требует места в контексте модели; эти параметры не гарантируют
соблюдения токенного лимита. Время `elapsed` относится к основному запросу
(или соответствующему этапу мета-промптинга), без времени сжатия.

Метод `request_with_meta_prompt()` возвращает пару результатов: сгенерированный
промпт и итоговый ответ. Первый этап всегда использует текстовый формат, второй —
переданный формат ответа и сохранённый системный промпт диалога. В CLI результаты обоих
этапов выводятся после завершения всего вызова.
