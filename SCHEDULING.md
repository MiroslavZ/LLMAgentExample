# Планировщик и фоновые задачи — день 18

Расписание задаётся в cron или Windows Task Scheduler. Планировщик запускает
обычный CLI агента с сообщением `--user`: модель выбирает MCP-инструменты,
агент сохраняет результаты, а следующий запрос строит по ним сводку.
Все запуски используют один `--conversation` и один `--data-dir`.

Это интерпретация задания с учётом [обсуждения](CHAT.md): 24 сентября преподаватель
уточнил, что cron вызывает агента с MCP, и разрешил локальный запуск.
Собственного планировщика, отдельного GitHub-worker и нового MCP-сервера здесь нет.
Сбор и сводка — обычные пользовательские сообщения. Локальный инструмент
`local_read_observations` даёт модели доступ к сохранённым результатам, даже когда
старые сообщения уже исключены из рабочего контекста.

## Подготовка

Установите зависимости проекта, настройте `API_KEY` в корневом `.env` или
окружении и подключите MCP по [MCP.md](MCP.md). Для сбора подключение должно быть
включено для использования моделью. Настройки MCP хранятся в том же каталоге
данных, поэтому CLI и веб должны получать одинаковый `--data-dir`.
MCP-сервер запускается отдельно и должен быть доступен во время сбора.

Создайте диалог один раз; создание без сообщения не обращается к LLM:

```shell
python -m llm_agent --data-dir /opt/LLMAgentExample/data/conversations --new-conversation
```

Подставьте выведенный ID вместо `CONVERSATION_ID` во всех следующих командах.
Замените примерные пути и `user1/project1`, `user2/project2` реальными значениями.
Сначала проверьте сбор и сводку вручную из корня проекта:

```shell
python -m llm_agent --data-dir /opt/LLMAgentExample/data/conversations --conversation CONVERSATION_ID --batch --user "Используя MCP, получи по 3 последних коммита основных веток репозиториев user1/project1, user2/project2. Нужны только SHA, сообщения и даты, diff не нужен. Укажи, какие репозитории удалось проверить, и все ошибки или ограничения результата."
python -m llm_agent --data-dir /opt/LLMAgentExample/data/conversations --conversation CONVERSATION_ID --batch --user "Сделай сводку только по накопленным данным, не запрашивая свежие данные через внешние MCP. Прочитай сохранённые наблюдения со всеми нужными страницами. Покажи, какие коммиты появились в user1/project1 и user2/project2 после первого успешного наблюдения каждого репозитория. Сопоставляй по репозиторию и SHA, убери повторы. Первое наблюдение считай исходным состоянием. Укажи периоды наблюдений, ошибки и ограничения полноты. Если данных не хватает, явно отметь."
```

Сводку формирует LLM: модель сама выбирает локальное чтение архива или внешние
MCP-инструменты по сообщению пользователя. Для сводки только по архиву укажите
это в промпте. Внешние инструменты остаются доступны; запрет в промпте — инструкция
модели, а не программная блокировка. Каталог подключённых MCP запрашивается
перед выбором инструментов, поэтому серверы должны быть доступны и при запросе
сводки. Доступ к API модели и `API_KEY` также необходимы.
Сохранённую сводку также можно прочитать в полной ленте диалога через веб.

## Хранение и чтение наблюдений

Результаты инструментов сохраняются в `tool_calls` полной ленты JSON диалога
с аргументами, временем и признаком ошибки. Каждый завершённый вызов сохраняется
до следующего обращения к модели. Ошибка генерации итогового ответа не удаляет
уже сохранённые наблюдения. Сжатие, facts и скользящее окно меняют рабочий
контекст, но не удаляют исходные записи из полной ленты.
Отдельного хранилища наблюдений нет. Важно: существующий MCP-адаптер ограничивает
сохраняемый результат 20 000 символов, помечая усечение `truncated=true`.
Отброшенная адаптером часть отсутствует и в JSON диалога; последующее чтение
архива её не восстанавливает.

`local_read_observations` читает внешние вызовы инструментов текущего диалога.
Это локальный инструмент агента, а не запрос к удалённому MCP. Вызовы самого
`local_read_observations` не становятся новыми исходными наблюдениями.
Выборка фиксируется на начало текущего запроса и читается от старых записей
к новым. Фильтры `server_name` и `tool_name` требуют точного совпадения.
`since` включителен, `until` исключителен; они относятся к `run_started_at`
(времени начала хода), а не к дате коммита внутри ответа GitHub.
Даты задаются в ISO 8601 с обязательным часовым поясом и приводятся к UTC,
например `2026-09-27T00:00:00Z`. Для сравнения с началом периода нужны также
предыдущие наблюдения.

Пагинация начинается с `offset=0`; `limit` по умолчанию равен 10, максимум — 20.
Следующую страницу нужно читать с `offset`, равным полученному `next_offset`,
сохраняя фильтры. `next_offset=null` означает конец выборки. `total` — число
записей выборки, а не количество уникальных коммитов. Страница ограничена
60 000 символов и может содержать меньше записей, чем запрошено. Обычно записи
остаются целыми; слишком большая запись заменяется preview с `truncated=true`.
В этом случае полный сохранённый результат можно посмотреть в JSON диалога,
но он по-прежнему ограничен усечением исходного MCP-адаптера.

Ходы со статусом `error`, `partial` или `interrupted`, в которых нет внешних
MCP-вызовов, представлены записями `kind=failed_request`. Они включаются
в пагинацию даже при фильтре `server_name` или `tool_name`: источник сбоя
неизвестен, его нужно выяснять по исходному `request`. Поле `request` ограничено
2000 символов, при обрезании установлен `request_truncated=true`.
Такие записи помогают увидеть пропущенную проверку, но не содержат данных источника.

На один ход действует общий лимит 5 раундов и 10 вызовов инструментов, включая
локальное чтение и MCP. Если весь результат не помещается в лимиты страниц
или вызовов за ход, агент должен явно обозначить неполноту сводки.

Повторный запуск может сохранить те же коммиты ещё раз. Дедупликация по паре
«репозиторий + SHA» и сравнение наблюдений задаются сообщением и выполняются
моделью; отдельной таблицы коммитов и гарантии exactly-once нет.
Первое успешное наблюдение — исходное состояние, а не доказательство появления
всех увиденных коммитов после начала мониторинга. Три последних коммита не
гарантируют полноту: между проверками может появиться больше трёх, а история
ветки может измениться. Ошибка проверки не означает отсутствия новых коммитов.
Ограничения и усечение ответа MCP также ограничивают последующую сводку.

## Пакетный режим

`--batch` требует явные `--conversation` и `--user`; создание диалога выполняется
отдельно. Вместо оформления для терминала stdout содержит один JSON-объект
в одной строке: `conversation_id` и поля сохранённого `Turn`, включая ответ,
статус, ошибку и журнал инструментов. Такой вывод удобно дописывать в JSONL.

Код завершения `0` означает `completed` без ошибки хода и без вызовов с
`is_error`. При `partial`, ошибке хода или ошибочном вызове возвращается `1`,
даже если модель смогла написать частичный ответ. Ранние ошибки, например
неверные аргументы или отсутствующий диалог, выводятся в stderr и дают
ненулевой код; JSON хода в этом случае может отсутствовать.
Успешный код подтверждает только техническое завершение программы. Он не
проверяет содержательную полноту ответа, факт вызова нужного MCP-инструмента
или полноту данных источника.

Записи одного диалога защищены межпроцессной блокировкой. Если предыдущий запуск
ещё работает, следующий может завершиться ошибкой занятости: такую ошибку нужно
проверять в журнале планировщика. При необходимости можно дополнительно
организовать сериализацию через `flock`. Автоматического повтора внутри агента нет.

## Linux: cron

В примере проект расположен в `/opt/LLMAgentExample`, окружение — в `.venv`.
Создайте каталог `/opt/LLMAgentExample/logs` заранее и проверьте права пользователя,
от имени которого работает cron. Запускайте интерпретатор окружения по абсолютному
пути; `cd` нужен для импорта модуля. Не рассчитывайте на окружение интерактивного
терминала: ключи должны быть доступны пользователю cron через `.env` или его
окружение. Установите две строки в пользовательский crontab:

```cron
15 * * * * cd /mnt/c/Users/Miroslav/PycharmProjects/LLMAgentExample && /opt/PycharmProjects/LLMAgentExample/venv/bin/python -m llm_agent --conversation 631c1ffed5a24fb1b73c46899e126090 --batch --user "Используя MCP, получи по 3 последних коммита основных веток репозиториев https://github.com/NixOS/nixpkgs, https://github.com/pytorch/pytorch, https://github.com/llvm/llvm-project. Нужны SHA, сообщения и даты, diff не нужен. Укажи, какие репозитории удалось проверить." >> /mnt/c/Users/Miroslav/PycharmProjects/LLMAgentExample/logs/collect.jsonl 2>> /mnt/c/Users/Miroslav/PycharmProjects/LLMAgentExample/logs/collect.log

30 */2 * * * cd /mnt/c/Users/Miroslav/PycharmProjects/LLMAgentExample && /opt/PycharmProjects/LLMAgentExample/venv/bin/python -m llm_agent --conversation 631c1ffed5a24fb1b73c46899e126090 --batch --user "Сделай сводку по накопленным данным, не запрашивая данные через MCP. Прочитай сохранённые наблюдения. Покажи, какие коммиты появились в репозиториях после первого успешного наблюдения каждого репозитория. Сопоставляй по репозиторию и SHA, убери повторы. Первое наблюдение считай исходным состоянием. Если данных не хватает, явно отметь." >> /mnt/c/Users/Miroslav/PycharmProjects/LLMAgentExample/logs/summary.jsonl 2>> /mnt/c/Users/Miroslav/PycharmProjects/LLMAgentExample/logs/summary.log
```

Сбор запускается каждый час в 15 минут, сводка — каждые 2 часа в 30 минут

JSONL содержит результаты всех запусков, включая частичные; stderr записывается
отдельно. Объём ленты диалога и логов растёт: настройте резервное копирование
данных и ротацию логов. На постоянно работающем сервере cron продолжает запускать
агента без открытого терминала и без веб-интерфейса.

## Windows: Планировщик заданий

Создайте диалог из корня проекта:

```powershell
.\venv\Scripts\python.exe -m llm_agent --data-dir "C:\Users\Miroslav\PycharmProjects\LLMAgentExample\data\conversations" --new-conversation
```

В Планировщике заданий создайте две задачи с действием «Запуск программы»:

- **Программа:** `C:\Users\Miroslav\PycharmProjects\LLMAgentExample\venv\Scripts\python.exe`.
- **Рабочая папка:** `C:\Users\Miroslav\PycharmProjects\LLMAgentExample`.
- **Аргументы сбора:** строка ниже с вашим ID и именами репозиториев.

```text
-m llm_agent --data-dir "C:\Users\Miroslav\PycharmProjects\LLMAgentExample\data\conversations" --conversation CONVERSATION_ID --batch --user "Используя MCP, получи по 3 последних коммита основных веток репозиториев user1/project1, user2/project2. Нужны только SHA, сообщения и даты, diff не нужен. Укажи, какие репозитории удалось проверить, и все ошибки или ограничения результата."
```

Для сбора выберите ежедневный триггер с повторением каждые 30 минут в течение
суток. Для сводки задайте ежедневный запуск в 18:00, те же программу и рабочую
папку, а аргументы замените следующими:

```text
-m llm_agent --data-dir "C:\Users\Miroslav\PycharmProjects\LLMAgentExample\data\conversations" --conversation CONVERSATION_ID --batch --user "Сделай сводку только по накопленным данным, не запрашивая свежие данные через внешние MCP. Прочитай сохранённые наблюдения со всеми нужными страницами. Покажи, какие коммиты появились в user1/project1 и user2/project2 после первого успешного наблюдения каждого репозитория. Сопоставляй по репозиторию и SHA, убери повторы. Первое наблюдение считай исходным состоянием. Укажи периоды наблюдений, ошибки и ограничения полноты. Если данных не хватает, явно отметь."
```

Для каждой задачи выберите запуск независимо от входа пользователя и запрет
параллельного запуска экземпляров этой задачи. Это не исключает пересечения
двух разных задач: при необходимости сдвиньте сводку на 18:10.
Учётная запись задачи должна читать `.env`, запускать Python и записывать каталог
данных. Время задаётся в часовом поясе ОС. Проверьте действие кнопкой «Выполнить»,
код последнего запуска и сохранённый ход в веб-чате с тем же каталогом данных.
При прямом запуске Python Планировщик не сохраняет stdout в файл; результаты
остаются в JSON диалога. Для отдельных stdout/stderr-логов нужен скрипт-обёртка.

Расписание работает, пока компьютер включён и доступны LLM API и нужный MCP.
Пропущенные запуски во время выключения не восстанавливают прошлые данные.
Доставка в мессенджер или почту в эту реализацию не входит: сводка сохраняется
в диалоге и возвращается вызывающему процессу через stdout.
