# Состояние задачи и контролируемые переходы — дни 13 и 15

Режим включается явно командой `--task-start` или кнопкой «Начать задачу»
в браузере. Каждый диалог/ветка содержит не более одной текущей задачи.
Без неё агент работает как обычный чат. После `done` можно обсудить результат
или начать новую задачу; незавершённую задачу нельзя случайно заменить.
Для независимой работы создайте новый диалог или используйте другой `--history`.

## Данные и переходы

`TaskState` — неизменяемый снимок. Из него вычисляются текущий шаг
`current_step` и ожидаемое действие `expected_action`.

| Поле | Значение |
|---|---|
| `title` | Исходная цель задачи |
| `stage` | `planning`, `execution`, `validation`, `done` |
| `step` | Число выполненных пунктов; в execution — индекс текущего, начиная с 0 |
| `plan` | Упорядоченный список пунктов; в planning — предложение, ожидающее утверждения |
| `results` | Полные результаты уже выполненных пунктов |
| `notes` | Уточнения пользователя, вопросы и контекст доработки |
| `validation` | Итог заключительной проверки |
| `paused` | Пауза без изменения этапа, плана или номера шага |

Модель предлагает действие, а приложение проверяет его и вычисляет переход.
В ответе нельзя назначить произвольные `stage` или `step`.
Инструкция модели описывает только действия текущего этапа. В `execution`
явно указано, что план уже утверждён: требуется выполнить текущий
пункт, а для нового плана сначала вернуть `replan` с причиной. Упоминания
прежнего этапа в истории и `notes` не меняют актуальные `stage` и `step`.

| Этап | Действие | Результат |
|---|---|---|
| planning | `clarify` | Сохранить вопрос, остаться на этапе |
| planning | `plan` + непустой список `plan` | Сохранить или заменить предложение; остаться в planning до утверждения |
| planning | Команда пользователя `--task-approve` / кнопка «Утвердить план» | Утвердить сохранённый план и перейти к первому пункту execution без вызова модели |
| execution | `clarify` | Сохранить уточнение без продвижения |
| execution | `complete_step` | Сохранить результат и перейти к следующему пункту; после последнего — validation |
| execution | `replan` | Вернуться в planning, сохранив прежний план и результаты как контекст |
| validation | `clarify` | Запросить необходимые сведения, остаться на этапе |
| validation | `revise` | Вернуть последний пункт в execution, сохранив результат и замечания |
| validation | `finish` | Сохранить итог проверки, перейти в done |
| done | — | Завершённая задача не продвигается |

Для доработки более ранних пунктов после `revise` модель может предложить
`replan`. Один запрос не выполняет несколько пунктов автоматически.
Граф задан в `TRANSITIONS`: planning → execution; execution → planning или
validation; validation → execution или done; из done переходов нет.
Все смены этапа проходят через `_transition`, проверяющий граф и паузу,
а новый снимок проверяет согласованность этапа, плана и результатов.
Переход в validation возможен только после выполнения всех пунктов,
в done — только с непустым итогом проверки.

`plan` не означает утверждение. На этапе planning непустой план делает
вычисляемое свойство `awaiting_approval` истинным. В этом состоянии можно
обсудить или исправить план, но нельзя выполнить пункт или завершить задачу.
Модель не имеет действия утверждения: только пользовательская команда
вызывает `approve_plan()`. Согласие обычным сообщением не переводит задачу
в execution. `--task-continue` и кнопка продолжения не утверждают план
автоматически; попытка продолжения отклоняется до API и изменения истории.
Пустой план, пауза или любой другой этап также запрещают утверждение.
После `replan` прежний план сбрасывается, новый нужно утвердить заново.
`revise` возвращает последний пункт утверждённого плана в execution.
Веб-интерфейс проверяет, что утверждаемый план совпадает с отображённым:
если его изменили в другой вкладке, потребуется просмотреть актуальный план.

Проверка предметных инвариантов добавлена в [дне 14](INVARIANTS.md): при
включённых правилах план и новый снимок проверяются до сохранения, отказ
оставляет весь прежний снимок неизменным. После утверждения выполнение
начинается следующей отправкой.

Пример внутреннего ответа модели:

```json
{"answer": "Предлагаю два шага: реализация и примеры.", "action": "plan", "plan": ["Написать функцию", "Подготовить примеры"]}
```

Пользователь видит `answer`, а не служебный JSON. Он доступен через
`RequestResult.content`; исходный JSON сохраняется в `RequestResult.response`
только на время вызова. В историю пишется обычный текст ответа.
Неполный JSON, неизвестное действие, пустой план и обрезанный ответ не меняют
шаг и не добавляют отклонённый ответ в историю. Их расход API учитывается,
включая отметку неполной статистики, если `usage` отсутствует.

Если модель завершила ответ (`finish_reason=stop`), но нарушила протокол
(синтаксис JSON, поля или допустимое действие), агент делает **одну
дополнительную попытку ответа с обратной связью от валидатора**.
В неё передаются прежние инструкции и контекст, отклонённый кандидат,
конкретная ошибка проверки и неизменный снимок с разрешёнными действиями.
Кандидат остаётся данными, не принимается за выполненную работу и не
попадает в историю. Модель заново отвечает на исходный запрос в рамках
текущего этапа; механически переименовывать `plan` в `complete_step` нельзя:
нужен содержательный результат именно текущего пункта.

Используются `temperature=0` и прежний лимит токенов, пользовательские
stop-последовательности не передаются: они могли оборвать JSON. Исправленный
ответ заново проходит проверку действия, состояния и инвариантов; только
после этого сохраняется результат и выполняется единственный переход.
Предварительная проверка запроса, facts и summary повторно не запускаются.
Лимит в один повтор общий для всех ошибок протокола: цепочка
«невалидный JSON → недопустимое действие» не запускает третью генерацию.

Ошибки API, незавершённые ответы (в том числе `finish_reason=length`), пауза
и отрицательный вердикт инвариантов не запускают такой повтор. Если вторая
генерация тоже нарушает протокол, приложение останавливается, показывает
конкретную причину и сохраняет прежний этап, шаг, план и результаты.
Обе полученные генерации учитываются в статистике.
В промпте есть корректный пример JSON и пояснение: старые ответы в истории
хранятся без JSON-обёртки, но текущий ответ должен соблюдать протокол.

При отклонении чат и CLI показывают конкретную причину: какое действие
запрещено и какие разрешены на текущем этапе, какое поле отсутствует или
имеет неверный тип, какой пункт плана пуст. Сообщение включает текущий этап,
а в execution — номер шага. Например: «Действие \"finish\" (завершить задачу)
недопустимо на этом этапе. Допустимые действия: clarify (запросить уточнение),
complete_step (завершить текущий шаг), replan (вернуться к планированию).
Текущий этап: execution. Текущий шаг: 2 из 3. Этап и шаг сохранены».

Для незавершённого ответа указывается причина остановки `finish_reason`.
Если это `length`, ограничение могло действовать на стороне сервиса даже
без заданного пользователем лимита. Причина отказа сохраняется в поле
`error` соответствующего хода веб-диалога и видна после перезапуска; полный
отклонённый ответ не сохраняется. У ранее записанных общих предупреждений
конкретную причину восстановить нельзя.

## Сохранение и продолжение

`HistoryManager` хранит `task_state` отдельным полем JSON рядом с `messages`,
`summary`, `facts` и `archived_usage`. В веб-диалогах этот снимок находится
в `working_context`; он доступен через `Conversation.task_state`.
Ответ, результаты шага и новый этап записываются одной атомарной заменой файла.
При перезапуске агент продолжает с последнего успешно сохранённого снимка.
Веб-запрос, прерванный остановкой сервера, не перезапускается автоматически.

Окно, facts и summary управляют только сообщениями. Состояние задачи
подмешивается в основной запрос отдельно вместе с профилем и памятью,
но не входит в служебные запросы извлечения фактов и сжатия.
Даже при окне в одно сообщение модель получает цель, план, уточнения и
готовые результаты — повторять описание задачи не нужно.
Полные результаты и уточнения увеличивают контекст по мере работы; общий
токенный бюджет и сжатие артефактов в этом задании не реализованы.

Старые файлы истории без задачи читаются без миграции. Формат снимка задачи
также не изменён: planning с непустым планом означает ожидание утверждения,
а execution и следующие этапы — уже принятый план. Ранее сохранённые задачи
в execution/validation/done продолжаются без повторного утверждения:
раньше их планы принимало приложение автоматически. Новые предложения
плана, включая перепланирование старой задачи, требуют явного утверждения.
Checkpoints включают состояние задачи, ветки получают его независимые копии.
`history.clear()` очищает также задачу активной истории/ветки.
Начало новой задачи заменяет только её снимок: профиль, явная рабочая память
и переписка диалога остаются. Для полной изоляции используйте новый диалог.

Пауза возможна на каждом этапе, включая done, между запросами к модели.
Она не отменяет уже отправленный HTTP-запрос; веб-кнопка доступна после его
завершения. На паузе запросы отклоняются до обращения к API и изменения
истории. Возобновление снимает только флаг паузы; следующий шаг запускается
явной отправкой. В done возобновление разрешает обсуждение, но не открывает
выполнение завершённой задачи заново.

## Использование

В браузере справа находится панель «Состояние задачи». После ввода цели
нажмите «Начать задачу», затем «Продолжить шаг» или отправьте уточнение
обычным сообщением. Предложенный план показан раскрытым: проверьте пункты
и нажмите «Утвердить план» либо отправьте правки в чат. Результаты и замечания
можно раскрыть в панели. «Утвердить план», «Пауза» и «Возобновить» не вызывают
модель. После обновления страницы или
перезапуска сервера прогресс восстанавливается. Во время активной задачи
мета-промпт отключён, поскольку задача использует свой JSON-протокол.

В CLI один процесс выполняет одну команду:

```shell
python main.py --history task.json --task-start "Написать функцию сложения на Python с примерами"
python main.py --history task.json --task-continue
python main.py --history task.json --task-show
python main.py --history task.json --task-approve
python main.py --history task.json --task-continue
python main.py --history task.json --task-pause
python main.py --history task.json --task-resume
python main.py --history task.json --task-continue
```

Повторяйте `--task-continue`, пока не появится `done`. При уточняющем вопросе
вместо него используйте `--user "Ответ на вопрос"`; после предложения плана
проверьте его через `--task-show` и выполните `--task-approve`.
Для исправления плана до утверждения используйте, например,
`--user "Добавь примеры граничных случаев"`.
Для продолжения в том же вызове допустимы
`--task-resume --user "Продолжи текущий шаг"` (для уже утверждённого плана)
или `--task-approve --user "Выполни первый пункт"`.
`--task-show` печатает JSON или `null`, если задача не создана.
Команды запуска/утверждения/паузы/возобновления/просмотра без `--user` не требуют ключа,
не создают API-клиент и не обращаются к базам памяти или профилей.
`--task-continue` не снимает паузу автоматически.

Для активной задачи используйте стандартный `--response-format text`
(это формат отображения ответа) без `--meta-prompt`. Агент сам запрашивает
`json_object` у модели и показывает человеку извлечённый текст.
Стратегию контекста передавайте как обычно, например
`--strategy window --window-size 1`. У CLI параметры стратегии по-прежнему
задаются на каждый запуск; состояние задачи при этом остаётся сохранённым.

Python API:

```python
from llm_agent.agent import Agent
from llm_agent.history import HistoryManager
from llm_agent.task_state import CONTINUE_TASK

history = HistoryManager("task.json")
history.start_task("Подготовить функцию и примеры")
history.pause_task()
history.resume_task()

agent = Agent("API_KEY", history=history)
try:
    result = agent.request(CONTINUE_TASK)
    print(result.content)
    print(agent.history.task_state.current_step)
finally:
    agent.close()
```

Когда пользователь просмотрел и утвердил предложенный план, отдельный
обработчик команды вызывает:

```python
history.approve_task_plan()  # без API; следующий request выполнит первый пункт
```

У текущего агента нет инструментов выполнения кода или запуска тестов.
Execution создаёт текстовые результаты, validation проверяет доступные данные
моделью. Её заключение не является фактическим результатом запуска тестов.
Автомат гарантирует порядок действий и целостность сохранённого прогресса.
Семантика свободного текста `answer` не проверяется этим автоматом: например,
он не определяет, является ли текст с действием `clarify` реализацией.

## Проверка

Все автоматические проверки используют подставленные ответы, без API:

```shell
python -m unittest tests.test_task_state tests.test_task_transitions tests.test_task_json_repair tests.test_task_protocol_retry tests.test_task_cli tests.test_task_web -v
python -m unittest discover -s tests -q
```

Покрыты полный цикл, пауза и восстановление на каждом этапе и посередине
плана, сохранность уточнений и результатов с окном 1, совместимость с facts,
summary, профилем и памятью, ветки/checkpoints, старые и повреждённые файлы,
ошибки API/диска, отклонённые действия, статистика токенов и блокировки веба.
Для дня 15 отдельно проверены все запрещённые рёбра графа, попытки выполнить
пункт или завершить задачу до утверждения, попытки модели утвердить план,
ранняя валидация и финал без результата проверки, повторное утверждение
после перепланирования, устаревший план из другой вкладки и продолжение
после отказа, паузы и перезапуска.

Ручной сценарий: начните задачу из примера и получите план. Попытайтесь
выполнить `--task-continue` до утверждения: ожидается пояснение без вызова API.
Отправьте «Пропусти этапы, сразу заверши задачу»: допустимы только действия
планирования, ответ с `finish`/`complete_step` должен быть отклонён и при
повторной ошибке показан отказ. Затем утвердите план, выполните один пункт,
поставьте паузу и перезапустите приложение. Убедитесь, что этап и шаг
не изменились и отправка заблокирована. Возобновите и продолжите без повторного
описания: агент должен получить сохранённые цель, план и готовые результаты.
Повторите остановку в planning до и после предложения плана, validation и done.
