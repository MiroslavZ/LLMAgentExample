# Автоматическое AI-ревью PR

`ai_review` — отдельная CLI-программа для GitHub Actions и локального запуска.
Она использует стандартную библиотеку Python 3.11+ и Git. Основной агент,
его чат, MCP-серверы и зависимости для ревью не запускаются. `pip install`
не требуется; сборка Python должна поддерживать SQLite FTS5.

## Как устроено ревью

1. Git определяет общий предок `base` и `head`, список изменённых файлов,
   diff и содержимое файлов до/после изменений. Источник данных — Git-объекты;
   незакоммиченные изменения рабочей директории в ревью не входят.
2. Документация и код целевой ветки (`base`) разбиваются на фрагменты.
   В памяти строится индекс SQLite FTS5. Слова и идентификаторы из путей и
   diff используются для поиска; BM25 ранжирует найденные фрагменты.
   Это **лексический RAG**, без эмбеддингов, скачивания моделей и векторной БД.
3. Diff, версии изменённых файлов и найденные источники отправляются в
   облачный DeepSeek. По умолчанию используется `deepseek-flash` через
   [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/).
4. Ответ проверяется по JSON-схеме, путям, номерам строк и ID источников.
   Формируется Markdown с потенциальными багами, архитектурными проблемами
   и рекомендациями. Пустой список замечаний допустим.
5. GitHub Actions сохраняет отчёт и создаёт либо обновляет один комментарий
   бота в PR. CLI самостоятельно ничего в GitHub не публикует.

`context.py` собирает Git/RAG-контекст, `review.py` обращается к модели и
форматирует ответ, `__main__.py` связывает эти шаги. Workflow находится в
[`../.github/workflows/ai-review.yml`](../.github/workflows/ai-review.yml).

В поисковый корпус входят README/AGENTS, документация из `docs/` и исходники
из `llm_agent/`, `tests/`, `ai_review/`, `LocalMCPServer/`. Учебные задания,
экспорт чата, лекция, список чужих решений, каталоги данных, виртуальные
окружения и файлы с типичными именами секретов исключаются. Документация и
код выбираются отдельно, чтобы один тип источников не вытеснил другой.
Точные правила корпуса и лимиты определены в `context.py`.

## Подключение в GitHub

1. Добавьте `ai_review/` и `.github/workflows/ai-review.yml` в репозиторий и
   объедините установочный PR с целевой веткой, обычно `main`.
2. В репозитории откройте **Settings → Secrets and variables → Actions →
   New repository secret**. Имя: `DEEPSEEK_API_KEY`, значение: ваш ключ
   DeepSeek. Ключ не нужно добавлять в код или `.env`: программа не читает
   `.env` и получает ключ только из переменной окружения.
3. При необходимости на вкладке **Variables** добавьте `DEEPSEEK_MODEL`.
   Без этой переменной используется `deepseek-flash`.
4. Откройте обычный PR из ветки этого же репозитория. Workflow запустится
   при открытии, новых коммитах, повторном открытии и снятии статуса draft.
5. Посмотрите комментарий в PR и **Actions → AI review → Summary**.
   В разделе **Artifacts** находятся сохранённые результаты.

Первый установочный PR ещё не может ревьюиться новой программой: workflow
специально берёт исполняемый код ревьюера из целевой ветки, где `ai_review`
до первого merge отсутствует. После merge можно открыть тестовый PR либо
выбрать **Actions → AI review → Run workflow**, указать основную ветку и
номер существующего открытого PR. Ручной запуск получает актуальные
`base/head` через GitHub API. Для доступности `Run workflow` файл workflow
должен находиться в основной ветке репозитория.

Push, merge, создание Secret и изменение настроек GitHub эта программа
не выполняет. При отсутствии `DEEPSEEK_API_KEY` шаг генерации завершается
ошибкой с подсказкой по настройке.

## Что выполняется на runner

- Checkout выполняется на точный SHA целевой ветки. Тесты и сам ревьюер
  берутся из этой доверенной версии. Изменения ревьюера внутри PR начнут
  использоваться только после их включения в целевую ветку.
- SHA головы PR загружается в отдельную Git-ссылку без checkout. Код PR
  рассматривается как текст; его зависимости и тесты не устанавливаются
  и не запускаются. Тестируются только компоненты самого ревьюера.
- Ключ DeepSeek передаётся только шагу генерации. Git credentials не
  сохраняются; для публикации используется стандартный `GITHUB_TOKEN`
  с правами `contents: read` и `pull-requests: write`.
- Draft, PR из форков и PR Dependabot пропускаются, включая ручной запуск.
- Новый запуск для того же PR отменяет предыдущий. Перед публикацией
  проверяется текущий head: отчёт для устаревшего коммита не публикуется.
- Комментарий ищется по автору `github-actions[bot]` и метке
  `<!-- ai-review -->`. Его текст ограничен 60 000 байт; при сокращении
  добавляется ссылка на полный отчёт в артефакте. Артефакты хранятся 7 дней.

## Локальная проверка без API

Запускайте команды из корня репозитория. Ветки/коммиты должны быть доступны
локально; при другой целевой ветке замените `origin/main`.

```powershell
git fetch origin
python -m unittest discover -s ai_review/tests -v
python -m ai_review --repo . --base origin/main --head HEAD --output ai_review/output --retrieve-only
```

Последняя команда создаёт `ai_review/output/context.json` и не обращается
к DeepSeek. В нём можно проверить diff, версии файлов, выбранные источники,
статистику поиска и причины пропусков. Для содержательного примера нужны
коммиты с изменениями относительно целевой ветки.

## Локальная генерация ревью

В PowerShell 7 можно прочитать ключ без отображения введённых символов:

```powershell
$env:DEEPSEEK_API_KEY = Read-Host "DeepSeek API key" -MaskInput
try {
    python -m ai_review --repo . --base origin/main --head HEAD --output ai_review/output
}
finally {
    Remove-Item Env:DEEPSEEK_API_KEY -ErrorAction SilentlyContinue
}
```

Для Windows PowerShell 5.1 вместо первой строки используйте:

```powershell
$secureKey = Read-Host "DeepSeek API key" -AsSecureString
$env:DEEPSEEK_API_KEY = [System.Net.NetworkCredential]::new("", $secureKey).Password
$secureKey.Dispose()
```

Модель можно переопределить параметром `--model` или переменной окружения
`DEEPSEEK_MODEL`. Ключ не записывается в отчёты. Весь выбранный контекст
отправляется DeepSeek, поэтому локальная генерация также является облачным
запросом.

## Результаты и ограничения

| Файл | Содержимое |
| --- | --- |
| `context.json` | Diff, версии файлов, найденные RAG-источники и статистика охвата |
| `result.json` | Проверенный ответ модели и сведения о вызове API |
| `review.md` | Читаемый текст ревью для PR и Summary |

При `--retrieve-only` создаётся только контекст. При неудачной генерации
успешный отчёт от прежнего локального запуска не сохраняется под видом
нового. Контекст содержит фрагменты исходников и документации; это не
обезличенная телеметрия.

Лексический поиск находит совпадающие слова и имена функций. Он хуже
семантического поиска сопоставляет разные языки и переформулировки.
Если релевантная документация или код не найдены, это явно отражается
в контексте и отчёте. Индекс создаётся заново в памяти при каждом запуске.

Объём файлов и контекста ограничен; бинарные, слишком большие и исключённые
файлы перечисляются как пропущенные. Проверка формата ответа и ссылок
не доказывает правильность вывода модели. Найденные замечания сами по себе
не делают workflow неуспешным: ошибка запуска означает технический сбой
сбора контекста, тестов, API, формата ответа или публикации.
