# План реализации дня 21: индексация документов

Дата подготовки: 30 сентября 2026 года.

Это самостоятельное задание для агента Codex в новом диалоге. Документ описывает рекомендуемую реализацию в проекте LLMAgentExample. Сам индексатор на этапе подготовки этого плана не реализован. Названия модулей, параметры и команды ниже — проектные предложения, а не уже существующие возможности.

## 1. Цель и границы работы

Реализовать отдельный локальный индексатор документов на Python внутри текущего проекта. Он должен прочитать выбранные документы, разбить их двумя способами, получить семантические эмбеддинги и сохранить два индекса с текстами и метаданными. Затем нужно сравнить стратегии и объяснить результаты.

Основной сценарий:

```text
Документы → загрузка текста → чанки → embedding-модель → SQLite
                                 ↑
                  fixed или structural

Контрольный вопрос → та же embedding-модель → поиск в сохранённом индексе
                                              ↓
                                  чанки, источники, оценки сходства
```

Индексирование — подготовительный процесс, который запускается отдельно. Перестраивать индекс при каждом вопросе пользователя не требуется. При поиске вычисляется только вектор вопроса, а векторы документов загружаются из сохранённого индекса.

**Требования задания:** корпус размером минимум 20–30 страниц текста или эквивалент в коде, chunking, эмбеддинги, сохранённый локальный индекс. В этой реализации также выполнить усиление: метаданные каждого чанка и сравнение фиксированного и структурного разбиения.

Ответ преподавателя: "Пока нужно сделать разбиение на чанки"

**Оставить на следующие задания:** подключение найденного контекста к `Agent`/`ConversationService`, ответы LLM с RAG и без RAG, веб-интерфейс поиска, reranker, query rewriting, пороги отказа, генерация цитат в ответах и память RAG-чата. День 21 не требует менять текущий сценарий общения с агентом.

Основание для границ работы: [TASKS.md](TASKS.md), особенно дни 21–25. [CHAT.md](CHAT.md) использовать как пояснения к формулировкам, а не как основание исключать эмбеддинги и сохранение индекса из результата дня 21.

Перед реализацией прочитать применимые `AGENTS.md`, этот документ и релевантные части проекта. Проверить актуальные зависимости и состояние рабочего дерева: план не заменяет изучение кода.

Начать с документации этого репозитория. Она уже доступна, соответствует предметной области агента и позволяет проверить результат без PDF-парсеров, OCR и загрузки чужого кода.

Такая оценка — способ показать масштаб, а не установленная организатором формула. Во время реализации заново измерить объём и указать способ подсчёта в отчёте.

Правила загрузки:

- Для первой версии достаточно UTF-8 Markdown и TXT. Поддержка всех перечисленных в задании форматов одновременно не требуется.
- Сохранять относительный путь от корня проекта как `source`; одних имён файлов недостаточно из-за возможных совпадений.
- Нормализовать переводы строк в `\n`. Не удалять содержимое таблиц, ссылок и блоков кода и не схлопывать весь текст в одну строку.
- Считать символы, слова, строки, хеш каждого нормализованного документа и общий хеш корпуса. Подсчёт слов определить явно, например разделением по пробельным символам.
- Обе стратегии запускать на одном и том же снимке загруженных документов.
- Не включать в корпус этот план, контрольные вопросы и отчёт сравнения. Они содержат служебные сведения и могут исказить оценку поиска.

Если в процессе реализации меняется README, итоговые индексы и отчёт строить уже после этих изменений, чтобы их хеши соответствовали финальному корпусу.

## 4. Предлагаемый стек и устройство

| Область | Начальный выбор | Причина |
| --- | --- | --- |
| Интерфейс | Отдельный CLI `python -m llm_agent.indexing` | Можно строить и проверять индекс независимо от чата |
| Корпус | Markdown/TXT из явного списка | Достаточно для задания и легко проверить извлечение текста |
| Эмбеддинги | `intfloat/multilingual-e5-small` через SentenceTransformers | Подходит для русских и английских текстов, может работать локально |
| Хранение | Два SQLite-файла | Просто просматривать, связывать тексты с векторами и сохранять настройки |
| Поиск | Точное сравнение нормализованных векторов | Для нескольких сотен чанков отдельный поисковый сервер не нужен |
| Тесты | `unittest`, временные каталоги и тестовые векторы | Соответствует проекту, не требует сети в обычных тестах |

Первичная загрузка модели требует доступа к сети и места на диске; после загрузки вычисления можно выполнять локально на CPU. Зафиксировать использованную модель, доступную ревизию и версии библиотек. Не устанавливать зависимости глобально: использовать окружение проекта и документировать установку.

У модели E5 small размерность 384 и ограничение входа 512 токенами модели. Для документов используется префикс `passage: `, для запросов — `query: `, в том числе для русского текста. Проверить эти параметры по конфигурации установленной модели. Официальное описание: [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small).

Число токенов считать токенизатором embedding-модели. Токенизатор чата из `tiktoken`, количество символов и количество слов не являются взаимозаменяемыми величинами.

Примерное размещение кода:

```text
llm_agent/indexing/
    __init__.py
    __main__.py       # CLI
    models.py         # Document, Chunk, SearchResult и настройки
    loaders.py        # загрузка корпуса и нормализация
    chunking.py       # fixed и structural
    embeddings.py     # адаптер модели и ограничения входа
    store.py          # SQLite, чтение индекса и поиск
    pipeline.py       # построение индекса
    evaluation.py     # статистика и сравнение
examples/indexing/
    corpus.json
    questions.json
data/indexes/
    fixed.sqlite3
    structural.sqlite3
reports/day21/
    comparison.json
INDEXING.md
```

Это ориентир для разделения ответственности. Можно объединить небольшие модули, если отдельные файлы не дают пользы. Не создавать универсальный framework провайдеров, систему плагинов или сервисный слой ради одного индексатора. Достаточно простого заменяемого адаптера эмбеддингов, чтобы обычные тесты не загружали модель.

## 5. Две стратегии chunking

### Fixed: окно фиксированного размера

Начальные параметры: до **350 токенов текста** в чанке и **50 токенов перекрытия** соседних окон. Это отправная точка, которую допустимо изменить с объяснением в отчёте.

Алгоритм проходит каждый документ последовательно, создаёт окна заданного размера и сдвигается с учётом overlap. Между разными файлами чанки не объединяются. Последний фрагмент может быть короче.

Для токенового разбиения использовать доступные символьные смещения токенизатора или другой способ, сохраняющий исходные подстроки без потери символов. Простое разрезание token IDs и обратное декодирование нужно проверить на Unicode: оно не должно повреждать русские буквы и менять исходный текст.

Fixed не должен выбирать границы по заголовкам. При этом метаданные раздела можно определять по позиции чанка в документе; если окно пересекает несколько разделов, явно отражать это, например отдельным списком `sections` при основном `section` по началу окна.

### Structural: Markdown-разделы и абзацы

Разбирать иерархию Markdown-заголовков и сохранять путь раздела, например `Модель памяти > Долговременная память`.

Правила:

1. Заголовки внутри fenced code blocks не считать заголовками документа. В README проекта такие строки действительно встречаются.
2. В пределах раздела собирать последовательные абзацы до того же целевого бюджета — 350 токенов текста.
3. По возможности сохранять заголовок вместе с его содержимым; не производить множество чанков только из коротких заголовков.
4. Между самостоятельными разделами границы не стирать. Очень длинный раздел, абзац или блок кода разбивать с ограничением размера; допустим fallback на fixed с overlap 50.
5. Документ без заголовков разбирать по абзацам, а слишком длинные фрагменты — через тот же fallback.
6. Содержательный текст до первого заголовка тоже индексировать. Пустой документ не должен создавать пустой вектор.

Не обязательно реализовывать весь стандарт Markdown вручную. Выбрать небольшой парсер либо явно документированный поддерживаемый набор синтаксиса; проверить его на реальном корпусе. Короткие разделы допустимы: их количество и влияние на поиск показать в сравнении.

### Общие требования

- Хранить исходный текст чанка, а служебный префикс E5 добавлять только при обращении к модели.
- Проверять длину **полного входа модели**, включая префикс и специальные токены. Не полагаться на незаметное обрезание длинного текста библиотекой.
- Сохранять символьные смещения относительно нормализованного снимка документа. Их нельзя выдавать за байтовые смещения исходного файла.
- Отсутствие overlap на обычных границах структурных разделов допустимо; описать фактическую политику. Если в длинных разделах есть overlap, учитывать его в статистике.
- Не терять содержательный текст на границах. Проверить покрытие по смещениям и отдельно объяснить обработку пробельных краёв.
- Сделать `chunk_id` детерминированным для одинакового корпуса и параметров. В идентификатор должны влиять источник, версия содержимого, стратегия и позиция чанка; одного номера `chunk_1` недостаточно.

Структурная стратегия не обязана победить. Цель — получить корректные реализации, измерить различия и объяснить наблюдения.

## 6. Эмбеддинги и локальный индекс

Модель загрузить один раз на запуск, обрабатывать чанки батчами и показывать понятный прогресс. Не делать отдельную загрузку модели на каждый фрагмент.

Векторы L2-нормализовать: длина вектора становится равной единице. Это не преобразование всех координат в диапазон `[0, 1]`. Для нормализованных векторов скалярное произведение соответствует cosine similarity.

Каждый индекс должен хранить как минимум:

| Данные | Поля или эквивалент |
| --- | --- |
| Документ | `source`, `title`, хеш, нормализованный текст снимка |
| Чанк | `chunk_id`, ссылка на документ, `section`, `strategy`, `text`, `token_count`, порядок, символьные смещения |
| Вектор | связь с `chunk_id`, значения, размерность |
| Настройки сборки | версия схемы, модель и ревизия, нормализация, префиксы, параметры chunking, хеш корпуса, время сборки |

`title` брать из подходящего заголовка, иначе из имени файла. Для текста вне разделов использовать явное согласованное значение `section`.

Достаточно SQLite с обычными таблицами и векторами `float32` в BLOB; документировать формат и порядок байтов. JSON-массивы тоже допустимы, если это заметно упрощает реализацию. FAISS и специальные SQLite-расширения для выбранного объёма не обязательны.

При сохранении и чтении проверять количество векторов, размерность, конечность чисел, ненулевую норму и связь с правильными чанками. Не сопоставлять строки и векторы по случайному порядку выдачи SQL без `ORDER BY`.

Полной пересборки достаточно. Новую базу собирать во временный файл и заменять существующую только после успешной записи и проверок. Ошибка модели или прерывание сборки не должны разрушать предыдущий рабочий индекс. Сравнение двух файлов разрешать только при совместимых настройках и одинаковом хеше корпуса.

Добавить точечные правила `.gitignore` для сгенерированных индексов и локального кеша, если он хранится внутри проекта. Корпус, конфигурация, вопросы и текстовый отчёт должны оставаться доступными для воспроизведения. Игнорирование индексов в Git не отменяет требования реально создать их локально.

## 7. CLI и проверочный поиск

Ниже желаемые сценарии; точный синтаксис допустимо упростить и затем зафиксировать в `INDEXING.md`:

```powershell
# Объём и состав выбранного корпуса
python -m llm_agent.indexing corpus

# Построение обоих индексов
python -m llm_agent.indexing build --strategy all

# Размеры, количество чанков и настройки сохранённых индексов
python -m llm_agent.indexing stats --strategy all

# Просмотр реального текста и метаданных нескольких чанков
python -m llm_agent.indexing inspect --strategy structural --limit 3

# Проверки целостности сохранённых данных
python -m llm_agent.indexing verify --strategy all

# Поиск без обращения к чат-модели
python -m llm_agent.indexing search "Как продолжить один диалог в CLI и браузере?" --strategy structural --top-k 5

# Сравнение на одном наборе вопросов
python -m llm_agent.indexing compare --questions examples/indexing/questions.json --top-k 5
```

`stats`, `inspect` и базовый `verify` должны работать с сохранёнными данными без загрузки модели и без ключа DeepSeek. Индекс должен открываться в новом процессе после завершения сборки.

Поиск загружает настройки модели из индекса, строит вектор вопроса с `query: ` и возвращает top-k: score, `source`, `section`, `chunk_id`, текст. Не использовать другую модель с такой же размерностью: одинаковая размерность не делает векторные пространства совместимыми.

На данном этапе score — оценка сходства, а не вероятность правильного ответа. Универсальный порог «релевантно/нерелевантно» не вводить без отдельной оценки. Для слишком длинного запроса задавать понятное поведение, например ошибку с указанием лимита, вместо скрытого обрезания.

## 8. Как сравнить стратегии

### Статистика разбиения

Для каждого индекса показать:

- число документов и чанков;
- минимальный, медианный, средний, p95 и максимальный размер чанка в токенах;
- суммарное количество токенов, переданных модели, включая повторения из-за overlap;
- количество очень коротких чанков с явно заданным порогом;
- покрытие исходного текста и объём повторений;
- время chunking и получения эмбеддингов, размер базы на диске.

Для времени отдельно указывать загрузку/скачивание модели и непосредственно обработку корпуса. Не сравнивать холодный запуск одной стратегии с прогретым запуском другой без этого пояснения.

Показать несколько пар чанков из одинаковых мест документа: где fixed разрывает объяснение, где structural сохраняет раздел, а где структурная стратегия создаёт неудобный короткий фрагмент. Если конкретного недостатка в корпусе нет, не придумывать пример.

### Проверка поиска

Подготовить 10 осмысленных вопросов по фактическому содержимому корпуса: память, продолжение диалога, MCP, оркестрация, планировщик, инварианты, состояние задачи и персонализация. Вопросы писать своими словами, не копировать все заголовки дословно.

Для каждого вопроса до оценки результатов сохранить:

- текст вопроса;
- краткое ожидание: какая информация нужна;
- допустимые источники и разделы;
- один или несколько коротких точных эталонных отрывков, содержащих нужную информацию.

Сам список тем выше не является готовой разметкой: найти и проверить конкретные отрывки в текущих документах. Если эталон перестал находиться в корпусе, оценка должна сообщать об устаревшей разметке.

Не считать любой чанк из правильного файла релевантным: большой README содержит много несвязанных ответов. Для простой автоматической проверки использовать совпадение источника и наличие короткого эталонного отрывка внутри текста чанка, с явно описанной нормализацией пробелов. Если вопрос требует нескольких фрагментов, отдельно отметить ограничение такой проверки и вручную разобрать выдачу. Не подбирать эталоны после просмотра результатов, чтобы улучшить метрики.

Метрики для обеих стратегий при одинаковом `top-k = 5`:

- **Hit@1:** доля вопросов, у которых первый чанк релевантен.
- **Hit@5:** доля вопросов, у которых среди первых пяти есть релевантный чанк.
- **MRR@5:** среднее значение `1 / позиция первого релевантного чанка`; если его нет в первых пяти — 0.

Дополнительно сохранить результаты по каждому вопросу и разобрать 2–3 показательных случая. Совпадение только по файлу можно вывести как вспомогательный показатель с соответствующим названием, но не выдавать за нахождение ответа.

Модель, корпус, нормализация и вопросы должны быть одинаковыми. Поскольку structural сохраняет естественные границы, размеры чанков и overlap будут различаться; это ограничение эксперимента явно описать. Десять вопросов дают учебное сравнение, а не универсальный рейтинг стратегий.

Результаты сохранить в `reports/day21/comparison.json`, а понятные человеку таблицу, примеры и выводы — в `INDEXING.md`. Все цифры должны происходить из реального запуска. Вывод может быть смешанным: одна стратегия лучше ищет, другая создаёт меньше чанков или требует меньше вычислений.

## 9. Последовательность реализации

1. **Изучить проект и зафиксировать корпус.** Проверить зависимости, объём и формат файлов, создать явный список источников. Выбрать совместимые версии библиотек.
2. **Реализовать загрузку и chunking.** Сначала проверить тексты, смещения, метаданные и обе стратегии без загрузки embedding-модели.
3. **Добавить модель и ограничения входа.** Префиксы E5, токенизатор модели, batch encoding, L2-нормализация, проверка фактических размеров.
4. **Реализовать SQLite и построение индекса.** Настройки сборки, снимки документов, тексты, метаданные, векторы, безопасная замена файла.
5. **Добавить CLI для просмотра и поиска.** Убедиться, что индекс повторно открывается и используется независимо от чата.
6. **Подготовить контрольные вопросы и сравнение.** Проверить эталоны по источникам и реализовать прозрачные метрики.
7. **Выполнить проверки и реальные сборки.** Построить оба индекса выбранной моделью, получить фактические результаты, изучить выдачу.
8. **Завершить документацию.** Инструкции установки и запуска, описание решений, таблица сравнения, ограничения, перечень полученных файлов. При изменении корпуса повторить итоговую сборку и сравнение.

Не требуется останавливать работу после составления ещё одного плана: агенту в новом диалоге поручается реализация и проверка до готового результата. Рутинные детали выбирать самостоятельно в рамках этого документа; существенные изменения корпуса, стека или объёма объяснять пользователю.

## 10. Проверки

Обычные автоматические тесты должны выполняться без сети и без скачивания весов. Для них допустимы небольшие детерминированные тестовые векторы и подставной адаптер модели. Они проверяют инфраструктуру, но не заменяют итоговый запуск настоящих семантических эмбеддингов.

Проверить основные риски:

- Fixed: размер окна, overlap, последний фрагмент, пустой и короткий документы, русские символы, покрытие текста без потерь.
- Structural: вложенные заголовки, текст до первого заголовка, документ без заголовков, `#` внутри code fences, длинный раздел и длинный блок кода.
- Метаданные: правильный источник и раздел, стабильные ID, отсутствие коллизий между файлами с одинаковыми именами.
- Хранилище: запись и чтение в новом экземпляре, точное соответствие чанков и векторов, некорректная размерность, NaN/Inf, сохранность старого индекса при ошибке пересборки.
- Поиск: известный порядок результатов на простых векторах, top-k больше числа чанков, пустой индекс, несовместимые настройки.
- Оценка: правильные Hit/MRR на искусственной выдаче, отсутствие попаданий, неверный фрагмент правильного файла, устаревший эталон.

Запустить новые целевые тесты, затем существующий набор проекта:

```powershell
python -m unittest discover -s tests -v
```

Проверку токенизатора выбранной модели и реальных эмбеддингов провести отдельным интеграционным запуском. Дополнительно вручную просмотреть несколько чанков и выдачу на контрольных вопросах.

Если окружение не позволяет скачать/запустить модель, точно сообщить о препятствии и готовности остальных частей. Не заменять семантические эмбеддинги хешами слов или случайными числами без явного изменения задачи и не объявлять локальные индексы готовыми на основании одних mock-тестов.
