# День 23. Фильтрация, query rewrite и сравнение режимов RAG

План подготовлен 3 октября 2026 года по условию задания, материалам проекта и
решениям из `SOLUTIONS.md`. Это план будущей реализации: код приложения и индекс
в рамках подготовки плана не изменялись, эксперименты с моделями не запускались.

## 1. Что требуется от задания

В день 22 агент передавал модели несколько ближайших к вопросу фрагментов базы.
Но «ближайший среди имеющихся» не означает «содержит ответ»: поиск вернёт top-K
даже для вопроса, на который в базе вообще нет информации.

День 23 добавляет две операции:

1. **Query rewrite перед поиском.** Превратить вопрос пользователя в удобный для
   поиска запрос, сохранив его смысл. Модель, которая отвечает пользователю,
   по-прежнему получает исходный вопрос.
2. **Проверку кандидатов после поиска.** Отсечь слабые фрагменты по порогу и/или
   оценить их другим способом, изменить порядок и выбрать лучшие.

Пример возможного rewrite: «Если попрошу запомнить, оно останется навсегда?» →
«Сохраняет ли просьба запомнить сведения в постоянную память агента?». Это пример
формулировки, а не доказательство улучшения поиска на текущем индексе. Нельзя
дописывать в поисковый запрос предполагаемый ответ.

**Фильтр** решает, какие фрагменты оставить. **Реранкер** заново оценивает
кандидатов и меняет их порядок. Cross-encoder — один из вариантов реранкера:
он совместно читает вопрос и текст фрагмента и оценивает их соответствие.
Фильтр по уже вычисленному cosine score тоже выполняет условие задания:
в нём явно написано «reranker или фильтр».

В строке результата отдельно указан query rewrite. Поэтому одного порога,
без переписывания запроса и сравнения режимов, недостаточно для полного результата.
В `CHAT.md` нет дополнительных разъяснений, отменяющих это требование:
обсуждение в основном относится к дням 21–22.

## 2. Что уже есть в этом проекте

Текущее состояние реализации дня 22 — коммит `79188ed`.

- `llm_agent/agent.py`: найденные тексты добавляются в запрос как справочные

- `examples/indexing/questions.json`: десять вопросов с ожиданиями и

- `tests/test_rag.py`: проверяется передача контекста, сохранение, ошибки,

существующую цепочку. Исходный индекс и модель эмбеддингов зафиксировать на время
сравнения. В `docs/INDEXING.md` уже описаны ограничения текущей RuBERT; замену
модели на E5 можно исследовать отдельно, чтобы не смешивать её эффект с фильтром.

## 4. Рекомендуемый первый вариант

Реализовать **один query rewrite через LLM + фильтр по cosine similarity**.
Это достаточный по условию и наиболее простой вариант для текущей архитектуры.
Использовать существующий способ обращения к LLM для отдельного короткого
служебного запроса, не запускать полный цикл агента с памятью и инструментами.

Пайплайн:

```text
Исходный вопрос
    ↓
Query rewrite, если включён
    ↓
Эмбеддинг фактического поискового запроса
    ↓
Поиск top_k_before кандидатов
    ↓
Фильтр score >= similarity_threshold, если включён
    ↓
Первые top_k_after из оставшихся
    ↓
Исходный вопрос + отобранный контекст → ответ LLM
```

Начальная конфигурация для эксперимента: `top_k_before=20`, `top_k_after=5`.
Это стартовые значения, а не требование задания. Порог определить по реальным
оценкам своего индекса; не копировать 0.6, 0.83 или 0.10 из чужих проектов.

**Ограничение этого варианта:** фильтр по тому же cosine score сохраняет порядок
выдачи. Он может сократить top-5, но не поднять чанк с места 12 в первые пять:
если 12-й проходит абсолютный порог, то первые 11 тоже проходят. Увеличение
`top_k_before` само по себе здесь не улучшает итоговую выдачу. Запас кандидатов
полезен для диагностики и последующего настоящего реранкинга.

Если измерения покажут, что нужные чанки лежат ниже top-5 или cosine не отделяет
полезные фрагменты от шума, следующим отдельным шагом добавить **один** реранкер:
локальный multilingual cross-encoder либо оценку релевантности через LLM.
Выбор сделать по результатам измерений и доступным ресурсам. Новую оценку и её
порог хранить отдельно от cosine; не добавлять сразу несколько моделей и RRF.

## 5. Режимы

Сохранить общий переключатель «Использовать RAG». Внутри RAG добавить независимые
настройки «Переписывать поисковый запрос» и «Фильтровать по релевантности».

| Режим | Rewrite | Фильтр | Что передаётся модели |
|---|---|---|---|
| Без RAG | Нет | Нет | Обычный запрос, индекс и служебная LLM не вызываются |
| Базовый RAG | Нет | Нет | До 5 ближайших к исходному вопросу чанков |
| RAG + фильтр | Нет | Да | До 5 чанков, прошедших порог |
| RAG + rewrite | Да | Нет | До 5 ближайших к переписанному запросу чанков |
| RAG + rewrite + фильтр | Да | Да | До 5 чанков по переписанному запросу, прошедших порог |

Обязательное сравнение дня 23 — базовый и улучшенный RAG. Промежуточные режимы
рекомендуются, чтобы понять вклад каждого изменения. «Без фильтра/rewriting»
означает RAG с исходным поиском; это не то же самое, что вообще без RAG.
Режим без RAG сохранить из дня 22; повторять его оценку для дня 23 необязательно.

Для согласованной диагностики можно во всех RAG-режимах получать top-20 и затем
выбирать top-5: при текущем точном поиске без фильтра и rewrite итог совпадёт
с прежним top-5. Не подавать все 20 в baseline, иначе сравнение будет одновременно
менять и способ отбора, и максимальное количество контекста.

## 6. Порядок реализации для Codex

### Шаг 1. Настройки и совместимость

Добавить настройки rewrite, фильтра, количества кандидатов, максимума результатов
и порога. Настройки принадлежат диалогу, а в каждом ходе сохраняется снимок
фактически применённых значений. Изменение настроек не должно менять подписи
и диагностику прошлых ответов.

Валидировать `1 <= top_k_after <= top_k_before`, целые значения K, конечный
cosine-порог в диапазоне от -1 до 1. Выключенный фильтр задаётся явным флагом,
а не магическим порогом. Score — мера сходства, не вероятность правильности.

Старые диалоги без новых настроек должны продолжать работать в прежнем режиме:
если RAG включён, то исходный запрос и top-5, без автоматически включённых
rewrite и фильтра. Не заводить несколько независимых полей для одного режима,
которые могут противоречить друг другу.

### Шаг 2. Разделить поиск кандидатов и окончательный отбор

Переиспользовать `search()` из индексатора. Заменить жёсткий `top_k=5` в RAG
на настройку количества кандидатов. Второй этап оформить простой отдельной
функцией: кандидаты → отбор по порогу → ограничение количества.

Сначала применять порог, затем максимум `top_k_after`. Не дополнять выдачу до
пяти заведомо отброшенными чанками. При равных оценках сохранить устойчивый
порядок. Возвращать и финальные чанки, и данные для объяснения отбора.

Общие низкоуровневые функции индексатора не должны получать настройки диалога
или LLM-клиент. Индексация остаётся отдельной операцией.

### Шаг 3. Добавить query rewrite

Один короткий служебный запрос к модели выполняется только при включённом RAG
и rewrite, перед вычислением эмбеддинга. Промпт просит вернуть один поисковый
запрос, сохранив язык, смысл, отрицания и точные идентификаторы. Не придумывать
названия файлов, команды и факты. Уже ясный вопрос допустимо оставить без изменений.

В первом варианте переписывать только текущий вопрос; подключение истории для
фраз вроде «а с этим что?» оставить отдельным расширением. Служебный вызов
не должен пользоваться эталонами контрольных вопросов, MCP или памятью агента.

Проверять непустой результат и длину с учётом токенизатора эмбеддингов. При
ошибке, пустом или оборванном ответе использовать исходный вопрос и сохранять
признак и причину возврата к нему. Не считать такой запуск успешным rewrite
в отчёте сравнения. Ограничить время и объём служебного ответа.

В основной запрос, историю и состояние задачи передавать исходный вопрос.
Rewrite хранить только в диагностике RAG. Учитывать длительность и расход
токенов дополнительного вызова отдельно от генерации ответа. Не удерживать
блокировку локальной embedding-модели во время сетевого вызова rewrite.

### Шаг 4. Описать результат и пустую выдачу

Результат поиска должен позволять восстановить:

- исходный и фактический поисковый запросы, статус rewrite;
- индекс и фактические настройки данного хода;
- кандидатов с `chunk_id`, источником, текстом, score и исходным местом;
- окончательный список и причины исключения: «ниже порога» либо «за пределами
  top-K после отбора»;
- число найденных, прошедших порог и переданных модели фрагментов;
- состояние «релевантных фрагментов не найдено» и ошибки этапов.

Сохранять прежнее значение `score` как cosine. Если позже появится реранкер,
добавить `rerank_score`, а не перезаписывать cosine.

**Особенность текущего кода:** `ConversationStore._decode()` в
`llm_agent/storage.py` требует ровно поля `index`, `chunks` и запрещает пустой
`chunks`. При расширении результата обновить эту проверку, обеспечить чтение
старого формата и корректное сохранение/загрузку пустой выдачи. Для новых полей
также нужна валидация.

Когда все кандидаты отсеяны, сохранить включённый режим RAG и пустой итоговый
контекст. Передать генератору явное сообщение, что подходящих фрагментов не
найдено, с существующей инструкцией обозначить недостаток информации.
Не возвращать отброшенный top-1 и не переключаться молча в «без RAG».
Обязательное «не знаю» с просьбой уточнить относится к усилению дня 24.

Ошибку загрузки индекса или поиска по-прежнему показывать как ошибку, не
маскировать пустой выдачей. Если будет добавлен реранкер, заранее определить
и явно отображать поведение при его сбое; такой запуск не засчитывать как
успешный прогон улучшенного режима.

### Шаг 5. Подключить к существующему чату и CLI

Расширить текущие настройки и раскрываемый блок источников. Показывать
пользователю режим, поисковый запрос, порог, «найдено → прошло → отправлено»
и причины отсева. Отдельная демонстрационная программа не требуется.

В запрос к LLM включать **только финальные чанки**. Полный список кандидатов
нужен для диагностики; если передать его модели, фильтр фактически перестанет
работать. Сохранить правило считать текст документов данными, а не инструкциями.
В режиме мета-промпта повторно использовать один результат поиска на обоих
этапах, как сейчас.

Основные места изменений: `rag.py` — пайплайн; `models.py` и `storage.py` —
настройки и сохранение; `service.py` — организация этапов; `agent.py` — передача
контекста при необходимости; `cli.py`, `web/page.py`, `web/components.py` —
управление и отображение. Имена новых классов/модулей выбрать по фактическому
объёму кода; универсальный фреймворк стратегий для одного фильтра не нужен.

### Шаг 7. Проверить интеграцию и обновить документацию

Добавить содержательные проверки:

- без RAG не вызываются ни rewrite, ни поиск; базовый RAG сохраняет прежнюю выдачу;
- граничное значение `score == threshold` проходит, меньшее отсекается;
- результат не превышает `top_k_after`, порядок стабилен;
- все кандидаты могут быть отсеяны, пустой результат сохраняется и загружается;
- старые JSON-диалоги читаются, новые настройки сохраняются для каждого хода;
- пустой/ошибочный rewrite приводит к исходному вопросу с записью причины;
- поиск использует переписанный запрос, генератор и история — исходный;
- отсеянные чанки не оказываются в сообщениях LLM или в рабочей истории;
- ошибки поиска и генерации не уничтожают уже сохранённую диагностику.

Для этих проверок подменять модель и внешний LLM; настоящий эксперимент качества
проводить отдельно. После целевых тестов запустить существующий набор регрессий,
особенно сохранение диалогов, CLI, веб-интерфейс и мета-промпт.
Обновить `docs/RAG.md`, примеры настроек и подготовить `docs/DAY23_COMPARISON.md`.

## 7. Как сравнивать качество

### Условия

Использовать существующие десять вопросов из `examples/indexing/questions.json`.
Перед прогоном убедиться, что подтверждающие отрывки реально присутствуют
в выбранном снимке индекса. Эталоны и отчёт не добавлять в корпус и не передавать
модели. Сохранить модель и ревизию эмбеддингов, индекс, стратегию chunking,
модель ответа, промпт, температуру и максимальный объём контекста одинаковыми.

На каждый вопрос и режим создавать новый диалог. Отключить MCP, профиль,
память и режим задачи либо обеспечить одинаковое пустое исходное состояние.
Предыдущие ответы не должны подсказывать следующему режиму правильный ответ.
Зафиксировать фактически отправленные чанки и ответы, а не только текущий UI.

Основной прогон: 10 вопросов × 4 RAG-режима = 40 ответов. Это рекомендуемый
диагностический объём, не дополнительное требование организатора. Минимальный
прогон baseline против полного режима — 20 ответов, но он показывает лишь
совместный эффект двух изменений. Автопрогон и LLM-судья не обязательны:
по подходу плана дня 22 допустимы ручной запуск и ручная оценка.

### Настройка порога

1. Получить кандидатов без отсечения и посмотреть распределение cosine scores
   у полезных и бесполезных фрагментов. Для полного режима проверить также
   оценки после rewrite: они могут измениться.
2. На нескольких калибровочных вопросах выбрать несколько порогов из фактического
   диапазона оценок. Желательно подготовить отдельные вопросы для настройки,
   сохранив исходные десять для итоговой проверки.
3. Проверить, сколько лишних чанков удаляет каждый порог и какие нужные фрагменты
   он ошибочно теряет. Повторно вызывать LLM для каждого порога не требуется:
   отбор можно рассчитать по одному сохранённому списку кандидатов.
4. Выбрать компромисс с сохранением нужной информации; затем зафиксировать
   параметры перед итоговым сравнением. Если настройка и оценка сделаны на тех
   же десяти вопросах, прямо назвать это учебным сравнением, не независимым тестом.
5. Если полезные и бесполезные cosine scores сильно пересекаются, зафиксировать
   ограничение фильтра и оценить необходимость отдельного реранкера.

Дополнительно проверить 2–3 вопроса вне корпуса и 2–3 менее формальные
перефразировки вопросов по базе. Например, вопрос о прогнозе погоды проверяет
отсутствие ответа в документации проекта, а «снесу профиль — чаты пропадут?»
проверяет поиск по разговорной формулировке. Ожидания сначала подтвердить по
корпусу. Эти случаи показывать отдельно от исходных десяти.

### Что записывать

| Поле | Назначение |
|---|---|
| Вопрос, режим, фактический rewrite, K и порог | Воспроизводимость |
| Полезные отрывки среди кандидатов и в итоговом контексте | Отличить провал поиска от потери при фильтрации |
| Количество кандидатов, прошедших порог и переданных чанков | Видеть работу отбора |
| Исходный и итоговый ранг нужного чанка | Объяснить эффект настоящего реранкинга, если он добавлен |
| Дословный ответ и оценка 0/1/2 | Оценить правильность и полноту |
| Выдуманные или не подтверждённые контекстом детали | Оценить опору ответа на найденные данные |
| Размер контекста, время и дополнительные токены rewrite | Оценить цену улучшения |
| Ошибки и возврат к исходному запросу | Не смешивать сбои с нормальными прогонами |

Шкала ответа: 0 — неверный/отсутствует при наличии ответа в базе; 1 — частично
верный; 2 — верный и достаточно полный. Для вопроса вне базы ожидаемое поведение
оценивается отдельно: честное сообщение об отсутствии данных не является ошибкой.

Достаточно итоговой суммы из 20 для каждого режима, числа ответов с выдумками,
числа вопросов с найденным подтверждающим фрагментом и среднего количества
переданных чанков. Совпадение одного имени файла слишком грубое: проверять
наличие нужного отрывка/раздела, используя имеющуюся разметку `source + quote`.
Автоматическая проверка цитаты — вспомогательная: полезную перефразировку может
не засчитать; точность всего ответа оценивает человек.

Разобрать несколько показательных случаев: улучшение, отсутствие изменения,
ухудшение или пустую выдачу. Не обещать, что фильтр или rewrite обязательно
улучшат каждый вопрос. Если результаты не изменились, это тоже измеренный
результат, но утверждать улучшение качества на его основании нельзя.

## 8. Границы и критерии готовности

В рамках дня 23 не требуются новая БД, перенос поиска в MCP, автоматическое
решение модели о вызове RAG, несколько реранкеров, multi-query/RRF или обучение
модели. Обязательные цитаты и проверка их соответствия ответу — день 24;
длинные диалоговые сценарии и развитие памяти задачи — день 25.

Результат готов, когда:

1. В существующем агенте работают baseline, фильтр, rewrite и их сочетание.
2. Настраиваются порог, число кандидатов и максимум передаваемых чанков.
3. В интерфейсе и сохранённом ходе видны фактические параметры, запрос и отбор.
4. Пустая выдача штатно обрабатывается; отброшенные чанки не возвращаются в prompt.
5. Сохраняются прежнее поведение без RAG и возможность открыть старые диалоги.
6. Проверена корректность реализации и отдельно проведено реальное сравнение
   качества; в отчёте есть ответы, оценки, условия и выводы с ограничениями.

Наличие переключателей и зелёных unit-тестов подтверждает реализацию, но не
завершает пункт «сравните качество». Если реальный прогон ещё не выполнен,
отчёт должен прямо содержать этот статус, без придуманных оценок.
