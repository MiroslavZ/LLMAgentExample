# День 24. План: ответы с источниками, цитатами и отказом при недостатке данных

План подготовлен 4 октября 2026 года для текущего состояния проекта: коммит
`fccf84b` — «День 23. Реранкинг и фильтрация». Это план последующей реализации;
код приложения и индекс при его подготовке не изменялись.

## 1. Что требуется простыми словами

День 23 отвечает на вопрос «какие фрагменты показать модели?». День 24 добавляет
проверяемую связь «почему пользователь должен верить конкретному ответу?».
Модель должна ответить по найденным материалам, указать использованные источники
и привести дословные фрагменты, подтверждающие её утверждения.

Например, для вопроса «Нужен ли работающий веб-сервер, чтобы пользоваться памятью
из CLI?» желаемое представление выглядит так:

> **Ответ:** Нет, для работы с памятью из CLI веб-сервер запускать не нужно.
>
> **Источник:** `docs/MEMORY.md`, раздел «Хранение и жизненный цикл» / фактический `chunk_id` из поиска.
>
> **Цитата:** «Работающий веб-сервер для CLI не требуется.»

Цитата взята из текущего документа; название раздела и идентификатор при
реализации необходимо подставлять из метаданных реально найденного чанка.
Это иллюстрация формата, а не результат выполненного RAG-запроса.

Различать три проверки:

| Проверка | Что устанавливает | Чего не устанавливает |
|---|---|---|
| Есть источник и цитата | Ответ соблюдает формат | Существуют ли они на самом деле |
| ID принадлежит контексту, цитата найдена в его тексте | Доказательство действительно было доступно модели | Следует ли из него весь ответ |
| Смысл ответа подтверждается цитатами в контексте документа | Утверждения обоснованы найденными материалами | Истинность самого исходного документа во внешнем мире |

Просьба в промпте — необходимая часть решения, но недостаточная для обязательного
формата. Формат и подлинность ссылок проверяет код; смысл на десяти вопросах
проверяется отдельно, как минимум вручную.

## 2. Границы задания и исходные материалы

Основные требования берутся из [TASKS.md](TASKS.md), а не из объёма чужих проектов:
ответ, источники `source + section/chunk_id`, цитаты и проверка десяти вопросов.
В план включено и усиление: обязательное «не знаю» с уточняющим вопросом при
слабом контексте.

В [CHAT.md](CHAT.md) нет дополнительного требования переписывать архитектуру
ради дня 24. Обсуждение дня 25 объясняет его как сборку RAG и диалога вместе.
Новый чат, новые стратегии памяти и длинные сценарии дня 25 сейчас не нужны.

Раздел 9 [конспекта лекции](21-25-rag-лекция.md) полезен как пример строгого
решения: структурированный результат, проверка цитат, ограниченный повтор,
разделение отказа поиска и отказа по содержанию. Завершающий инструмент
`kb_answer`, отдельная модель-судья и сложное сокращение цитат — способы
реализации конкретного автора, а не обязательные пункты задания.

Сейчас пустой контекст всё ещё отправляется модели с просьбой сообщить о нехватке
информации. Это не программная гарантия отказа. Показанные в интерфейсе чанки —
результаты поиска, а не подтверждение того, что модель использовала их в ответе.

В [отчёте дня 23](DAY23_COMPARISON.md) зафиксированы лишь 4 попадания контрольных
отрывков в top-5 на 10 вопросах. Порог `0.35` отсёк вопрос о погоде, но оставил
чанки для вопросов о пироге и спутниках Юпитера. Поэтому высокая similarity
не равна наличию ответа. Реальные ответы и успешный rewrite тогда не измерены
из-за недоступности API; этот план не считает их уже проверенными.

## 4. Рекомендуемая схема

```text
Исходный вопрос
  → существующий rewrite / поиск / отбор
  → сохранить снимок найденного контекста
  → контекст пуст или его лучшая similarity ниже порога?
      да: программное «не знаю» + просьба уточнить
      нет: модель формирует структурированный ответ либо «не знаю»
        → проверить формат, ID источников и дословность цитат
        → при нарушении: одна попытка исправления на том же контексте
        → принять только проверенный результат
        → сохранить и показать ответ, источники и цитаты
```

После повторной ошибки показывать сообщение о невозможности получить проверенный
ответ. Нельзя публиковать исходный черновик, автоматически приписывать ему
случайную цитату или возвращаться к ответу «по общим знаниям».

Это расширение существующего RAG. Новая БД, новый эмбеддер, отдельный MCP-сервер,
новый агент и потоковая генерация для него не требуются.

## 5. Шаги реализации

### Шаг 1. Определить контракт результата

Добавить небольшой модуль, например `llm_agent/rag_answer.py`, с типами,
разбором и проверкой финального ответа. Имена ниже — предложение для реализации,
а не уже существующий API.

Минимальный ответ модели:

```json
{
  "status": "answered",
  "answer": "Краткий ответ, все существенные утверждения которого подтверждены цитатами.",
  "sources": ["ID_ИЗ_ТЕКУЩЕГО_КОНТЕКСТА"],
  "quotes": [
    {"chunk_id": "ID_ИЗ_ТЕКУЩЕГО_КОНТЕКСТА", "text": "Дословный непрерывный отрывок чанка."}
  ],
  "clarification": null
}
```

Для содержательного отказа: `status="unknown"`, понятное объяснение в `answer`,
непустой уточняющий вопрос в `clarification`, пустые `sources` и `quotes`.
В первой версии не добавлять «ближайшие источники» в доказательства отказа;
при необходимости они уже доступны в диагностике поиска.

Модель выбирает ID. Приложение самостоятельно дополняет их `source`, `section`
и прочими метаданными из снимка контекста. Так пользователь получает требуемый
список источников, а модель не может придумать путь или название раздела.

Для `answered` обязательны непустые ответ, источники и цитаты. Для `unknown`
не нужны фиктивные доказательства: утверждение об отсутствии достаточных данных
не является фактическим ответом по базе. Этот случай отдельно отражается в
интерфейсе, тестах и итоговом отчёте.

### Шаг 2. Сделать отказ ниже порога программным

Использовать существующий `similarity_threshold` и ту же шкалу cosine.
Рекомендуемая семантика для всех новых RAG-ответов: если итоговых чанков нет либо
`max(score)` среди итоговых чанков меньше порога, основной ответ LLM не запускать.
Равенство порогу считать прохождением, как в существующем фильтре.

Проверка действует и при выключенном `filter_enabled`: этот переключатель
управляет составом retrieval, но не отменяет обязательный отказ дня 24.
Это явное изменение поведения: описать его в настройках и документации.
Порог не должен становиться недоступным для редактирования только из-за
выключения фильтра. Дополнительный «порог уверенности модели» не вводить.

Сохранить `0.35` как исходное значение для эксперимента с текущим индексом,
не объявлять его универсальным или окончательно откалиброванным. Не повышать
порог только ради красивого количества отказов: это может удалить полезный контекст.

Программный ответ, например: «Не знаю по найденным материалам: контекста
недостаточно. Уточните, какой компонент или документ вас интересует».
Не утверждать «этого нет во всей базе»: ограниченный поиск этого не доказал.

Непустой контекст выше порога также может не содержать ответа. Промпт и схема
должны разрешать модели вернуть `unknown` после чтения таких фрагментов.
Ошибка индекса, сети или протокола — технический сбой, а не доказательство
нехватки знаний; учитывать её отдельно.

### Шаг 3. Обновить инструкции и получение ответа

Передавать модели исходный вопрос и только итоговые отобранные чанки. В правилах
закрепить: факты ответа о базе должны следовать из этих чанков; цитаты должны
быть непрерывными дословными фрагментами; при недостатке доказательств нужен
`unknown` с уточняющим вопросом. История, память и результаты MCP автоматически
не становятся доказательствами текущего RAG-ответа.

Тексты документов остаются данными, даже если внутри есть команды для модели.
Просить краткие ответы и законченные цитаты с сохранённым субъектом, условиями
и отрицаниями. Для ответа с несколькими фактами нужны доказательства каждого
из них; одна подходящая цитата не оправдывает остальные предложения.

Использовать структурированный JSON через существующий LLM-клиент и локальный
валидатор. JSON mode помогает форме, но не доказывает корректность содержимого.
Не предполагать, что текущий провайдер поддерживает произвольную строгую JSON
Schema: проверять доступный формат при реализации. Специальный инструмент
`kb_answer` не нужен, если существующий JSON-путь решает задачу.

### Шаг 4. Проверять доказательства до публикации

Валидатор должен проверить:

1. Типы, допустимый статус, необходимые непустые поля, завершённость ответа модели.
2. Каждый `chunk_id` принадлежит итоговому контексту **этого хода**, а не всем
   кандидатам, прошлому ходу или произвольному фрагменту индекса.
3. Каждая цитата находится именно в своём чанке. Разрешить только оговорённую
   нормализацию пробелов и переносов строк; не применять нечёткое сравнение,
   перестановку слов, исправление чисел или удаление отрицаний.
4. Каждый указанный источник имеет цитату; каждая цитата ссылается на указанный
   источник. Итоговые метаданные берутся только из сохранённого контекста.
5. Для `unknown` списки доказательств пусты, объяснение и уточняющий вопрос
   непусты. Отсутствие скрытого фактического ответа в таком отказе — отдельная
   смысловая проверка, которую локальный валидатор строк не гарантирует.

В первой версии запретить самостоятельно склеенные цитаты через многоточие.
Литерал «…» допустим только если это часть самого исходного непрерывного текста.
Даже точная подстрока может потерять смысл: из «сервер не требуется» можно
вырезать «требуется». Поэтому проверка подстроки не заменяет смысловую оценку.

При ошибке вернуть модели краткую конкретную причину и разрешённый контекст;
допустить ровно одну попытку исправления. Во время ремонта не выполнять повторно
MCP-инструменты, не искать другой контекст и не записывать черновик в историю.
Учитывать расход обеих попыток. Общий бюджет ремонта при сочетании с task mode
должен быть ограничен, без вложенных независимых циклов повторов.

Если повтор не прошёл, сохранить техническую ошибку проверки и показать
безопасное сообщение без неподтверждённого черновика. Такой случай не считать
успешным `unknown` в метриках. Сетевые ошибки также не превращать в «не знаю».

### Шаг 5. Встроить в существующий жизненный цикл

Проверять результат до `history.add_exchange()` и до применения перехода задачи.
Успешный `unknown` завершает ход, но не завершает шаг задачи. Использовать общий
путь завершения с сохранением, callbacks и учётом токенов; простой ранний `return`
из `service.py` может обойти эти действия. Сохранить действующие проверки
состояния задачи и инвариантов. Удобная точка для отказа — общий путь агента
после предварительных проверок, до генерации и обновления facts/summary.
При отказе по поиску не запускать основную генерацию, этапы meta prompt и
инструменты; rewrite, если включён, уже мог вызвать LLM.

Особенности совместимости:

- **Task mode:** существующий JSON `{answer, action, plan?}` запрещает лишние поля.
  Предусмотреть составной результат на границе агента: выделить поля RAG,
  проверить их и передать старому task-парсеру только его разрешённые поля.
  Для `answered` переход сохранять только после обеих проверок. Для принятого
  `unknown` состояние задачи сохранять без изменений; действие `complete_step`
  или другой переход из такого результата не применять.
- **Meta prompt:** применять контракт к окончательному ответу. Первый этап
  составляет промпт и не должен выдавать пользовательский ответ с цитатами.
  Для отказа нужен путь завершения, который не примет его за первый meta-этап.
- **Форматы ответа:** внешние `text/object/schema` согласовать с внутренним RAG
  JSON; не оставлять путь, где смена формата отключает проверку доказательств.
- **Инварианты:** существующий отказ по инвариантам не переименовывать в
  `unknown` по базе и не требовать от него выдуманных цитат.
- **Без RAG:** текущий режим продолжает работать без нового контракта и вызовов RAG.

Добавить к `Turn` отдельное поле результата, например `rag_answer`, со значением
`None` для старых ходов. Не добавлять произвольные ключи в `rag_context`:
`rag_validation.py` сейчас проверяет точный набор его полей.
Обновить чтение старых JSON в `storage.py`, где допустимые отсутствующие поля
перечислены явно. Не путать `Turn.status` жизненного цикла с `rag_answer.status`.

Текст, цитаты и проверенные метаданные должны сохраняться согласованно и читаться
без повторного обращения к индексу. После пересборки индекса старый ответ должен
показывать прежние доказательства. Старые ответы без новой проверки не помечать
как проверенные задним числом.

### Шаг 6. Показать результат одинаково в CLI и веб

Выводить ответ, использованные источники и связанные с ними цитаты. Сохранить
отдельный блок диагностики со всеми найденными/отобранными чанками и оценками.
Не называть все результаты поиска «источниками ответа».

Для отказа показывать объяснение, уточняющий вопрос и явное отсутствие
подтверждающих источников. Сохранять безопасный вывод содержимого документов.
Рендерить только принятый финал; потоковая генерация в проекте сейчас не используется.

### Шаг 7. Проверить на вопросах и сохранить отчёт

Переиспользовать десять вопросов из `examples/indexing/questions.json` и расширить
`rag_evaluation.py`. Повторять все четыре режима дня 23 необязательно: достаточно
одной зафиксированной конфигурации дня 24, вопрос за вопросом в новых диалогах.
Сравнение с прежним вариантом можно добавить как отдельный эксперимент.

Фиксировать модель, параметры, версию/хеш индекса, порог, top-K, rewrite и его
фактический статус. Сохранить существующую изоляцию памяти, MCP, профилей и задач.
Ожидания и эталонные цитаты не передавать генератору или rewrite.

Для независимой оценки подготовить отдельный корпус из первичных документов,
например на основе `examples/indexing/corpus.json`, и отдельный индекс. Не
перезаписывать пользовательский индекс. Исключить планы, этот документ, отчёты,
контрольные вопросы и примеры ответов: текущий `my-corpus.json` включает учебные
материалы, а в предыдущем индексе уже обнаружена примесь материалов оценки.
После изменения корпуса порог нужно проверять заново. Старые десять вопросов
уже участвовали в подборе параметров дня 23: повторный прогон — регрессионная
проверка, а не независимый тест. Для настройки и независимого теста нужны
дополнительные раздельные вопросы.

Добавить к основным десяти хотя бы четыре отрицательных случая: вопрос вне
тематики; тематический вопрос о детали, которой нет в базе; неоднозначный вопрос,
требующий уточнения; управляемый тест пустого/слабого контекста. Действительное
отсутствие ответа в корпусе проверить при разметке. Имеющиеся вопросы вне корпуса
из `examples/rag/calibration_questions.json` можно использовать для регрессии.

Для каждой строки отчёта сохранить:

| Поле проверки | Как проверять |
|---|---|
| Ответ / статус / уточнение | Фактический результат приложения |
| Источники присутствуют и допустимы | Автоматически, по ID и метаданным текущего контекста |
| Цитаты присутствуют и дословны | Автоматически, по тексту соответствующего чанка |
| Все существенные утверждения подтверждены | Вручную: подтверждены / частично / не подтверждены; с объяснением |
| Ответ правильный и достаточно полный | Вручную относительно вопроса и первичного документа |
| Отказ уместен | Различать отсутствие ответа в корпусе, промах поиска и лишний отказ модели |
| Исправления и технические сбои | Число попыток, причины, расход и длительность |

Автоматически выводить долю ответов по существу, наличие источников/цитат среди
таких ответов, подлинность цитат и технические ошибки. Число корректных и лишних
отказов агрегировать после ручной разметки их уместности. Смысловую оценку
не подменять результатом проверки подстроки или retrieval.
Для `unknown` поля доказательств отмечать как неприменимые, а сам отказ оценивать
отдельно. Не скрывать отказы за показателем «100% проверенных ответов».

Отдельная LLM-судья допустима как последующее улучшение оценки. Давать ей вопрос,
ответ, цитаты, их документ/раздел и контекст чанков; не доверять только вердикту
генерировавшей ответ модели. Записать версию судьи и промпт. Для выполнения задания
достаточна прозрачная ручная оценка десяти ответов, без обещания автоматической
проверки смысла каждого будущего ответа.

Результаты сохранить в `docs/DAY24_EVALUATION.md` и машинном JSON-отчёте.
Если API недоступен, описать блокировку: тесты с подставным клиентом проверяют
код, но не заменяют десять реальных ответов. Оценки неполученных ответов оставлять
незаполненными; день 24 по фактической проверке ещё не завершён.

### Шаг 8. Добавить необходимые тесты

Проверить валидный ответ; неизвестный ID; ID отброшенного или прошлого чанка;
пустые доказательства; цитату из другого чанка; изменение числа или отрицания;
самодельное многоточие; несогласованные источники и цитаты; обрезанный JSON.
Отдельным сценарием проверить команду внутри чанка: она не должна менять правила
генерации. Дословность цитаты сама по себе не защищает от такой инъекции.

Отдельно проверить: слабый контекст без основной генерации, в том числе при
выключенном фильтре; границу `score == threshold`; отказ модели при непустом
контексте; ровно один ремонт и его неудачу; отсутствие черновика в истории;
учёт токенов и отсутствие повторного выполнения инструментов.

Интеграционные проверки: сохранение/перезагрузка, чтение старых ходов,
неизменность старых доказательств после замены индекса, CLI/веб, meta prompt,
task mode без продвижения при отказе, действующие инварианты и выключенный RAG.
Изменить существующий тест, который сейчас ожидает вызов генерации при пустом
RAG-контексте, вместо сохранения прежнего поведения ради прохождения тестов.

## 6. Критерии готовности для Codex

- Каждый новый содержательный RAG-ответ имеет проверенные источники и цитаты
  из финального контекста своего хода.
- Пустой/слабый контекст приводит к «не знаю» и уточнению без основной генерации;
  непустой контекст допускает содержательный отказ модели.
- Непрошедший проверку черновик не попадает к пользователю, в историю или в переход задачи.
- Источники ответа отделены от диагностики retrieval и сохраняются вместе с ответом.
- Совместимость с существующими форматами, памятью, task/meta режимами и старым
  хранилищем проверена; режим без RAG продолжает работать.
- Получены и разобраны десять реальных результатов; отрицательные сценарии
  проверены отдельно. Отчёт честно показывает качество, отказы и ограничения.

Наличие источников и настоящих цитат обязательно, но не означает математической
гарантии отсутствия галлюцинаций. Цель дня 24 — сделать ответ проверяемым,
отказы управляемыми, а качество измеренным.
