# День 25. План: диалоговый RAG и память задачи

План подготовлен 5 октября 2026 года для коммита `6bfb2b6` — «День 24.
Цитаты, источники и анти-галлюцинации». Он предназначен для последующей
реализации агентом Codex. При подготовке код приложения и индекс не менялись.

## 1. Главный вывод

**Новый мини-чат создавать не требуется.** В этом проекте уже есть общий
CLI/веб-чат, сохранение диалогов, поиск перед каждым RAG-ответом и проверенные
источники с цитатами. Основная часть дней 22–24 уже встроена в агента.

День 25 здесь — довести существующий RAG до устойчивого многошагового разговора:

1. Поиск понимает продолжения вроде «а как это сделать в CLI?».
2. Цель, уточнения, ограничения и определения пользователя доступны после
   сокращения истории и перезапуска.
3. Память помогает выбрать вопрос и форму ответа, а документальные утверждения
   по-прежнему подтверждаются текущими найденными источниками.
4. Это проверено на двух последовательных диалогах, а не на независимых вопросах.

Если ограничиться обязательной частью задания без усиления, основная разработка
уже выполнена: остаются длинные проверки и устранение обнаруженных проблем.
Ниже рекомендован вариант **с усилением**, без переписывания существующего чата.

Само усиление не требует именно автоматического извлечения или новой структуры
хранения: существующая ручная working-память уже может содержать цель, условия
и термины. Самый короткий вариант — явно заполнить её, использовать выбранные
записи в контекстном rewrite и проверить длинные диалоги. Это допустимая сдача,
если честно описать ручное обновление условий. План ниже предлагает более удобный
вариант: уточнения из обычных реплик сохраняются автоматически. Новый небольшой
блок нужен именно для этой выбранной функции и её отделения от ручной памяти,
а не потому, что задание требует ещё одну систему хранения.

## 3. Что уже реализовано и чего не хватает

Пути и номера строк относятся к исходному коммиту; после реализации они изменятся.

| Требование | Состояние сейчас | Работа дня 25 |
|---|---|---|
| CLI/веб-чат | Оба интерфейса работают через `ConversationService` | Использовать их |
| История и продолжение | Полная лента `turns`, сокращаемый `working_context`, атомарное JSON-хранение | Проверить длинный диалог и перезапуск |
| Поиск на каждом вопросе | `service.py:503–511` вызывает retrieval перед генерацией каждого RAG-хода | Сохранить обязательность поиска; улучшить поисковый запрос |
| Дни 22–23 | Индекс, rewrite, similarity-фильтр, top-K до/после и диагностика уже есть | Подключить контекст диалога к rewrite |
| День 24 | `rag_answer.py:64–103`: схема, проверка ID текущих чанков и дословности цитат, ограниченный repair | Сохранить контракт и проверки |
| Слабый контекст | `_rag_gate` и модель могут вернуть `unknown`; FSM не продвигается | Не терять новые уточнения пользователя при отказе |
| Источники после открытия истории | `Turn.rag_answer/rag_context`, проверка при загрузке в `storage.py:163–176` | Регрессионная проверка |
| Память задачи | FSM `TaskState`, ручной `MemoryStore`, отдельные facts/summary | Добавить компактную актуальную память свободного диалога |
| Длинные проверки | `rag_evaluation.py` создаёт новый диалог на каждый вопрос/режим | Добавить сценарный прогон одного диалога |

Конкретные разрывы:

- `rewrite_query` в `rag.py:40–51` получает только текущий вопрос. Даже включённый
  rewrite не знает, что означает «это». Память загружается в сервисе уже после
  поиска, поэтому наличие памяти у генератора не исправляет retrieval.
- `TaskState` — автомат `planning → execution → validation → done`. Он включается
  явно, хранит цель и заметки, но не ведёт структурированные актуальные условия
  обычного разговора. Для RAG-справки не требуется запускать выполнение плана.
- Явная рабочая память дня 11 заполняется командами/редактором. Обычная фраза
  пользователя не создаёт запись. Facts зависят от выбранной стратегии контекста.
- При раннем `unknown` facts не обновляются; в составном RAG/FSM-протоколе отказ
  сохраняет прежний FSM. Само сообщение есть в полной ленте, но его уточнения
  могут перестать попадать в запрос после сокращения окна.
- Grounding-инструкция запрещает сведения из прежних сообщений слишком широко.
  Нужно разрешить использование пользовательских условий, сохранив запрет на
  неподтверждённые документальные факты из старых ответов.
- `unknown` сейчас отображается без раздела источников. Требование «всегда»
  лучше выразить явным сообщением об отсутствии подтверждающих материалов.

## 4. Рекомендуемая архитектура

```text
Текущий вопрос + сохранённая память + короткий хвост диалога
  → подготовка хода: обновления памяти и самостоятельный поисковый запрос
  → проверка и сохранение подтверждённых пользователем уточнений
  → существующий retrieval → существующий фильтр/top-K
  → существующая проверка достаточности контекста
  → генерация: исходный вопрос + история + память + текущие чанки
  → существующая проверка источников/цитат и один repair
  → сохранение ответа, диагностики и доказательств
```

### 4.1. Память диалога и автомат выполнения — разные обязанности

Добавить небольшой тип `DialogueTaskMemory` с четырьмя группами данных:

| Поле | Пример для этого корпуса |
|---|---|
| `goal` | Подготовить памятку по памяти Python-агента для работы через CLI |
| `clarifications` | Используется Windows; обсуждаем один локальный диалог |
| `constraints` | До двух пунктов в ответе; общую долговременную память не изменять |
| `terms` | «Сеанс» означает диалог; «общая память» означает `long_term` |

У каждого значения хранить происхождение: номер пользовательского хода и
дословный фрагмент его сообщения. Это внутреннее происхождение записи памяти,
**оно не является цитатой из базы знаний**. Не нужен полный журнал всех версий:
исходные реплики уже сохраняются в `turns`.

Рекомендуемое место хранения — новое необязательное поле
`Conversation.dialogue_task_memory` в существующем JSON диалога, рядом с
`working_context`. Передавать агенту неизменяемый снимок параметром, по аналогии
с `MemorySnapshot`. `_ConversationHistory._write_data` уже копирует всю
`Conversation`, поэтому не требуется расширять внутренний формат каждой
стратегии истории ради этой функции.

Это осознанно функция общего CLI/веб-сервиса. Поддержка новой памяти в отдельном
низкоуровневом `Agent(history_path=...)` и его ветках не нужна для дня 25.
Не добавлять вторую БД и не записывать автоматические наблюдения в ручной
`MemoryStore` или профиль пользователя.

Правила состояния:

- Заполнять только явно сообщённые цель, условия, уточнения и определения.
  Текст ассистента помогает разрешать ссылки, но не становится подтверждённым
  требованием пользователя. Чанки RAG вообще не участвуют в извлечении памяти.
- Новое явное исправление заменяет соответствующее прежнее значение. Удаление
  ограничения возможно по явной отмене. Обычный новый вопрос не заменяет цель.
- Не принимать предположения, цитируемые чужие инструкции и гипотетические
  примеры за реальные решения пользователя.
- Проверять типы, размер, допустимые операции обновления и наличие цитаты в
  указанной пользовательской реплике. Дословное происхождение снижает риск
  выдумки, но не доказывает правильность интерпретации; это проверяется сценариями.
- Ограничить объём памяти и передаваемого хвоста. Не вытеснять действующее
  ограничение только потому, что оно старое. При невозможности безопасно
  применить обновление сохранять прежнюю память и диагностировать проблему.
- Новый диалог имеет пустое состояние. Выключение RAG сохраняет накопленную
  память, но не запускает её служебную обработку. Возврат в RAG использует
  прежний снимок и текущий вопрос; скрытого переноса из других диалогов нет.
- Начало новой FSM-задачи в том же диалоге и очистка ручной working-памяти
  не очищают этот блок скрыто. Для полностью новой темы есть новый диалог;
  явные исправления/отмена условий текущего разговора обрабатываются обновлением
  памяти. Эту семантику объяснить рядом с просмотром памяти.
- Новый блок описывает цель разговора; `TaskState.title` описывает явно запущенную
  задачу выполнения. Не менять `title`, этапы, план и утверждение автоматически.
  При активном FSM его правила остаются обязательными. Уточнение в разговоре
  не является командой утверждения плана.
- Текущие явные пользовательские условия уточняют автоматически извлечённые
  старые значения; системные правила, инварианты и ограничения FSM сохраняют
  свой приоритет. Конфликт с ручной памятью не должен молча перезаписывать её БД.

### 4.2. Подготовка поискового запроса

Реализовать одну небольшую подготовку хода, например в `rag_dialogue.py`.
Её чистые части — валидация/применение обновления памяти и сборка контекста;
внешний вызов LLM отделить от них.

Один ограниченный служебный вызов может возвращать
`{memory_delta, standalone_query}`. Это заменяет отдельный вызов rewrite в
диалоговом режиме, а не добавляет несколько последовательных извлекателей.
Вход: текущая исходная реплика, прежняя память и ограниченный хвост последних
успешных обменов. Предыдущий ответ брать без больших блоков источников/цитат,
когда доступен структурированный `rag_answer`. Не отправлять всю `turns`, старые
чанки, отклонённые черновики, эталоны проверки и результаты инструментов.

Обновление памяти и запрос проверять независимо. Если одно поле невалидно,
это не основание принять другое без проверки. Ошибка API/формата сохраняет
прежнюю память и исходный поисковый вопрос с явной диагностикой fallback.
Учитывать время и токены служебного запроса отдельно и без двойного подсчёта.

Поведение rewrite:

- «А как её очистить?» после обсуждения рабочей памяти становится вопросом об
  очистке рабочей памяти, а не поиском местоимения.
- Определённые пользователем термины помогают поиску: «сеанс» → «диалог».
- Явный новый предмет вопроса важнее недавней темы. Вопрос о профилях после
  памяти должен искать профили; вопрос о погоде не превращается в вопрос о памяти.
- Не приклеивать всю цель и все ограничения к каждому запросу: они могут
  ухудшить retrieval. Добавлять только сведения, нужные для смысла этого вопроса.
- При неразрешимой неоднозначности не выдумывать объект; сохранить возможность
  честного отказа/уточнения по существующему RAG-контракту.
- Сохранить смысл `--no-rag-rewrite`: поиск исходной реплики. При включённой памяти
  подготовка продолжает извлекать условия, но `standalone_query` игнорируется,
  диагностика rewrite остаётся `disabled`, а расход подготовки учитывается
  отдельно. Генератор получает актуальную память. Настройки и исходный вопрос сохранять.

Не менять незаметно baseline дня 23: прежний одношаговый evaluator должен
явно работать без новой памяти либо фиксировать её режим в отчёте. Для основных
сценариев дня 25 включить RAG, диалоговую память, rewrite и фильтр.

### 4.3. Порядок сохранения и обработка отказов

В `ConversationService.send` после записи пользовательского хода подготовить
и сохранить валидное обновление памяти **до retrieval**, затем создать агент
с актуальным снимком. Операции выполнять под существующей блокировкой диалога.
Обновление должно предшествовать созданию `_ConversationHistory`: иначе его
старый снимок `Conversation` может перезаписать новую память при сохранении ответа.

Состояния различаются:

| Ситуация | Память условий пользователя | FSM выполнения |
|---|---|---|
| Найден ответ с проверенными доказательствами | Сохранить валидные уточнения | Применить только допустимое проверенное действие |
| Пустая выдача или содержательный `unknown` | Сохранить валидные уточнения | Не продвигать |
| Ошибка поиска/генерации после сохранения памяти | Уточнения остаются, ход явно помечен ошибкой | Не продвигать |
| Ошибка подготовки памяти | Сохранить прежний снимок; исходная реплика остаётся в ленте | Обычные действующие правила |
| Ошибка записи на диск | Не изображать успешное сохранение | Сохранить действующие гарантии сервиса |

Подготовка выполняется один раз на пользовательский ход. Repair финального
ответа использует тот же поисковый контекст и память: он не должен повторять
обновление памяти, retrieval или внешние инструменты.

### 4.4. Ответ и источники

Сохранить строгий контракт дня 24:

- Для `answered` нужны источники и дословные цитаты только из **текущих выбранных
  чанков**. История, memory, высокий score и факт наличия кандидатов не являются
  доказательством ответа по документации.
- Память определяет цель, терминологию, ограничения и формат. Пользовательское
  «только CLI» не нужно подтверждать документацией. Инструкцию grounding уточнить
  так, чтобы она допускала эти условия и запрещала старые недоказанные факты.
- Для `unknown` массивы доказательств остаются пустыми. В CLI и веб показывать
  «Источники: подтверждающие материалы не найдены» и просьбу уточнить вопрос.
  Не прикладывать случайные чанки ради формального наличия ссылки.
- Список всех найденных фрагментов оставить диагностикой, отдельно от реально
  использованных источников ответа.
- Сохранённый ответ открывается вместе с прежними доказательствами, даже если
  пользователь изменил настройки или текущий индекс уже другой.

Служебный просмотр цели и условий реализовать через панель памяти и CLI-команду
чтения состояния. Это не RAG-вопрос и не требует выдумывать документальный источник
личной цели. Отдельная маршрутизация естественных реплик «напомни цель» с новым
типом ответа не обязательна для этого плана; в длинных сценариях цель проверяется
по состоянию и предметным ответам. На обычных вопросах чат продолжает выполнять RAG.

   отключение rewrite и сопоставимость одношаговых режимов.
3. **Включить в общий сервис.** Сохранение уточнений перед поиском; снимок памяти
   у генератора, включая мета-промпт; стабильность при unknown/ошибках/repair.
4. **Уточнить инструкции и представление.** Разделить пользовательские условия и
   фактические доказательства; показать память в существующем интерфейсе и
   отсутствие источников при unknown. Новый чат не нужен.
5. **Добавить регрессионные проверки.** Проверить существенные пути ниже.
6. **Подготовить и выполнить два сценария.** Один диалог на сценарий, короткое
   окно, реальные RAG/LLM, перезапуск и исправления ограничений.
7. **Обновить документацию и отчёт.** Описать новую автоматическую память отдельно
   от ручной, команды запуска/просмотра и фактические результаты проверки.

| `models.py`, `storage.py` | Поле памяти и необязательная диагностика подготовки в `Turn`, совместимое чтение |
| `service.py` | Порядок preparation → save memory → retrieval → Agent |
| `rag.py` | Переиспользование текущих механизмов rewrite/fallback без дублирования поиска |
| `agent.py`, `rag_answer.py` | Подмешивание снимка и уточнение grounding-инструкции |
| `cli.py`, `web/page.py`, `web/components.py` | Просмотр памяти и представление источников/отсутствия источников |
| Новый сценарный runner или расширение `rag_evaluation.py` | Последовательные ходы и метрики памяти с переиспользованием существующих проверок |
| `examples/rag/day25_scenarios.json`, `docs/DAY25_REPORT.md` | Входные сценарии и проверенные результаты |
| `docs/RAG.md`, `docs/MEMORY.md`, при необходимости README | Различие ручной памяти, памяти RAG-диалога и FSM |

Точные названия новых функций и модулей можно упростить при реализации.
Отдельный сервис, фреймворк агентов и универсальный движок памяти не нужны.

## 6. Совместимость, которую нельзя пропустить

- `ConversationStore._decode` проверяет точное множество верхних полей. Простого
  добавления dataclass-поля недостаточно: старые JSON должны продолжать читаться,
  а новые данные — проходить строгую проверку.
- `Turn` тоже имеет обязательные/необязательные поля. Диагностика подготовки
  должна читаться при её отсутствии в старых ходах.
- `rag_validation.py` строго проверяет поля rewrite/context и соответствие
  fallback исходному вопросу. Новую диагностику предпочтительно хранить отдельно
  от прежнего контракта либо явно расширить его совместимым способом.
- Хранилище сверяет `turn.answer` с результатом `render_answer`. Если изменить
  renderer отказов, старые сохранённые `unknown` могут перестать читаться.
  Проще добавить обозначение отсутствия источников в представление CLI/веб;
  при изменении сохранённого текста предусмотреть чтение прежнего формата.
- Поле `Turn.memory_updated` уже используется facts/summary. Не подменять его
  смысл автоматически: для новой подготовки нужна однозначная диагностика.
- Не менять `TaskState.from_dict`, граф переходов и правила утверждения плана
  ради свободного диалога. RAG+FSM уже интегрированы.
- Сохранить режим без RAG, мета-промпт, object/schema, работу явной памяти и
  проверку инвариантов. MCP не переносить в новый preparation-вызов.

## 8. Как проверять и что сохранять

### Автоматические проверки без внешнего API

Нужны тесты наблюдаемого поведения, а не повторение реализации:

- Разрешение продолжения и явная смена темы; неизвестный объект не додумывается.
- Обновление/отмена ограничения, защита от фактов ассистента и инструкций чанка.
- Поиск вызывается на каждом новом RAG-ходе; repair не вызывает его повторно.
- Сохранение уточнения при раннем unknown, содержательном unknown и последующей
  ошибке генерации; FSM не продвигается вследствие отказа.
- Память попадает в генератор после обрезки окна и при summary/facts; полная
  история не используется как скрытый обход ограничения окна.
- Перезапуск и изоляция диалогов; совместимость старых JSON, включая unknown.
- Поддельный/старый chunk_id и цитата только из прошлого ответа отклоняются.
- Сбой preparation, невалидный JSON и превышение лимита имеют явный fallback;
  статистика вызовов и исходная реплика сохраняются корректно.
- CLI и веб показывают один сохранённый снимок памяти и источников.
- Режим без RAG, отключённый rewrite и активный FSM сохраняют прежние контракты.

Подставная модель подтверждает сборку и передачу контекста, но не качество
понимания естественного языка. Не называть такие тесты результатом live-сценария.

### Реальный последовательный прогон

Переиспользовать сервис и метрики из `rag_evaluation.py`, но сохранять один
`conversation_id` на весь сценарий. Эталонные ответы, ожидаемые источники и
ожидаемое состояние доступны только проверяющему коду, не модели и не индексу.

В JSON-отчёте фиксировать: коммит приложения, модель и параметры, hash индекса
и корпуса, настройки окна/RAG, исходную реплику, поисковый запрос, диагностику
подготовки, память до/после, фактический ответ, статус, источники/цитаты, время,
токены и ошибки. В человекочитаемом отчёте дать итог по каждому ходу и примеры
проверки после выпадения первой реплики из окна.

| Метрика | Критерий |
|---|---|
| Полнота прогона | Два сценария по 13 ходов; сбои явно отражены, не заменены заглушками |
| Новый поиск | Выполнен на каждом обычном пользовательском RAG-ходе при исправной инфраструктуре |
| Источники для answered | В каждом таком ответе; все ссылки относятся к текущей выдаче |
| Дословность цитат | Все цитаты проходят существующую проверку |
| Unknown | Есть уточняющий вопрос и явное отсутствие подтверждающих источников |
| Удержание цели | Цель сохранена и итоговые ответы соответствуют ей после сокращения окна |
| Уточнения и условия | Нет потерянных действующих ограничений; исправленные значения заменены |
| Перезапуск/изоляция | Состояние восстановилось в том же диалоге и отсутствует в новом |
| Смысл ответа | Вручную проверено, что существенные утверждения следуют из цитат |

Разделять знаменатели: доля ответов с доказательствами среди `answered`, число
обоснованных/необоснованных отказов, число технических ошибок. Система, отвечающая
unknown на всё, не выполнила содержательную часть задания. На заранее выбранных
вопросах с доступным доказательством требуется правильный ответ, иначе исправить
retrieval/контекст и повторить прогон с честным сохранением предыдущего результата.

Достаточно двух итоговых сценариев с включённой памятью. Повтор одного сценария
без неё полезен для демонстрации вклада памяти, но это дополнительный эксперимент.
Сложный LLM-судья и новый набор бенчмарков для дня 25 не обязательны.

## 9. Корпус и воспроизводимость

Текущий корпус — документация самого агента. Изменение `MEMORY.md` и README
меняет предмет справки, поэтому после реализации нельзя молча сравнивать новый
текст с прежним индексом. Зафиксировать используемый снимок, проверить наличие
нужных документов и при необходимости собрать **отдельный** индекс дня 25.
Не перезаписывать пользовательский индекс ради теста без необходимости.

Не включать в корпус планы реализации, тестовые сценарии, эталонные ответы и
отчёты. В предыдущей документации RAG уже отмечен риск попадания проверочных
примеров в индекс; проверить не только список файлов, но и содержимое выбранных
README/инструкций. Иначе ответы могут находиться непосредственно в отчёте теста.

Порог и эмбеддер сначала оставить текущими. Высокий similarity не доказывает
наличие ответа. Замена модели эмбеддингов, новый reranker или гибридный поиск
нужны только при измеренном провале релевантных сценариев и оформляются отдельно.

## 10. Что считать готовым

Работа завершена, когда существующий CLI/веб-чат:

1. Ведёт один сохранённый диалог с актуальной памятью цели/уточнений/условий/терминов.
2. На каждом вопросе ищет документы с учётом разрешённых продолжений и не теряет
   явно новую тему.
3. Сохраняет проверки и представление источников дня 24, включая честный unknown.
4. Удерживает условия после короткого окна и перезапуска; не переносит их в другой диалог.
5. Имеет два выполненных длинных сценария, сохранённые ответы и проверку смысла цитат.

В среде без доступа к модели можно закончить код и локальные тесты, но итоговые
live-сценарии пометить как невыполненные и дать команду запуска. Не объявлять
качество диалога проверенным на основании моков или одного только retrieval.

Не требуется: новый чат, смена UI-фреймворка, замена SQLite, новый MCP для RAG,
обязательное решение моделью «искать или нет», переделка FSM, дообучение модели,
авторизация/деплой/распределённая инфраструктура. Здесь production-like означает
проверяемые контракты, сохранение состояния и понятное поведение при ошибках.

### Почему нельзя считать все чужие отчёты равноценными

- [Отчёт JagArt](https://github.com/JagArt/ai_advent/blob/40c43c1c2580379b5e641b046e37e3dd04f41b95/day25/README.md)
  показывает случай, когда ограничение сохранено и передано, но не соблюдено
  моделью. Проверки одного `state.goal` недостаточно.
- [Отчёт maverixjohn-dot](https://github.com/maverixjohn-dot/AI-Advent-Week5/blob/d886f8551542c3e6612f7c878ff1de7734a834a3/%D0%BE%D1%82%D1%87%D1%91%D1%82.md)
  раскрывает использование подставленных LLM-ответов при сценарной проверке.
  Такой replay полезен для инфраструктуры, но не доказывает качество штатного
  end-to-end чата с моделью.
- [Отчёт Vladislav-Zyuzko](https://github.com/Vladislav-Zyuzko/ai-challenge/blob/f88246b1de4354ca2083b2694f6c4969baa935ce/week5/day25.md)
  фиксирует retrieval/источники на 27 из 28 ходов и дословность 255 из 463 цитат.
  Пример не заменяет наши более строгие гарантии источников.
- [Результаты MariaAgafonova](https://github.com/MariaAgafonova/advent-day-25-rag-memory/blob/e25a2cf6047e26492649a826917b8103daa5d371/DAY25_RESULTS.md)
  сообщают об успешных mock/live-сценариях, но полные live-логи не опубликованы,
  а после последней правки длинный live-прогон не повторялся. Успех следует
  относить к заявленному прогону, а не автоматически к любому последующему коммиту.
- В [решении resokk](https://github.com/resokk/ai_challenge/blob/60accf5cfe5447e5684adfa3fc34ca2d134abcd4/day_25/README.md)
  наличие показанных источников и нахождение правильного источника дают разные
  результаты. Показ ближайших чанков при отказе не равен доказательству ответа.

Общий вывод из сравнения: **повторно использовать дни 22–24, связать компактную
память с поиском и генерацией и измерить поведение в длинном разговоре**.
Количество новых файлов, размер UI и сложность поискового pipeline не являются
критериями выполнения задания.
