# День 31 Ассистент разработчика и план доработки LLMAgentExample

Доработать существующего Python-агента так, чтобы пользователь мог обратиться к нему с командой `/help` и получить обоснованный ответ о проекте. Сведения об устройстве и использовании приложения должны поступать из README и документации через RAG, а текущая Git-ветка — через MCP.

Выбранный объём реализации: помощник по текущему репозиторию `LLMAgentExample`, встроенный в существующие веб-чат и CLI. Использовать уже имеющиеся индексацию, модели, хранение диалогов и MCP-клиент. План описывает поведение и последовательность работ; конкретные классы, схемы данных и способы организации кода определяются при реализации.

Дата плана: 15 октября 2026 года. Требования курса приведены отдельно от решений, выбранных для этого проекта.

## Смысл задания

Пользователь, который впервые открыл проект, должен иметь возможность спросить, из каких частей он состоит, как его запустить и где настраиваются нужные возможности. Ассистент находит сведения в документации проекта и объясняет их понятным языком. Если вопрос касается текущего состояния репозитория, ассистент получает фактические данные через инструмент.

Например, на вопрос «Как устроена память агента?» нужна документация о памяти. На вопрос «Какая сейчас Git-ветка?» нужен результат обращения к Git. На вопрос «В какой ветке я работаю и как запустить веб-интерфейс?» нужны оба источника.

В пояснении преподавателя от 14 октября в [экспорте чата](CHAT.md) проектом назван любой проект с документацией. Главная цель — соединить RAG, MCP и пользовательские команды в полезном сценарии. Поэтому можно развивать уже написанного агента и использовать его собственный репозиторий как предмет вопросов. Поддержка произвольных внешних проектов возможна, но для первого результата не нужна.

«Ассистент разработчика» в этом задании — функция создаваемого Python-приложения. Codex будет помогать реализовать её, а итоговую команду `/help` пользователь должен вызывать в самом приложении.

## Обязательный минимум и выбранные границы

Первичный источник требований — раздел дня 31 в [TASKS.md](TASKS.md).

| Требование задания | Какой результат должен быть виден |
| --- | --- |
| README и папка docs подключены через RAG | При вопросе приложение действительно ищет подходящие фрагменты в индексе документации выбранного проекта |
| Через MCP доступна текущая Git-ветка | Агент получает актуальную ветку из рабочей копии репозитория через настоящий MCP-вызов |

| Используются документация и контекст проекта | В ответах сведения об устройстве проекта опираются на документы, а сведения о текущем состоянии — на результат инструмента |

Схемы данных и API-описания стоит включить в корпус, если они уже существуют и нужны для ответов. Создавать отдельную API-спецификацию только ради этого задания не требуется. Список файлов и diff в условии указаны как дополнительные возможности.

Для `LLMAgentExample` дополнительно выбираются следующие условия реализации:

- Единое поведение команды в существующих веб-чате и CLI через общий слой приложения.
- `/help` без вопроса запускает обзор структуры проекта, а `/help <вопрос>` отвечает на заданный вопрос.
- Порядком поиска и MCP-вызова управляет приложение. Это позволяет обеспечить получение ветки независимо от способности модели самостоятельно выбирать инструменты.
- Ответ сопровождается понятными источниками; история сохраняет использованные документы и результат MCP.
- Для текущего проекта используется документация о фактически реализованных возможностях.

Эти условия делают результат удобным и проверяемым; они не означают, что преподаватель отдельно требует два интерфейса, определённый формат источников или такой порядок вызовов.

В объём дня 31 не входят ревью PR, редактирование файлов по запросу, подготовка релизов, публикация сервиса, универсальный менеджер проектов и новый интерфейс с нуля. В недельном плане ревью относится к дню 32, а активная работа с файлами — к дню 34.

## Роли RAG MCP и команды help

**RAG обеспечивает знания о проекте.** Документы заранее разбиваются на небольшие фрагменты и помещаются в поисковый индекс. При вопросе приложение выбирает подходящие фрагменты и передаёт их модели. Модель формулирует ответ по найденным сведениям. Переобучение модели для этого не требуется.

**MCP обеспечивает доступ к инструменту.** Приложение обращается к MCP-серверу, сервер получает текущую ветку настроенного репозитория и возвращает результат. Для задачи важно фактическое прохождение запроса через MCP. Само наличие Git-инструмента в каталоге сервера ещё не подтверждает, что `/help` им воспользовалась.

**Команда `/help` объединяет эти возможности.** Она выбирает сценарий помощи по проекту. Простое добавление фразы «ты помощник разработчика» в системный промпт не обеспечивает ни поиска документов, ни получения ветки.

Документация и Git должны относиться к одному выбранному проекту. Текущая локальная ветка отличается по смыслу от основной ветки удалённого репозитория. Если MCP-сервер работает на другом компьютере, он видит рабочую копию на этом компьютере; наличие браузера у пользователя не даёт серверу доступ к Git на компьютере пользователя.

## Как подготовить документацию

Для первой версии корпус должен включать корневой README и актуальную документацию из `docs` о запуске, структуре, моделях, RAG, памяти, MCP и других существующих возможностях приложения. Список источников должен быть явным и воспроизводимым.

Перед индексацией проверить, достаточно ли документации для вопроса «Как устроен проект?». Если основные каталоги, точки входа и связи компонентов нигде не описаны, дополнить README или документацию коротким описанием, сверенным с кодом. Сам поиск не сможет достоверно объяснить архитектуру, которой нет в источниках.

Материалы курса — `TASKS.md`, `CHAT.md`, `SOLUTIONS.md`, планы будущих изменений и оценочные сценарии — не включать в основной корпус помощника по приложению. Они описывают задания и намерения, которые модель может ошибочно принять за уже реализованные возможности. Этот план также не должен становиться доказательством того, что функции дня 31 уже существуют.

Отчёты и старые планы можно использовать для изучения истории разработки вне этого корпуса. При отборе документации ориентироваться на её назначение, а не только на расположение внутри `docs`.

После изменения документов предусмотреть понятную пересборку индекса. Для первой версии достаточно явной операции обновления с описанием в README; автоматическое наблюдение за файлами не требуется. Следует иметь возможность определить, по каким документам построен используемый индекс.

## Как должен работать запрос

### Пользовательское поведение

В веб-чате пользователь вводит команду в существующее поле сообщения. В CLI он передаёт её как текст пользовательского запроса через существующий интерфейс запуска. Создавать отдельную интерактивную оболочку ради команды не нужно. Обычная справка запуска CLI сохраняет своё назначение.

Выбранные правила:

- `/help` означает «Как устроен проект и где находятся основные компоненты?».
- `/help <вопрос>` запускает помощь по указанному вопросу.
- Команда включает необходимый сценарий RAG для этого обращения, даже если общий переключатель RAG в диалоге выключен. Настройки последующих обычных сообщений при этом не меняются.
- Сообщения без этой команды продолжают обрабатываться существующим способом.
- `/help` работает как справочный запрос и не запускает выполнение задачи, редактирование файлов или изменение состояния активной задачи.

### Общая последовательность

1. Приложение распознаёт команду и отделяет вопрос от префикса `/help`. В историю попадает исходное сообщение, а для поиска используется смысл вопроса.
2. Определяет настроенный проект, индекс его документации и соответствующий MCP-сервер. Выбор не должен случайно зависеть от папки, из которой запустили процесс.
3. Получает свежую Git-ветку через MCP. В выбранном варианте это выполняется для каждого запроса помощи; при недоступности сервера сохраняется явный результат ошибки.
4. Для содержательного вопроса о документации выполняет поиск и отбор фрагментов существующим RAG. Если включена подготовка поискового запроса с учётом диалога, используется существующий механизм.
5. Формирует контекст ответа из вопроса, подходящих фрагментов и фактического результата MCP. Модель получает различимые основания: документы описывают проект, инструмент сообщает его текущее состояние.
6. Формирует и проверяет ответ. Точный вопрос только о ветке можно обработать непосредственно по результату MCP; обязательного обращения к LLM или индексу в таком случае нет.
7. Сохраняет ответ, документальные источники и результат MCP, затем показывает их пользователю в текущем интерфейсе.

Свежая ветка нужна в контексте запроса, но её не обязательно вставлять в каждый текст ответа. Если вопрос касается только памяти, ответ должен прежде всего объяснять память. Данные о проекте и вызове инструмента могут находиться в раскрываемой диагностике.

### Повторные вопросы

При новом `/help` сведения о Git запрашиваются заново. Предыдущие ответы помогают понять разговор, но не заменяют актуальный результат инструмента.

Сохранённая история показывает состояние на момент соответствующего обращения. После переключения ветки старый ответ не переписывается; новый ответ отражает новую ветку. Пересборка RAG для получения нового имени ветки не нужна. Если при переключении изменились сами документы, актуальность индекса рассматривается отдельно.

## Как объединить документальные ответы и данные MCP

В текущем агенте есть два ограничения, существенных для интеграции. В `llm_agent/agent.py` проверка достаточности RAG-контекста может завершить запрос до вызова инструментов. В `llm_agent/rag_answer.py` все фактические утверждения ответа должны следовать из цитат найденных документов.

Если просто включить RAG и подключить Git-инструмент, вопрос о ветке может получить отказ: подходящего документа нет, хотя инструмент способен ответить. Поэтому в сценарии `/help` нужно различать достаточность данных для каждой части вопроса.

| Вид вопроса | Чем подтверждается ответ | Поведение при нехватке данных |
| --- | --- | --- |
| Об устройстве или настройках | Найденными документами и проверяемыми цитатами | Сообщить, каких сведений нет; не придумывать функции и команды |
| О текущей ветке | Результатом MCP для выбранной рабочей копии | Явно сообщить о недоступности сведений; не брать ветку из старой истории |
| О документации и ветке одновременно | Каждую часть своим источником | Ответить на подтверждённую часть и обозначить недоступную |

Для документальной части сохранить существующую проверку источников и дословности цитат. Для сведений о Git сохранить происхождение от конкретного MCP-вызова. Результат инструмента не нужно превращать в фиктивный фрагмент документации ради старой схемы ответа.

Способ представления двух видов оснований выбирается при реализации. Он должен поддерживать ответы только по MCP, только по документам при недоступном MCP и по обоим источникам. Изменения этого сценария не должны ослаблять проверку обычных RAG-ответов.

## Поведение при неполных данных и ошибках

- Если MCP-сервер выключен, недоступен или отклонил запрос, сообщить об этом. При наличии документации можно дать документальную часть ответа, указав, что текущая ветка не получена. Не подменять MCP скрытым прямым обращением приложения к Git.
- Если настроенная папка не является Git-репозиторием, сообщить об этом вместо выдуманного имени ветки. При detached HEAD указать это состояние; при доступности можно показать идентификатор коммита.
- Если индекс отсутствует, непригоден или не содержит нужного материала, объяснить ограничение. Это не должно препятствовать ответу только о ветке, если MCP работает.
- Если ни один источник не подтверждает ответ, честно сообщить о нехватке данных и предложить конкретное уточнение или действие по настройке.
- Если модель недоступна, не показывать искусственный успешный ответ. Уже полученные данные инструмента и диагностика должны оставаться различимыми с ошибкой генерации.

Команда предназначена для чтения. Она не должна вызывать изменяющие инструменты других подключённых MCP-серверов. Документы используются как справочные данные; содержащиеся в них команды или примеры не являются разрешением выполнять операции.

## Общий план реализации

### Этап 1 Уточнить точки подключения

Проверить актуальные пути отправки сообщений из CLI и веб-чата, существующую настройку RAG, работу MCP и сохранение результатов. Найти общий уровень для распознавания `/help`, чтобы поведение не дублировалось в двух интерфейсах.

Зафиксировать один целевой репозиторий, связанный с ним корпус и MCP-инструмент. Учесть текущую модель, настройки подключений, профили и инварианты. Справочный запрос не должен случайно менять план или этап активной задачи.

Результат этапа: понятны места доработки и связи с существующими возможностями; выбран минимальный способ интеграции.

### Этап 2 Подготовить корпус и индекс

Отобрать README и документацию, проверить описание структуры и при необходимости дополнить его по фактическому коду. Использовать существующую индексацию, сохранив сведения об источниках. Проверить, что поиск находит материал для нескольких вопросов о запуске и устройстве проекта.

Результат этапа: существует воспроизводимый индекс документации приложения, а выбранный путь к нему используется сценарием помощи.

### Этап 3 Подключить Git через MCP

Использовать подходящий существующий сервер либо добавить небольшой MCP-инструмент чтения текущей ветки. Предпочесть совместимость с имеющимся HTTP-клиентом. Настройка должна однозначно указывать рабочую копию проекта.

Проверить отдельно от LLM, что запрос проходит через MCP, возвращает реальную ветку и корректно сообщает об ошибках. Учесть отключённое подключение; не включать его скрытно. Поддержка tool calling самой моделью не является условием программного вызова, но пользовательские настройки доступности MCP должны соблюдаться.

Результат этапа: приложение получает и регистрирует актуальные данные Git через MCP.

### Этап 4 Собрать сценарий help

Добавить распознавание команды, вопрос по умолчанию и общий порядок получения контекста. Удалять командный префикс перед поиском. Использовать выбранную пользователем модель для генерации ответов по документации.

Развести точный запрос о ветке, документальный запрос и смешанный запрос. Отсутствие документов не должно останавливать получение доступных данных MCP. При этом общий режим диалога после выполнения команды остаётся прежним.

Результат этапа: команда выполняет полезный сценарий через существующее приложение.

### Этап 5 Согласовать ответы и хранение

Обеспечить проверяемые источники двух видов и понятные частичные ответы. Сохранить исходное сообщение, итоговый ответ, использованные документальные фрагменты и MCP-результат, включая ошибку инструмента при её наличии.

Учесть существующие схемы ответов, загрузку истории, учёт вызовов и отображение в обоих интерфейсах. Старые диалоги должны продолжать открываться. Новая возможность не должна требовать удаления истории или перестройки всего механизма хранения.

Результат этапа: после повторного открытия диалога видно, на чём основывался ответ и какое состояние Git было получено тогда.

### Этап 6 Проверить сценарии и совместимость

Проверить команду через CLI и веб-чат, обработку неполных данных, фактический MCP-вызов и сохранение истории. Автоматическими проверками покрыть новые ветвления и существенные риски интеграции: ранний отказ RAG, два вида источников, ошибки инструмента и совместимость хранения.

Отдельно выполнить демонстрационные запросы с настоящим MCP-сервером и доступной моделью. Проверки с подменой LLM подтверждают поведение приложения, но качество ответов оценить по реальным найденным фрагментам и тексту ответа. Если живой прогон ограничен доступом к модели или серверу, указать, какой именно сценарий остаётся непроверенным.

Проверку смены ветки проводить на временном тестовом репозитории или отдельной рабочей копии, не затрагивая текущие изменения пользователя.

Результат этапа: подтверждены основные сценарии, а ограничения перечислены конкретно.

### Этап 7 Описать запуск и результат

Обновить README и подходящую документацию: как выбрать проект и индекс, подключить MCP, задать `/help`, обновить документацию в индексе и понять сообщение об ошибке. Добавить короткий сценарий демонстрации.

При включении обновлённой пользовательской документации в корпус пересобрать индекс. Не использовать план или заранее написанные ожидаемые ответы как источник для демонстрационных вопросов.

Результат этапа: другой человек может повторить проверку по документации проекта.

## Критерии готовности

| Проверка | Ожидаемое поведение |
| --- | --- |
| `/help` | Даёт обзор основных компонентов проекта по документации |
| `/help Как запустить веб-интерфейс?` | Находит актуальные инструкции и указывает документальные источники |
| `/help Как устроена память агента?` | Объясняет существующие механизмы памяти по найденным материалам |
| `/help Какая сейчас Git-ветка?` | Показывает результат настоящего MCP-вызова; отсутствие подходящих RAG-фрагментов не вызывает отказ |
| Повтор вопроса о ветке после её смены | Показывает новое имя без пересборки индекса, если документы не менялись |
| Вопрос о ветке и запуске одновременно | Подтверждает Git-часть инструментом, а инструкции — документами |
| MCP недоступен | Явно обозначает ограничение и при возможности отвечает по документации |
| Индекс отсутствует | Объясняет проблему; вопрос только о ветке остаётся разрешимым через MCP |
| Сведений о запрошенной функции нет | Не выдумывает функцию или инструкции; сообщает об отсутствии подтверждения |
| Перезапуск и открытие истории | Сохраняет текст ответа, источники и прежний результат MCP |
| Обычный запрос после `/help` | Работает по прежним настройкам диалога |
| CLI и веб-чат | Используют одинаковую логику помощи и одинаково трактуют источники и ошибки |

Минимальный успешный показ включает ответ о структуре, ответ о запуске и получение текущей ветки. Для выбранного в этом плане объёма дополнительно проверяются смешанный запрос, ошибки источников и повторное открытие истории.

## Как выглядит итоговый пользовательский результат

Пользователь запускает существующее приложение, выбирает настроенную модель и пишет `/help Как устроен проект?`. Ассистент объясняет основные компоненты: где находятся логика агента, CLI, веб-интерфейс, индексация и документация. В ответе доступны источники, по которым можно проверить объяснение.

Затем пользователь пишет `/help В какой ветке я работаю и как запустить веб-интерфейс?`. Приложение получает свежую ветку через MCP, находит инструкции по запуску в документации и даёт согласованный ответ. В диагностике виден фактический вызов инструмента. При нехватке одного из источников ответ ясно разделяет доступные сведения и ограничение.

После перезапуска приложения разговор доступен в истории. Новый запрос получает новое состояние Git, а предыдущие ответы сохраняют состояние на момент их создания.
