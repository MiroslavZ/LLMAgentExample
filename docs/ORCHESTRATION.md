# Оркестрация MCP — день 20

Агент работает с любым набором подключённых MCP-серверов через обычный запрос
в чате или CLI. Модель выбирает инструменты из общего каталога по их описаниям
и определяет последовательность действий по запросу пользователя.
Агент связывает каждое имя функции с конкретным сервером, проверяет аргументы,
выполняет вызов и передаёт результат модели для выбора следующего шага.
Список серверов задаётся настройками подключения. В качестве демонстрации ниже
используется цепочка **GitHub → NIST NVD → Telegram** для нескольких проектов.

## Запуск серверов демонстрационного примера

Из корня проекта запустите три команды в отдельных терминалах. В этом проекте
у каждого сервера уже есть своё окружение; для новых окружений установите
зависимости из `requirements.txt` соответствующего сервера.

```powershell
.\MCPServerExample\venv\Scripts\python.exe -m MCPServerExample.server
.\VulnSearchMCPServerExample\venv\Scripts\python.exe -m VulnSearchMCPServerExample.server
.\TelegramMCPServerExample\venv\Scripts\python.exe -m TelegramMCPServerExample.server
```

| Сервер | Endpoint | Инструмент сценария | Серверный `.env` |
| --- | --- | --- | --- |
| GitHub | `http://127.0.0.1:8000/mcp` | `get_repository(owner, repo)` | `GITHUB_TOKEN` |
| NIST NVD | `http://127.0.0.1:8001/mcp` | `search_vulnerabilities(project_name, limit=5)` | `NIST_API_TOKEN` |
| Telegram | `http://127.0.0.1:8002/mcp` | `send_message(text)` | `API_TOKEN`, `CHAT_ID` |

Существующие `.env` сохраняются. Токены внешних сервисов остаются на их серверах;
модель не получает токен Telegram или ID чата. Для личного чата пользователь
должен предварительно начать диалог с ботом. Каждый сервер содержит собственный
`http_server.py` с HTTP-транспортом и авторизацией. Для переноса в отдельный
репозиторий достаточно его директории; файлы из корня проекта агента не нужны.
Из директории сервера можно запускать `python server.py`.

Запустите веб-приложение:

```powershell
.\venv\Scripts\python.exe -m llm_agent.web
```

В панели **MCP → Добавить MCP** зарегистрируйте нужные серверы: укажите название,
URL, при необходимости имя переменной с MCP-токеном, включите **Использовать в чате**
и сохраните. Через **Get tools** можно проверить каталог каждого сервера.
Для примера выше добавьте три адреса из таблицы; для других задач подключите
соответствующие MCP-серверы тем же способом.

Настройки общие для CLI и веба (`data/conversations/mcp.sqlite3`). Если используете
`--data-dir`, задавайте один каталог обоим интерфейсам. Регистрация не запускает
процессы серверов. Если изменены порты или включена авторизация MCP, отредактируйте
URL и имя переменной с MCP-токеном в панели. Для разных серверов можно использовать
разные переменные окружения. `MCP_ACCESS_TOKEN` не связан с NIST/GitHub/Telegram
API-ключами; по умолчанию доступ без него разрешён только на loopback.

## Демонстрационный запрос

В обычном чате, без режима задачи с утверждением плана:

> Собери отчёт о проектах https://github.com/pytorch/pytorch и
> https://github.com/microsoft/vscode. Сначала получи через GitHub общую информацию
> о каждом: название, описание, язык, число звёзд и ссылку. Затем через NIST найди
> по 5 первых уязвимостей для PyTorch и Visual Studio Code. Для каждой укажи CVE,
> краткое описание, CVSS и ссылку NVD; если совпадений нет, явно это напиши.
> Поиск по имени не подтверждает уязвимость конкретной версии. После проверки
> обоих проектов отправь единый отчёт мне в настроенный Telegram-чат. Если поиск
> завершился ошибкой, не выдавай её за отсутствие CVE: отметь неполную проверку.
> В конце сообщи результат отправки.

После настройки подключений отправьте обычный запрос из CLI:

```powershell
.\venv\Scripts\python.exe -m llm_agent --user "Получи через GitHub сведения о https://github.com/pytorch/pytorch и https://github.com/microsoft/vscode. Затем через NIST найди по 5 CVE для PyTorch и Visual Studio Code с описаниями, CVSS и ссылками. Отправь общий отчёт в Telegram и сообщи результат отправки."
```

Ожидаемый логический порядок: сведения о проектах → поиски NVD → общий отчёт
в Telegram → итог. Независимые чтения GitHub могут быть предложены моделью
в одном раунде; зависимые вызовы выполняются после получения источника.
Журнал веб-чата и CLI содержит номер, сервер, инструмент, аргументы, результат
и статус каждого вызова и сохраняется вместе с диалогом.

## Передача данных и ограничения

Вызовы всех серверов используют один кэш результатов текущего запроса. Например,
если название репозитория совпадает с названием продукта:

```json
{"project_name": {"$mcp_result": "call_repository", "pointer": "/data/name"}, "limit": 5}
```

Для `microsoft/vscode` модель выбирает полное название `Visual Studio Code`
по сведениям о продукте. `$mcp_result` берётся из фактического `result_ref`,
а не из приведённого примера. Агент подставляет данные до проверки исходной
схемы сервера. Ссылки на ошибочные результаты или ещё не завершённые вызовы
не допускаются. Полные результаты доступны по ссылке независимо от preview.

Поиск NVD возвращает до 5–10 первых CVE в порядке API, включая ID, описание,
CVSS, даты и ссылку. Это поиск по ключевым словам, без проверки CPE или установленной
версии. `no_results` означает отсутствие совпадений; сбои сети, квоты и ключа —
ошибки инструмента. NVD вызывается последовательно, с ограничением времени.

Telegram принимает полный текст, автоматически разбивает длинный отчёт и
возвращает подтверждённые `message_ids`. Частичная доставка и неопределённый
результат являются ошибками MCP с сохранением известных ID; автоматических
повторов отправки нет. Статус `sent` появляется только после подтверждения всех
частей. Подробности: [NIST](VulnSearchMCPServerExample/README.md),
[Telegram](TelegramMCPServerExample/README.md).

На запрос допускается 16 раундов и 40 вызовов инструментов. JSON аргументов
одного вызова ограничен 64 000 символами; для передачи более длинного готового
результата используйте `$mcp_result` (общий предел передачи — 1 000 000 символов).
При достижении
лимита модель получает указание завершить ответ и отметить невыполненные шаги.
Порядок выбирает модель по описаниям и системным правилам; семантическую
правильность произвольного плана маршрутизатор не доказывает.

## Проверка

После установки корневого `requirements.txt`:

```powershell
.\venv\Scripts\python.exe -m unittest tests.test_nist_server tests.test_telegram_server tests.test_mcp_orchestration_integration -v
.\venv\Scripts\python.exe -m unittest discover -s tests -q
```

Сквозной тест запускает три настоящих HTTP MCP-сервера с разными Bearer-токенами,
делает discovery и исполняет 7 последовательных вызовов в 8 раундах модели:
три чтения GitHub, три поиска NVD и отправку в Telegram. Проверяются маршрутизация,
аргументы, ссылки на предыдущие результаты, текст отчёта и восстановление журнала.
Дополнительные сценарии проверяют ошибку NVD и частичную доставку Telegram.
Внешние API и LLM заменены тестовыми ответами: тесты не отправляют реальные сообщения.
Самостоятельный выбор инструментов реальной моделью проверяется запросом выше.
