# Помощь разработчику — команда /help

В существующем веб-чате введите `/help` для обзора структуры проекта или
`/help Как запустить веб-интерфейс?` для конкретного вопроса. Та же команда
доступна в CLI как текст `--user`. Выберите модель в каталоге приложения;
для ответа и выбора инструментов используется именно её подключение.

## Документация проекта

Общий для RAG и `/help` список источников находится в `examples/indexing/corpus.json`:
корневой README и руководства `docs/` по структуре, запуску, моделям, памяти,
задачам, инвариантам, RAG и MCP. Учебные TASKS/CHAT/SOLUTIONS/LECTURE,
планы, результаты экспериментов и оценочные сценарии в корпус не входят.
Описание Python-схем данных и API находится в `docs/PROJECT_STRUCTURE.md`.

Из корня проекта, в основном окружении агента:

```powershell
.\venv\Scripts\python.exe -m llm_agent.indexing build --strategy structural --model intfloat/multilingual-e5-base --cache-dir data/model-cache
```

Первая сборка скачивает embedding-модель. Для уже заполненного кэша добавьте
`--offline`. Чтобы воспроизвести конкретную модель, задайте `--revision` с SHA
из метаданных индекса. SQLite-индекс хранит снимки документов, хеш корпуса,
чанки и параметры embedding-модели. Просмотр и проверка:

```powershell
python -m llm_agent.indexing stats --strategy structural
python -m llm_agent.indexing verify --strategy structural
python -m llm_agent.indexing search "Как устроен проект?" --strategy structural --cache-dir data/model-cache --offline
```

Добавьте в корневой `.env`:

```dotenv
RAG_CACHE_DIR=data/model-cache
```

Обычный RAG и `/help` используют один индекс и один экземпляр поискового сервиса
с общей embedding-моделью в памяти. По умолчанию это `data/indexes/structural.sqlite3`.
`RAG_INDEX_PATH` задаёт путь для обоих сценариев. Относительный путь индекса
считается от корня проекта, а не от текущего каталога процесса.
Если настроен другой путь, при сборке укажите соответствующий `--output-dir`.

После изменения README, включённого документа или списка источников повторите
команду `build`: поиск использует сохранённый снимок документов и сам не обновляет
его при редактировании файлов. Пересборка атомарна, новый индекс виден обоим
сценариям со следующего запроса. При изменении `.env` перезапустите приложение.

## Подключение Git через MCP

В отдельном терминале запустите сервер:

```powershell
.\LocalMCPServer\venv\Scripts\python.exe LocalMCPServer/server.py
```

Он обслуживает текущий репозиторий на `http://127.0.0.1:8001/mcp` через
Streamable HTTP. Инструмент `git_branch` читает имя ветки и коммит без изменения
репозитория; в detached HEAD возвращает коммит и отсутствие именованной ветки.
В новом репозитории без коммитов доступно имя ветки. Путь проекта задан серверу
при запуске и не принимается от модели. Подробнее: `LocalMCPServer/README.md`.

В веб-интерфейсе откройте **MCP**, добавьте этот URL, оставьте поле токена пустым,
включите **Использовать в чате** и сохраните. **Get tools** проверяет подключение.
Либо сохраните общее подключение через CLI:

```powershell
python main.py --new-conversation --mcp-url http://127.0.0.1:8001/mcp
```

Команда создаёт пустой диалог и печатает его ID. Подключение сохраняется с ID `cli`: если оно уже есть,
оно будет обновлено. Чтобы сохранить другой сервер с этим ID, добавьте локальный
сервер через веб-менеджер. Достаточно одного включённого подключения к URL проекта.
Для другого порта задайте `PROJECT_HELP_MCP_URL` в `.env`, измените URL подключения
и запустите сервер с соответствующим `--port`.

Для вопросов о текущей ветке выберите модель с поддержкой tool calling и включите
инструменты в её настройках. В `/help` модели доступен только `git_branch`
настроенного проектного сервера. Она сама решает по смыслу вопроса, нужен ли вызов;
принудительного запроса ветки перед ответом нет. Вопросы о структуре, запуске
и настройках проекта должны обходиться документацией, без MCP-вызовов.

Отключённый сервер не вызывается и не включается автоматически. Описание известного
инструмента доступно локально: сетевое соединение устанавливается только при выборе
вызова моделью. Корень репозитория в результате MCP проверяется: сведения другого
проекта не используются. Выполненный вызов сохраняется до следующего ответа модели,
включая случаи сбоя при формировании финального ответа.

## Поведение команды и история

- `/help` ищет сведения о структуре и основных компонентах.
- `/help Какая сейчас Git-ветка?` позволяет модели запросить `git_branch` и ответить
  по его результату. Отсутствие релевантных документов не блокирует этот вызов.
- `/help В какой ветке я работаю и как запустить веб-интерфейс?` объединяет сведения
  из документов с результатом выбранного моделью вызова MCP. Имя ветки берётся
  из проверенного результата инструмента.
- Общий RAG можно оставить выключенным: команда включает поиск только для своего
  хода. Она использует параметры top-K, порога и rewrite текущего диалога.
- Мета-промпт для `/help` не применяется. Команда не продвигает этапы задачи,
  работает при её паузе и не запускает изменяющие инструменты.
- Документальная часть проходит существующую проверку JSON, источников и дословных
  цитат. После успешного вызова Git выводится отдельно с пометкой
  **Источник Git: MCP / git_branch**. Без вызова блок Git не добавляется.

После перезапуска в истории остаются исходная команда, ответ, найденные фрагменты,
цитаты и результаты действительно выполненных вызовов MCP. История показывает
ветку на момент вызова; для нового вопроса о текущей ветке модель должна запросить
свежее значение. Последующие обычные сообщения используют прежние настройки диалога.

При недоступности MCP ответ по документации остаётся доступен. Ошибка получения Git
выводится только после попытки вызова. При отключённых инструментах или отсутствии
подключения модель сообщает, что не может получить текущую ветку; фиктивный вызов
в журнал не записывается. При отсутствии или повреждении индекса выводится инструкция
по пересборке; модель по-прежнему может вызвать Git. Если документов недостаточно
для документальной части вопроса, ассистент сообщает об этом. При ошибке модели ход
отмечается ошибкой/частичным результатом; ранее выполненные вызовы доступны в журнале.

## Сценарий демонстрации

После сборки индекса, подключения MCP и выбора модели выполните в одном чате:

```text
/help
/help Как запустить веб-интерфейс?
/help Как устроена память агента?
/help Какая сейчас Git-ветка?
/help В какой ветке я работаю и как запустить веб-интерфейс?
```

У первых трёх запросов проверьте источники и цитаты без вызова `git_branch`;
у последних двух — запись вызова в журнале и актуальную ветку. Перезапустите
приложение и откройте историю. Отключение MCP не должно мешать вопросам по документам.
Проверку смены ветки и detached HEAD выполняют на временном репозитории тесты
`tests/test_project_mcp_server.py`, без переключения рабочей ветки проекта.
