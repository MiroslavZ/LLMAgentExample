# Структура проекта LLMAgentExample

LLMAgentExample — ИИ-агент на Python с консольным интерфейсом и веб-чатом
на NiceGUI. Для генерации ответов используется OpenAI-совместимый API;
локальные и облачные модели задаются в общем каталоге подключений.
Агент поддерживает историю диалогов, память, профили, контролируемое состояние
задачи, инварианты, инструменты MCP и RAG по локальному индексу документов.

## Каталоги и точки входа

| Путь | Назначение |
|---|---|
| `main.py` | Точка входа консольного клиента; вызывает `llm_agent.cli.run`. |
| `llm_agent/__main__.py` | Та же CLI-команда через `python -m llm_agent`. |
| `llm_agent/` | Ядро агента, общий сервис диалогов, модели данных, хранилища, RAG и MCP-клиент. |
| `llm_agent/web/` | Веб-интерфейс NiceGUI и выполнение запросов вне потока UI. |
| `llm_agent/indexing/` | Самостоятельный CLI загрузки документов, разбиения, эмбеддингов, поиска и проверки индексов. |
| `LocalMCPServer/` | Отдельный локальный MCP-сервер проекта со своими зависимостями и виртуальным окружением. |
| `docs/` | Руководства по возможностям, описание архитектуры, учебные задания, планы и отчёты. |
| `examples/` | Примеры профилей, инвариантов, манифесты корпуса и вопросы для проверки RAG. |
| `tests/` | Автоматические проверки на `unittest`. |
| `data/` | Локальные данные диалогов, SQLite-индексы, кэш embedding-моделей и результаты проверок. |
| `requirements.txt` | Зависимости основного Python-приложения. |

## Запуск CLI и веб-чата

Все команды ниже выполняются из корня репозитория с установленными зависимостями.
В Windows существующее окружение можно использовать без активации:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
.\venv\Scripts\python.exe -m llm_agent --help
.\venv\Scripts\python.exe -m llm_agent.web
```

Веб-чат по умолчанию доступен по адресу `http://127.0.0.1:8080`.
Аргументы веб-сервера: `--host`, `--port`, `--data-dir`,
`--invariants-file` и `--no-browser`. Например:

```powershell
.\venv\Scripts\python.exe -m llm_agent.web --port 8081 --no-browser
```

Перед отправкой сообщения добавьте и выберите модель в менеджере моделей
веб-чата либо через CLI. Каталог при первом запуске пустой; наличие ключа
в `.env` само по себе не создаёт подключение. Пример CLI после добавления модели:

```shell
python -m llm_agent --models-list
python main.py --new-conversation --model MODEL_RECORD_ID --user "Привет"
python -m llm_agent --conversation ID --user "Продолжим"
```

`MODEL_RECORD_ID` и `ID` заменяются идентификаторами модели и диалога.
`python main.py` и `python -m llm_agent` используют один CLI.
Подключения и настройки выбора модели описаны в [LLM_MODELS.md](LLM_MODELS.md).

## Обработка сообщения и основные модули

CLI и веб-интерфейс используют общий `ConversationService` из
`llm_agent/service.py`. Сервис управляет диалогами, выбирает сохранённую модель,
загружает память и профиль, подготавливает RAG-контекст и создаёт `Agent`.
Он также координирует сохранение результата и защищает диалог от одновременных
изменений. Веб-обработчик запускает синхронную работу сервиса вне потока UI.

| Модуль | Ответственность |
|---|---|
| `llm_agent/cli.py` | Аргументы терминала, отправка сообщений, управление диалогами и вывод результата. |
| `llm_agent/agent.py` | Вызовы LLM, сборка контекста, шаги задачи, проверки правил и цикл вызовов инструментов. |
| `llm_agent/llm_client.py` | Настройки подключения к OpenAI-совместимому API. |
| `llm_agent/llm_models.py` | Каталог моделей, параметры подключений и получение доступных моделей с сервера. |
| `llm_agent/history.py` | Рабочий контекст истории, сжатие, факты и статистика использования токенов. |
| `llm_agent/context_strategy.py` | Стратегии ограничения окна контекста и хранения фактов. |
| `llm_agent/storage.py` | Чтение и атомарное сохранение JSON диалогов, проверка сохранённых данных и блокировки. |
| `llm_agent/memory.py` | Явная рабочая и долговременная память в SQLite. |
| `llm_agent/profile.py` | Профили персонализации и их выбор для диалогов. |
| `llm_agent/task_state.py` | Состояние задачи и проверка допустимых переходов между этапами. |
| `llm_agent/invariants.py` | Общие правила проекта, их хранение и проверка. |
| `llm_agent/web/app.py` | Создание приложения NiceGUI и маршрут веб-чата `/`. |
| `llm_agent/web/page.py` | Страница чата, диалоги, сообщения и настройки. |
| `llm_agent/web/jobs.py` | Запуск фоновых запросов из интерфейса. |

## RAG и индексация документации

Индексатор отделён от генерации ответа. `llm_agent/indexing/chunking.py`
читает явный JSON-манифест с массивом `files` и разбивает Markdown/TXT
на фрагменты. `embeddings.py` вычисляет локальные эмбеддинги.
`store.py` хранит документы, фрагменты, векторы и метаданные в SQLite,
а `pipeline.py` объединяет сборку и сравнение стратегий разбиения.

`llm_agent/rag.py` содержит `Retriever`: он загружает готовый индекс,
лениво инициализирует embedding-модель, выполняет векторный поиск и фильтрацию.
`rag_dialogue.py` подготавливает самостоятельный поисковый вопрос и память
диалога. `rag_answer.py` проверяет источники и цитаты ответа;
`rag_validation.py` проверяет сохранённый поисковый контекст.

Общий RAG по умолчанию читает `data/indexes/structural.sqlite3`.
Путь меняется через `RAG_INDEX_PATH`, каталог кэша — через `RAG_CACHE_DIR`.
Файлы индексов создаются отдельной командой `python -m llm_agent.indexing build`;
после изменения корпуса требуется пересборка. Подробности:
[INDEXING.md](INDEXING.md) и [RAG.md](RAG.md).

Общий корпус RAG и ассистента разработчика задан в
`examples/indexing/corpus.json`: README и выбранные руководства
из `docs/`, включая этот документ. Учебные задания, переписки, планы и отчёты
не добавляются автоматически. Настройка справки по проекту описана
в [PROJECT_HELP.md](PROJECT_HELP.md).

## MCP и инструменты проекта

`llm_agent/mcp_config.py` хранит подключения MCP-серверов.
`mcp_client.py` получает каталог и вызывает инструменты через Streamable HTTP.
`mcp_tools.py` связывает имена и схемы MCP с вызовами инструментов модели.
`mcp_results.py` передаёт результаты предыдущих вызовов по ссылкам,
а `tool_events.py` описывает сохраняемый журнал и вложения.
`observations.py` предоставляет чтение накопленных наблюдений.

Настройки серверов общие для CLI и веб-чата. Подключение включается явно;
его каталог и вызовы доступны со следующего сообщения. URL и имя переменной
авторизации сохраняются в `mcp.sqlite3`. MCP-сервер запускается отдельным
процессом. Протокол и настройка: [MCP.md](MCP.md); многошаговые запросы:
[ORCHESTRATION.md](ORCHESTRATION.md).

## Данные, память и настройки

По умолчанию CLI и веб используют общий каталог `data/conversations/`.
Аргумент `--data-dir` позволяет выбрать другой каталог в обоих интерфейсах.

| Файл или модель данных | Содержимое |
|---|---|
| `data/conversations/<id>.json` | Полная лента сообщений, настройки диалога, выбранная модель, рабочий контекст, результаты RAG и журнал инструментов. |
| `data/conversations/memory.sqlite3` | Рабочая память отдельной задачи и общие долговременные записи. |
| `data/conversations/profiles.sqlite3` | Профили пользователя и выбор профиля для диалогов. |
| `data/conversations/models.sqlite3` | Подключения LLM и настройки поддерживаемых форматов ответа. |
| `data/conversations/mcp.sqlite3` | Подключения MCP-серверов и их состояние включения. |
| `data/invariants.json` | Общие инварианты; по умолчанию файл рядом с каталогом диалогов. |
| `llm_agent/models.py` | `Conversation`, `Turn`, `ContextSettings`, `RAGSettings` и `RequestOptions`. |
| `llm_agent/task_state.py` | `TaskState`, этапы и правила переходов задачи. |
| `llm_agent/response_schemas.py` | JSON Schema структурированных ответов и служебных запросов. |
| `llm_agent/structured_output.py` | Выбор поддерживаемого моделью структурированного формата. |

Краткосрочный контекст ограничивается выбранной стратегией истории.
Явная рабочая память хранится отдельно для задачи; долговременная память
общая для диалогов одного хранилища. Эти записи добавляются через редактор
памяти или CLI-команды. Память RAG-диалога (`dialogue_task_memory`) хранит
цель, уточнения, ограничения и термины отдельно от сокращаемой истории.
Профили персонализации также хранятся отдельно от истории.

## Проверка проекта

Автоматические проверки запускаются из корня проекта:

```powershell
.\venv\Scripts\python.exe -m unittest discover -s tests -q
.\venv\Scripts\python.exe -m unittest discover -s tests -p "test_indexing*.py" -v
```

Тесты отдельных подсистем находятся в файлах `tests/test_*.py`.
Настройка MCP, RAG, памяти и моделей проверяется своими группами тестов.
Ручные сценарии и команды приведены в соответствующих руководствах `docs/`.
