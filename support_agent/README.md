# Поддержка пользователей LLMAgent — день 33

Отдельное веб-приложение для вопросов о продукте `llm_agent`. Оно получает
демонстрационные данные пользователей и тикетов через настоящий MCP, ищет
инструкции в отдельном индексе документации и отвечает через облачный DeepSeek.

В интерфейсе есть выбор демонстрационного пользователя, его обращения или
общего вопроса, чат, использованные документы и контекст ответа. Настроек модели,
RAG, профилей, инвариантов и инструментов в пользовательском интерфейсе нет.
Существующий агент, его модельный каталог и индекс не изменяются.

## Запуск в текущем проекте

Все команды выполняются из корня репозитория в PowerShell. Используются уже
установленные зависимости корневого `requirements.txt`; новые пакеты не нужны.

1. В корневом `.env` должен быть `DEEPSEEK_API_KEY` либо уже используемый `API_KEY`.
   При наличии обоих применяется `DEEPSEEK_API_KEY`. Существующий `.env` не нужно
   заменять. Значение ключа не отправляется браузеру и не записывается в диалог.

2. Один раз соберите отдельный индекс поддержки:

   ```powershell
   .\venv\Scripts\python.exe -m support_agent.index
   ```

   Команда берёт модель и ревизию из текущего индекса LLMAgent
   (`RAG_INDEX_PATH` либо `data/indexes/structural.sqlite3`) и использует уже
   скачанные веса из `RAG_CACHE_DIR`. Сеть для этой команды выключена. Новый индекс
   сохраняется в `data/support/index/structural.sqlite3`; исходный не заменяется.
   В текущем окружении используется `intfloat/multilingual-e5-base`.

3. В отдельном терминале запустите MCP через его собственное окружение:

   ```powershell
   .\SupportMCPServer\venv\Scripts\python.exe -m SupportMCPServer.server
   ```

   Если терминал уже открыт в `SupportMCPServer`, используйте
   `.\venv\Scripts\python.exe .\server.py`. При активированном окружении этого
   каталога достаточно `python server.py`.

4. Во втором терминале запустите сервис поддержки:

   ```powershell
   .\venv\Scripts\python.exe -m support_agent
   ```

5. Откройте [http://127.0.0.1:8081](http://127.0.0.1:8081). Оба процесса
   останавливаются через Ctrl+C. На порту 8080 по-прежнему можно отдельно
   запускать основной веб-чат LLMAgent.

MCP по умолчанию слушает `127.0.0.1:8001/mcp`. Для другого порта используйте
`python -m SupportMCPServer.server --port 8002` и `SUPPORT_MCP_URL` в `.env`.
Порт интерфейса меняется через `python -m support_agent --port 8082`.

## Подготовка индекса на другой машине

Если готового индекса LLMAgent нет, существующий индексатор умеет собрать корпус
поддержки напрямую. Первая сборка требует скачивания embedding-модели:

```powershell
.\venv\Scripts\python.exe -m llm_agent.indexing build --corpus docs/support/corpus.json --strategy structural --model intfloat/multilingual-e5-base --output-dir data/support/index --cache-dir data/model-cache
```

Для последующего поиска укажите `RAG_CACHE_DIR=data/model-cache` в корневом
`.env`. После изменения документов повторите сборку. Проверка без LLM и загрузки
весов: `python -m llm_agent.indexing verify --strategy structural --output-dir data/support/index`.

Используется прежний `Retriever`, embedding-адаптер и формат SQLite. Это модель
поиска, а не локальная чат-модель. Сервис не обращается к Ollama/LM Studio для
генерации ответа и не меняет их настройки.

## Серверная конфигурация

| Переменная | По умолчанию |
|---|---|
| `DEEPSEEK_API_KEY` / `API_KEY` | Ключ из корневого `.env` |
| `SUPPORT_DEEPSEEK_MODEL` | `deepseek-flash` |
| `SUPPORT_MCP_URL` | `http://127.0.0.1:8001/mcp` |
| `SUPPORT_MCP_TOKEN_ENV` | Пусто для локального demo MCP |
| `SUPPORT_INDEX_PATH` | `data/support/index/structural.sqlite3` |
| `SUPPORT_DATABASE_PATH` | `data/support/conversations.sqlite3` |
| `RAG_CACHE_DIR` | Существующий кеш embedding-модели |

Адрес LLM фиксирован: `https://api.deepseek.com`. Текущая модель и отключение
thinking выбраны по [официальной документации DeepSeek](https://api-docs.deepseek.com/)
и [документации thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/).
За один вопрос выполняется один облачный запрос, без автоматических повторов.
При настройке другого API ID через `.env` он должен поддерживать JSON output.

## Как формируется ответ

1. Backend знает выбранного демопользователя и тикет; модель не выбирает их ID.
2. `get_support_context` получает свежий снимок JSON через MCP. Сервер проверяет
   принадлежность тикета пользователю. При ошибке MCP генерация не начинается.
3. Короткий запрос из вопроса, темы/ошибки тикета и предыдущего вопроса используется
   для RAG. Поиск возвращает до пяти фрагментов из whitelist документации.
4. DeepSeek получает системные правила, последние **10 сообщений истории**
   (пять завершённых пар), свежий контекст, документы и текущий вопрос.
   Текущий вопрос и справочные данные добавляются сверх окна истории.
5. JSON-ответ проверяется; ссылки разрешены только на найденные документы.
   В SQLite сохраняются последние пять пар с источниками и снимком контекста.

История разделена по cookie браузера, пользователю и тикету, переживает рестарт.
Смена тикета или пользователя переключает историю; «Новый диалог» очищает только
текущий контекст. Сжатия, извлечения фактов, долговременной памяти и планировщика нет.
Параллельные отправки/очистка одного диалога отклоняются до завершения ответа.
Приложение запускается одним worker.

Документация подтверждает инструкции продукта, MCP — факты о клиенте, история —
уточнения и уже испробованные действия. При пустом или недоступном RAG сервис
может ответить по данным тикета либо задать вопрос; предупреждение отображается
отдельно. Проверка source ID подтверждает существование источника, но не доказывает
логическое следование ответа: содержательное качество оценивается сценариями ниже.

Корпус и причины исключения старых учебных документов описаны в
[docs/support/README.md](../docs/support/README.md). Тексты тикетов и пользователи
в RAG не индексируются. Весь доступ к их JSON выполняет только MCP-сервер.

## Демонстрация

| Пользователь / обращение | Вопрос | Ожидаемое поведение |
|---|---|---|
| Алексей / `t-rag-off` | Почему агент не использует документацию? | Учитывает выключенный RAG и готовый индекс, объясняет включение |
| Мария / `t-index-missing` | Тот же вопрос | Учитывает включённый RAG и отсутствующий индекс, объясняет проверку/сборку |
| Иван / `t-mcp-disabled` | Почему Get tools работает, но агент не вызывает MCP? | Объясняет включение «Использовать в чате» |
| Алексей / `t-setup-resolved` | Какой статус моего обращения? | Отвечает по MCP, документы для статуса не обязательны |
| Любой / общий вопрос | Как добавить облачную модель? | Отвечает по документации без тикета |
| Продолжение первого диалога | А где именно это включить в веб-чате? | Понимает продолжение из короткой истории |

Данные синтетические, `observed_at` — время фиктивного наблюдения, а не живая
диагностика компьютера. Выбор демонстрационного пользователя не является входом
в реальную учётную запись. Серверы по умолчанию доступны только локально; версия
предназначена для учебного стенда. Прямую публичную эксплуатацию с реальными
клиентами нужно дополнять аутентификацией и серверной привязкой личности.
Изменение настроек, создание/закрытие тикетов и передача оператору не реализованы.

## Проверки

```powershell
.\venv\Scripts\python.exe -m unittest tests.test_support_service tests.test_support_web SupportMCPServer.tests.test_support -v
```

Проверяются порядок MCP → RAG → LLM, разные ответы при разном контексте,
изоляция и ограничение истории, отказ в чужом тикете, отсутствие секретов в
ответах, неизвестные source ID, сбои RAG/генерации, параллельные запросы и
настоящий Streamable HTTP MCP. Модель в автоматических тестах заменена заглушкой.

Основные файлы: `service.py` — сценарий; `crm.py` — адаптер MCP;
`generation.py` — DeepSeek и контракт ответа; `storage.py` — короткая история;
`web.py` и `static/` — API и интерфейс. Общие компоненты импортируются из
`llm_agent`, без наследования от универсального `Agent`.
